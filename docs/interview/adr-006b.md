# ADR-006b 꼬리 질문: 복구 작업자·보상 취소

[ADR-006b](../adr/006b-recovery-compensation.md)에 대한 예상 질문과 답이다(기획서 §12-3).

## 1. 결제 승인은 됐는데 DB 저장 직전에 서버가 죽으면 어떻게 되나요?
돈은 나갔는데 우리 기록은 "결제 확인 중"으로 남은 상태입니다. 처음 설계에서는 이 경우 결제를 취소해 돌려주기로 했는데, 다시 보니 그럴 필요가 없었습니다. 주문은 결제 확인 중 상태에서 만료되지 않기 때문입니다. 그래서 복구 작업자가 1분마다 오래된 "확인 중" 결제를 찾아 토스에 조회하고, 승인됐으면 주문을 결제 완료로 마무리합니다. 고객은 돈을 돌려받는 대신 정상적으로 주문을 받습니다. 이게 가능하려면 승인을 부르기 전에 paymentKey를 같은 트랜잭션에 저장해 둬야 하고, 그렇게 설계했습니다.

## 2. 그럼 보상 취소는 언제 하나요?
돈은 승인됐는데 주문이 그 돈을 받을 수 없을 때만 합니다. 예를 들어 이미 만료된 주문에 승인이 확인된 경우입니다. 만료된 주문은 되살리지 않는 것이 원칙이라, 그 결제 시도를 "고아"(`ORPHANED`)로 표시하고 취소합니다. 정상 흐름에서는 일어나지 않아야 하는 일이라 항상 오류 로그를 남깁니다.

## 3. 웹훅이 위조되면요?
웹훅 내용은 믿지 않습니다. 웹훅은 "이 결제를 다시 조회해 보라"는 신호로만 쓰고, 상태는 토스에 직접 조회한 결과로만 바꿉니다. 그리고 우리 DB에 있는 paymentKey만 조회합니다. 누군가 가짜 웹훅을 대량으로 보내도 우리가 토스 조회를 남발하지 않게 하기 위해서입니다. 서명 헤더는 재전송에는 붙지 않아서 필수 조건으로 쓸 수 없었습니다.

## 4. 같은 웹훅이 여러 번 오면요?
`(paymentKey, 상태, 생성 시각)`에 유니크 키를 걸어 두 번째부터는 저장되지 않게 했습니다. 처음에는 전송 ID를 쓰려 했지만, 실제로 받아 보니 재전송할 때마다 전송 ID가 바뀌었습니다. 생성 시각은 재전송해도 그대로였습니다. 그리고 설령 처리가 두 번 일어나도, 상태 전이는 "이미 목표 상태면 아무것도 하지 않는다"는 규칙이라 결과가 같습니다.

## 5. 취소 멱등키에 왜 숫자 ID 대신 UUID를 쓰나요?
토스는 멱등키를 15일 동안 기억합니다. 개발 중에 DB를 초기화하면 취소 요청 번호가 1번부터 다시 시작하는데, 그러면 `cancel-1`이라는 키로 보낸 새 취소에 토스가 예전 결제의 취소 응답을 돌려줄 수 있습니다. 또 고객 취소와 보상 취소를 서로 다른 표에 두면 번호가 겹칠 수도 있습니다. 그래서 취소 기록을 한 표로 모으고, 키는 겹칠 수 없는 UUID로 만들었습니다.
