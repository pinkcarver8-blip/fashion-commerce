# ADR-009 꼬리 질문: 프론트 구조

[ADR-009](../adr/009-frontend-structure.md)에 대한 예상 질문과 답이다(기획서 §12-3).

## 1. 고객 앱과 관리자 앱을 왜 따로 만들었나요? 보안 때문인가요?
보안 때문은 아닙니다. 관리자 앱도 주소만 알면 누구나 내려받을 수 있어서, 앱을 나눈다고 보안이 생기지는 않습니다. 보안은 서버의 권한 검사와 토큰 분리가 맡습니다. 앱을 나눈 이유는 번들 위생입니다. 한 앱에 두면 관리자 화면 코드와 관리자 API 경로가 고객이 받는 파일에 섞여 들어갑니다. 따로 빌드하고, 고객 앱이 관리자 코드를 import하면 린트가 실패하게 했습니다.

## 2. 전역 상태 관리 라이브러리를 안 쓴 이유는요?
커머스 화면의 상태는 대부분 서버 데이터입니다. 상품, 장바구니, 주문이 그렇습니다. 이건 TanStack Query가 캐시하고, 오래되면 다시 불러오고, 화면 사이에서 공유합니다. 그러고 나면 남는 전역 상태는 로그인 여부 정도라 Context로 충분했습니다. 라이브러리를 하나 덜 쓰면 의존성 관리와 공급망 위험도 줄어듭니다.

## 3. 액세스 토큰이 만료되면 프론트에서는 어떻게 처리하나요?
API 클라이언트가 401을 받으면 리프레시 요청을 한 번 보내 새 액세스 토큰을 받고, 실패했던 요청을 다시 보냅니다. 화면 여러 곳에서 동시에 401이 나도 리프레시는 한 번만 일어나게 묶습니다. 그러지 않으면 리프레시 토큰 회전 때문에 두 번째 리프레시가 "이미 쓴 토큰"으로 보여 로그인 전체가 폐기될 수 있습니다. 토큰은 메모리 변수에만 둡니다.

## 4. 스타일 방식을 왜 "임시"로 정했나요?
디자인 토큰이 아직 임시 값이고, 디자인 도구도 확정되지 않았습니다. 지금 Tailwind 같은 방식을 정하면 디자인이 나온 뒤 설정을 다시 만들어야 할 수 있습니다. 그래서 Vite가 기본으로 지원해 의존성이 늘지 않는 CSS Modules로 시작하고, 색·간격·글꼴은 반드시 `tokens.css` 변수만 쓰게 했습니다. 나중에 방식을 바꿔도 값은 토큰 한 곳에 모여 있어서 옮기는 범위가 작습니다.

## 5. API 타입은 어떻게 맞추나요?
백엔드가 springdoc으로 OpenAPI 문서를 만들고, 프론트는 그 문서에서 TypeScript 타입을 생성합니다. 백엔드에서 필드 이름을 바꾸면 프론트 빌드에서 타입 오류로 바로 드러납니다. 다만 호출 코드까지 생성하지는 않았습니다. 토큰 갱신과 오류 처리 같은 핵심 로직이 생성 코드에 묻히지 않게, fetch 래퍼는 직접 썼습니다.
