# ADR-007 꼬리 질문: QueryDSL

[ADR-007](../adr/007-querydsl.md)에 대한 예상 질문과 답이다(기획서 §12-3). 답의 근거는 [R0-04 보고서](../reports/r0-querydsl.md)다.

## 1. QueryDSL은 유지보수가 멈췄다는데 왜 썼나요?
원본은 Spring Data 문서에도 유지보수가 느려졌다고 적혀 있어서 쓰지 않았습니다. 대신 커뮤니티 포크(OpenFeign)를 썼습니다. 쓰기 전에 Java 21, Boot 4.1.3, Hibernate 7.4, MySQL 8.4 조합에서 시험 프로젝트로 빌드와 실제 조회를 먼저 확인했습니다(R0-04). 위험은 범위로 줄였습니다. QueryDSL은 읽기 조회 전용 클래스에만 두어서, 포크가 멈추면 그 클래스만 Specification이나 JPQL로 바꾸면 됩니다. 언제 다시 검토할지(12개월 무배포, 버전을 올렸을 때 깨짐)도 ADR에 적어 두었습니다.

## 2. 왜 쓰기(UPDATE)에는 QueryDSL을 안 쓰나요?
돈과 재고를 바꾸는 쓰기는 이 프로젝트에서 가장 엄격하게 검토하는 코드라서, 쓰는 방법을 한 가지로 묶었습니다. 재고 차감은 `qty >= n` 조건을 붙인 원자적 UPDATE이고, 영향받은 행 수로 성공 여부를 판단합니다. 이런 쿼리는 조건이 고정되어 있어 동적 조회 도구가 필요 없습니다. 그래서 `@Modifying` JPQL로 쓰고, ArchUnit으로 QueryDSL의 update·delete·insert 사용을 막습니다.

## 3. 빈 검색 조건은 어떻게 처리했나요?
조건마다 값이 없으면 `null`을 돌려주는 작은 메서드를 만들고 `where(...)`에 넘깁니다. QueryDSL은 `null` 조건을 건너뜁니다. 실제로 조건을 모두 비웠을 때 나간 SQL에는 `where` 절이 아예 없었고, 가격 범위만 줬을 때는 `price >= ? and price <= ?`만 붙었습니다. 조건 조합마다 쿼리를 따로 쓰지 않아도 됩니다.

## 4. 페이지 조회에서 개수 쿼리는 어떻게 했나요?
`PageableExecutionUtils.getPage`를 썼습니다. 첫 페이지에서 가져온 건수가 페이지 크기보다 적으면 전체 개수를 이미 알 수 있으므로 개수 쿼리를 실행하지 않습니다. 시험에서도 다섯 시나리오 중 페이지 크기 2인 경우에만 `count` 쿼리가 한 번 나갔습니다. 개수 쿼리에는 조인을 넣지 않고 필요한 조건만 넣었습니다.

## 5. SQL 주입은 안전한가요?
값은 바인딩 파라미터(`?`)로 들어가므로 문자열을 이어 붙이는 방식보다 안전합니다. 그래도 두 곳은 조심해야 합니다. 하나는 `Expressions.stringTemplate` 같은 템플릿 함수입니다. 여기에 사용자 입력을 넣으면 주입이 가능하므로 넣지 않습니다. 다른 하나는 정렬입니다. 정렬 필드를 요청에서 받을 때 속성 이름을 그대로 쓰지 않고, 허용한 값만 Q클래스 경로로 매핑합니다.
