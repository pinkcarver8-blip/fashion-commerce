# ADR-005 꼬리 질문: 재고 3계층·원장·만료 분리·TTL·잠금 순서

[ADR-005](../adr/005-inventory-reservation.md)에 대한 예상 질문과 답이다(기획서 §12-3).

## 1. 재고 1개에 100명이 동시에 주문하면 어떻게 하나만 성공하나요?
예약을 `UPDATE sku_stock SET available = available - 1, reserved = reserved + 1 WHERE sku_id = ? AND available >= 1` 한 문장으로 합니다. MySQL은 이 행을 갱신하는 동안 행 잠금을 잡기 때문에 문장들이 차례로 실행됩니다. 첫 문장만 조건을 만족해 영향 행 1을 돌려받고, 나머지는 0을 받아 재고 부족으로 처리됩니다. DB에 `available >= 0` CHECK 제약도 걸어서 코드가 실수해도 음수가 되지 않습니다.

## 2. 여러 상품을 주문할 때 데드락은 어떻게 막나요?
잠금 순서를 하나로 정했습니다. 주문이 걸린 작업은 주문 행을 먼저 잠그고, SKU 행은 언제나 ID 오름차순으로 건드립니다. 두 트랜잭션이 같은 자원을 같은 순서로 잡으면 서로를 기다리는 원이 생기지 않습니다. A·B를 반대 순서로 담은 주문 두 건을 동시에 보내는 테스트로 고정합니다.

## 3. 예약 만료와 주문 만료를 왜 나눴나요?
처음 설계에서는 둘을 10분 하나로 묶었는데, 고객이 정상적으로 결제하는 도중에도 예약이 풀리는 버그였습니다. 지금은 예약은 20분 뒤에 풀 수 있지만 주문이 결제 확인 중(`CONFIRMING`)이면 건드리지 않습니다. 주문은 결제 대기로 남아 있다가 40분이 지나야 만료됩니다. 예약이 먼저 풀려도 결제 확정 직전에 재고를 다시 잡기 때문에 버그가 되지 않습니다. 다시 잡지 못하면 승인 API를 부르지 않으므로 돈도 나가지 않습니다.

## 4. 원장은 왜 필요하고, "정확히 한 번"은 어떻게 보장하나요?
원장은 재고가 왜 이 숫자인지 설명하는 기록입니다. SKU별 증감 합계가 현재 재고와 같은지 테스트가 끝날 때마다 검사합니다. "정확히 한 번"은 두 겹으로 지킵니다. 예약 기록은 `WHERE status = 'ACTIVE'` 조건으로 한 번만 해제되거나 소진되고, 원장에는 `(근거 유형, 근거 ID, 사유, SKU)` 유니크 키가 있어 같은 취소로 재고를 두 번 복구하려 하면 DB가 막습니다.

## 5. TTL 20분과 만료 40분은 어떻게 정했나요?
토스 테스트 서버에서 직접 재 봤습니다. 인증 뒤 승인하지 않은 결제는 30분이 지나고 1분쯤 안에 `EXPIRED`가 됐습니다. 우리 주문 만료를 그보다 길게(결제창을 마지막으로 연 시각부터 40분) 잡아서, 고객이 인증을 마쳤다면 토스 쪽 결과가 먼저 나오게 했습니다. 예약 TTL은 재고를 오래 묶지 않으려는 정책값이라 결제창 체류 시간을 약 10분으로 가정하고 여유를 더해 20분으로 정했습니다. 실제 이탈 데이터가 없어서 가정이고, 데이터가 생기면 다시 봅니다. 둘 다 설정값이고, 드롭처럼 재고 회전이 중요한 상황에서는 줄입니다.
