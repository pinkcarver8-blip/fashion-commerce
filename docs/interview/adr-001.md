# ADR-001 꼬리 질문: 모듈러 모놀리스와 동기 호출 목록

[ADR-001](../adr/001-modular-monolith.md)에 대한 예상 질문과 답이다(기획서 §12-3).

## 1. 왜 MSA가 아니라 모듈러 모놀리스인가요?
결제 흐름에는 한 트랜잭션이어야 하는 곳이 있습니다. 주문 생성, 재고 예약, 결제 시도 생성은 같이 성공하거나 같이 실패해야 합니다. 서비스를 나누면 이 부분이 분산 트랜잭션이나 보상 흐름이 됩니다. 혼자 만드는 프로젝트에서 그 비용을 먼저 치를 이유가 없었습니다. 대신 나중에 떼어 낼 수 있게 모듈 경계를 ArchUnit으로 CI에서 강제하고, 어떤 측정값이 나오면 분리를 검토할지 ADR에 적어 두었습니다. Shopify도 모듈러 모놀리스로 플래시 세일을 처리한다는 점을 참고했습니다.

## 2. 모듈끼리 트랜잭션을 공유하면 경계가 무슨 의미가 있나요?
경계의 목적은 "누가 누구를 부를 수 있는가"를 고정하는 것입니다. 다른 모듈의 엔티티나 리포지토리를 직접 건드리지 않고 공개 API로만 부르게 하고, 모듈 사이에 JPA 연관을 걸지 않고 ID로만 참조합니다. 그러면 트랜잭션을 공유하더라도 상태를 바꾸는 코드는 각 모듈 안에만 있습니다. 나중에 모듈을 떼어 낼 때도 끊어야 할 호출이 표에 다 나와 있습니다.

## 3. "주문 생성"을 왜 order가 아니라 payment 쪽에서 조율하나요?
order가 결제 시도를 만들려고 payment를 부르고, payment가 승인 뒤 주문 상태를 바꾸려고 order를 부르면 둘이 서로를 부르는 순환이 됩니다. 순환을 끊는 방법은 두 가지였습니다. 결제 흐름 전체를 payment가 조율하는 방법과, order가 조율하고 payment는 인터페이스로 결과를 돌려주는 의존 역전입니다. 뒤의 방법은 인터페이스와 구현이 모듈을 오가서 흐름을 따라가기 어렵고, ArchUnit 규칙에도 예외가 생깁니다. 그래서 이름이 조금 어색해지는 것을 감수하고 앞의 방법을 골랐습니다.

## 4. Spring Modulith를 쓰지 않은 이유는 뭔가요?
호환성 문제는 아닙니다. Modulith 2.1 계열은 Spring Boot 4.1을 따라갑니다. 다만 QueryDSL을 조회 전용으로만 쓰는 규칙과 돈 필드 타입 같은 코드 규칙은 어차피 ArchUnit으로 검사해야 했습니다. (처음에는 `@Setter` 금지도 ArchUnit으로 검사한다고 했는데, Lombok 표시는 컴파일 뒤에 남지 않아서 `lombok.config` 설정으로 바꿨습니다.) 도구를 둘로 나누면 규칙이 두 곳에 흩어지고 의존성도 늘어납니다. Outbox를 만드는 R2a에서 Modulith의 이벤트 발행 기록 기능은 다시 비교하기로 했습니다.

## 5. 언제 모듈을 떼어 낼 건가요?
측정 근거가 있을 때만 뗍니다. 후보는 드롭 모듈입니다. R3 부하 테스트에서 드롭 트래픽 때문에 주문·결제 경로가 목표를 넘고, 커넥션 풀을 나누고 튜닝해도 풀리지 않으면 분리를 검토합니다. Shopify 사례에서도 진짜 병목은 커넥션 풀이었기 때문에, 서비스를 나누기 전에 그쪽부터 봅니다.

## 6. 모듈 경계 규칙이 정말 동작하는지는 어떻게 확인했나요? (R0-06)
규칙마다 일부러 어긴 예시 코드를 시험 폴더에 두고, 그 예시에서 규칙이 실패하는지 봤습니다. 예를 들어 재고 모듈이 주문 모듈을 부르는 클래스, 결제와 주문이 서로를 부르는 클래스를 만들어 두었습니다. 실패했다는 것만 보지 않고, 실패 내용에 그 예시 클래스 이름이 있는지까지 확인합니다. 엉뚱한 이유로 실패한 것을 통과로 착각하지 않기 위해서입니다. 반대로 허용되는 예시 묶음은 모든 규칙을 통과해야 합니다. 규칙이 무엇이든 실패시키는 엉터리가 아니라는 확인입니다.

## 7. 공개 API 패키지만 쓰게 하면, 공개 API가 엔티티를 그대로 돌려주는 경우는요?
그 구멍이 있어서 규칙을 하나 더 뒀습니다. `<모듈>.api` 패키지의 public 메서드가 같은 모듈의 내부 타입(엔티티 등)을 매개변수나 반환 타입으로 쓰면 실패합니다. `List<Order>`처럼 제네릭 안에 들어간 것, 공개 API 클래스가 엔티티를 상속하는 것, `throws`로 내부 예외를 드러내는 것도 잡습니다. 그래서 공개 API는 DTO(record)와 공개 패키지의 타입만 주고받습니다. 독립 검토에서 상속과 `throws` 구멍을 지적받아 넣었습니다.

## 8. 관리자 API를 admin 모듈에만 두는 것을 어떻게 막나요?
컨트롤러의 `@RequestMapping` 계열 경로를 읽어서 세 가지를 봅니다. admin 모듈 밖에서 `/api/admin`으로 시작하는 경로를 열면 실패하고, 클래스 경로 `/api`와 메서드 경로 `/admin/x`를 이어 붙여 관리자 경로가 되는 경우도 잡습니다. admin 모듈의 컨트롤러는 클래스 경로가 정확히 `/api/admin` 아래여야 합니다. 처음에는 `admin`으로 시작하기만 하면 통과시켰는데, 독립 검토에서 `/api/admins`가 통과한다는 지적을 받았습니다. 보안 설정은 `/api/admin/**`만 관리자 체인으로 보내므로, 그런 경로는 관리자 화면인데 고객 로그인으로 열리는 구멍이었습니다. 지금은 보안 설정과 글자 그대로 같은 기준을 씁니다. Spring이 상위 클래스·인터페이스의 경로도 합쳐 쓰므로 그것까지 봅니다. 마지막으로 admin 밖에서 `/api/{변수}`·`/api/admi?`처럼 관리자 경로와 겹칠 수 있는 패턴도 막습니다. 함수형 라우팅은 못 잡으므로 쓰지 않기로 했고, 최종 방어는 보안 필터 체인입니다.

## 9. 공통 코드(common 폴더)는 어떻게 관리했나요?
공통 폴더를 두지 않았습니다. 공통 폴더는 모든 모듈이 부를 수 있어서, 두 모듈이 같이 쓰는 업무 규칙(예: 배송비 계산)을 옮겨 놓으면 모듈 호출 표를 피하는 뒷문이 됩니다. 대신 이름과 할 일이 정해진 공유 모듈 다섯 개(금액, 외부 ID, 오류 형식, 로그인한 사람 정보, 앱 설정)로 나눴습니다. 앱 설정 모듈은 아무도 부를 수 없게 했고, 나머지 넷은 DB와 업무 처리 표시를 쓸 수 없으며 정적 함수는 자기 타입을 만드는 것만 둡니다. 마지막으로 네 모듈의 클래스와 공개 함수를 허용 목록에 적어 두고, 목록과 코드가 다르면 시험이 실패하게 했습니다. 목록을 바꾸려면 사람이 승인해야 하므로, 공유 코드에 무엇이 들어오는지 사람이 모르게 바뀌지 않습니다. 남는 한계는 목록에 있는 함수의 속을 바꾸는 것인데, 이건 그 함수의 단위 시험으로 잡습니다.
