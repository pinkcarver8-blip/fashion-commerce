# ADR-010 꼬리 질문: 공통 규약

[ADR-010](../adr/010-common-conventions.md)에 대한 예상 질문과 답이다(기획서 §12-3). 이유의 출처는 `기획근거/7_작업진행근거.md` 라운드 9다.

## 1. 주문번호를 왜 UUIDv7로 하지 않았나요?
UUIDv7은 앞부분에 생성 시각이 들어 있어서, 주문번호만 보고 언제 주문했는지 알 수 있습니다. 외부 ID의 목적은 인덱스 성능이 아니라 추측할 수 없게 하는 것이라 UUIDv4를 썼습니다. 인덱스 성능은 내부 PK를 순차 `BIGINT`로 두어 지켰습니다. 그리고 추측 불가 ID는 2차 방어일 뿐이고, 1차 방어는 모든 주문·결제 API의 소유자 검사입니다. 처음에는 저도 흔히 권하는 UUIDv7을 쓸 뻔했다가 보안 재검토에서 고쳤습니다.

## 2. 금액을 왜 `BigDecimal`이 아니라 `long`으로 했나요?
원화에는 소수 단위가 없어서 원 단위 정수로 충분합니다. `long`이면 부동소수점 오차가 없고, `BigDecimal`의 `equals`가 scale까지 비교하는 것 같은 실수도 없습니다. 대신 `long`을 그대로 쓰지 않고 `Money` 값 객체로 감싸서, 금액 연산을 한 곳에 모았습니다. 외국 통화를 다루게 되면 다시 검토한다고 ADR에 적었습니다.

## 3. 시간은 어떻게 다뤘나요?
저장은 모두 UTC(`Instant`, `DATETIME(6)`)입니다. JVM, JDBC, Jackson, 컨테이너의 시간대를 각각 UTC로 명시하고, 하나라도 어긋나면 실패하는 테스트를 CI에 둡니다. 한 곳만 기본값에 기대면 배포 환경이 바뀔 때 9시간 어긋나기 때문입니다. 반대로 환급 기한처럼 사람이 쓰는 "날짜"가 필요한 계산은 Asia/Seoul 날짜로 합니다.

## 4. 오류 응답은 어떤 형식인가요?
RFC 9457 Problem Details에 우리가 정한 `code`를 더했습니다. 프론트는 `code`로 분기하고, 코드는 API 명세서에 목록으로 둡니다. 응답에는 스택 트레이스나 예외 메시지를 싣지 않고, 로그인 실패는 "아이디 또는 비밀번호가 맞지 않습니다"처럼 일반화해서 계정이 있는지 알 수 없게 했습니다.

## 5. 공급망 보안은 무엇을 했나요?
pnpm 11은 공개된 지 하루가 안 된 버전과 의존성 설치 스크립트를 기본으로 막습니다. 2025년 npm 웜 사건 이후라 이 기본 보호를 끄지 않는 것을 규칙으로 했습니다. 그 밖에 잠금 파일을 커밋하고 CI는 고정 설치만 하며, Gradle wrapper가 변조되지 않았는지 검증하고, GitHub Actions는 태그가 아니라 커밋 SHA로 고정했습니다. AI가 제안한 패키지는 실제로 있는 이름인지 확인합니다. 이름만 비슷한 가짜 패키지를 막기 위해서입니다.
