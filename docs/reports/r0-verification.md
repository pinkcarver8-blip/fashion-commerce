## 1. 결제 조회 (paymentKey)

`GET /v1/payments/{paymentKey}`.

| 상황 | 실제 응답 | 조치 |
|---|---|---|
| 없는 paymentKey | 404 `NOT_FOUND_PAYMENT` "존재하지 않는 결제 정보 입니다." | 우리 기록과 PG가 어긋난 것. 자동 처리하지 않고 운영자 큐로 보낸다 |
| 인증 직후, 승인 전 | 200 `IN_PROGRESS`, `method`·`approvedAt` = null | 승인을 진행한다(10분 안) |
| 승인 후 | 200 `DONE`, 승인 응답과 같은 본문 | 결제 완료로 확정한다 |
| 취소 후 | 200 `CANCELED`, `cancels[]`에 취소 내역, `balanceAmount` 0 | 취소 완료로 확정한다 |
| 우리 쪽 타임아웃 | 응답 없음(`SocketTimeoutException`) | 같은 멱등키로 재시도 또는 조회(§3 E) |
| 만료 | §2 참조 | |

- `requestedAt`은 인증 완료 시각이 아니라 **결제창을 연 시각**이다. C는 결제하기를 누른 13:44:56(이 PC 시계)에 대해 `requestedAt`이 13:44:59였다. 3초 차이는 시계 차이다.
- `ABORTED`는 이번에 나오지 않았다. 승인 실패를 일부러 만들 방법이 테스트 환경에 없었다.
- 응답 시간: 조회는 105~254ms, 승인은 596~749ms, 취소는 651ms였다.

## 2. 결제 유효 시간 30분과 승인 10분 제한

문서: 인증 후 10분 안에 승인해야 한다. `IN_PROGRESS`에서 30분 동안 승인하지 않으면 `EXPIRED`가 된다.

| 주문 | 경과 | 실제 |
|---|---|---|
| D | 인증(13:46:13) 10분 31초 뒤 승인 | 400 `EXPIRED_PAYMENT` "결제가 만료되었습니다. 다시 시도해주세요." 바로 조회하니 200 **`ABORTED`**, `failure.code` `EXPIRED_PAYMENT` |
| C | 인증(13:45:26) 뒤 승인하지 않고 1분마다 조회 | 10분, 20분, 30분이 지나도 `IN_PROGRESS`. 14:16:42(토스 시각)에 **`EXPIRED`**, `failure` null |

- **10분 제한은 상태를 바꾸지 않는다.** C는 10분이 지나도 `IN_PROGRESS`였다. D는 10분 뒤 승인을 시도한 순간 `ABORTED`가 되었다(그 사이 D는 조회하지 않았으므로 정확한 전환 시점은 승인 시도 이전 어딘가다. C와 비교하면 승인 시도가 계기로 보인다).
- 늦은 승인은 `EXPIRED`가 아니라 **`ABORTED` + `EXPIRED_PAYMENT`** 로 끝난다. 문서의 `EXPIRED`만 보고 만료를 판정하면 놓친다.
- **조치**:
  - 승인은 성공 URL이 도착하면 바로 서버에서 한다.
  - 조회 결과 `ABORTED`·`EXPIRED`는 모두 "승인되지 않음, 돈이 나가지 않음"으로 보고 결제 시도를 실패로 닫고 재고 예약을 푼다. 원인은 `failure.code`로 구분해 기록한다.
  - 복구 작업자가 `IN_PROGRESS`를 만나면 같은 멱등키로 승인을 불러도 안전하다. 10분 안이면 승인되고, 지났으면 `EXPIRED_PAYMENT`로 실패가 확정된다. 기다리지 않고 결과를 정할 수 있다.

**C의 만료 시점**(모두 토스 `Date` 헤더 기준. 이 PC 시계보다 약 3초 빠르다)

| 기준 | 시각 | 마지막 `IN_PROGRESS`(14:15:41)까지 | 첫 `EXPIRED`(14:16:42)까지 |
|---|---|---|---|
| `requestedAt`(마지막으로 결제창을 연 시각) | 13:44:59 | 30분 42초 | 31분 43초 |
| 인증 완료(성공 URL 도착) | 약 13:45:29 | 30분 12초 | 31분 13초 |

- 1분 간격으로 조회해서 두 기준 중 어느 쪽인지는 가를 수 없었다. 어느 기준이든 **30분이 지난 뒤 1분쯤 안에** `EXPIRED`로 바뀌었다. 정각에 바뀌지 않으므로 토스 쪽에서 주기적으로 처리하는 것으로 보인다.
- `EXPIRED`는 `failure`가 null이다. 10분 뒤 승인 시도로 생긴 `ABORTED`는 `failure.code`가 `EXPIRED_PAYMENT`였다.
- **조치**: 우리 결제 시도의 만료(재고 예약 해제)는 토스 상태 전환을 기다리지 않고 우리 시계로 판단한다. 판단 전에 paymentKey로 조회해 `DONE`이 아님을 확인한다. 주문 만료 시간을 30분보다 짧게 잡으면 토스에서는 아직 승인할 수 있는 결제가 우리 쪽에서 먼저 만료될 수 있다. 그래서 만료 처리 직전 조회는 빼지 않는다. 시간 값은 B5·ADR에서 정한다.

## 3. 멱등키

헤더 `Idempotency-Key`. 문서: 최대 300자, 15일간 유효, 같은 키로 다시 요청하면 처음 응답을 돌려준다.

| 시나리오 | 실제 응답 | 조치 |
|---|---|---|
| A. 승인 완료 뒤 같은 키로 재승인 | 200 `DONE`, 첫 응답과 같은 본문. 37ms(첫 요청은 616ms) | 재시도는 같은 키로 한다. 저장된 응답을 받으므로 안전하다 |
| A. 승인 완료 뒤 다른 키로 재승인 | 400 `ALREADY_PROCESSED_PAYMENT` "이미 처리된 결제 입니다." | 새 키로 재시도하면 성공 응답을 못 받는다. 이 코드는 "결과 불명"으로 보고 조회로 확정한다 |
| B. 같은 키로 2건 동시 승인 | 하나는 409 `IDEMPOTENT_REQUEST_PROCESSING` "이전 멱등 요청이 처리중입니다."(69ms), 하나는 200 `DONE` | 409는 실패가 아니다. 잠시 뒤 같은 키로 재시도하거나 조회한다 |
| E. 우리 쪽 읽기 타임아웃(1ms) | 응답 없음. 바로 조회하니 `IN_PROGRESS`, 4초 뒤에도 `IN_PROGRESS`. 같은 키로 재승인하니 200 `DONE`(629ms) | 타임아웃은 "결과 불명"이다. 같은 키로 재시도하면 이중 승인 없이 확정된다 |
| F. 틀린 금액(100원)으로 승인 | 403 `FORBIDDEN_REQUEST` "허용되지 않은 요청입니다." 결제는 `IN_PROGRESS` 그대로 | 금액 불일치 전용 코드가 없다. 403은 우리 요청이 틀린 것이므로 재시도하지 않는다 |
| F. 같은 키로 맞는 금액 재승인 | **403 `FORBIDDEN_REQUEST` 그대로**(51ms). 실패 응답도 저장되어 같은 키로는 본문을 고쳐도 같은 응답이 온다 | 같은 키는 같은 요청에만 쓴다. 키는 요청 내용(주문·금액)이 정해진 뒤 만든다 |
| F. 새 키로 맞는 금액 | 200 `DONE` | 금액은 서버에 저장한 값만 쓰므로 이 경로는 우리 버그가 아니면 생기지 않는다 |

- E에서 1ms 요청이 토스에 닿았는지는 구분할 수 없다. 닿았더라도 처리가 끝나지 않았고, 같은 키 재요청이 정상 처리되었다(37ms 저장 응답이 아니라 629ms 실제 처리).
- **설계 확인**: "승인·취소 재시도에 새 멱등키를 쓰지 않는다"(A5-1)가 맞다. A의 다른 키는 400, F의 같은 키는 저장된 실패를 돌려주므로, 키는 `confirm-{결제 시도 ID}`(우리가 토스 orderId로 보내는 값, 우리 주문번호가 아니다)처럼 요청 하나에 하나로 고정한다.

## 5. 거래 조회 API와 계약 전 위젯 키

`GET /v1/transactions?startDate&endDate`. 날짜는 `yyyy-MM-dd'T'HH:mm:ss`이다.

- 1회차: 결제위젯 시크릿 키로 호출하면 200이지만 **결과가 0건**이었다(2026-11-18 두 번, 승인 6건·취소 1건 뒤에도).
- **원인**: 계약 전 결제위젯 키는 내 상점 키가 아니라 토스 문서용 **공용 테스트 상점(`mId` `tgen_docs`)** 키다. 승인 응답의 `mId`가 그 값이었다. 개발자센터의 웹훅 등록과 거래 내역은 내 테스트 상점 기준이라, 위젯 키 결제는 둘 다에 나오지 않는다.
- 확인: 2회차에 내 상점의 **API 개별 연동 키**로 결제창 결제를 하고 2026-11-18~20을 조회했다.

| 키 | 결과 | 응답 시간 |
|---|---|---|
| API 개별 연동 키(내 상점) | 3건: W2 승인, W2 취소, I 승인. 승인하지 않고 만료된 W는 없다 | 7.6초 |
| 결제위젯 키(공용 상점) | 0건(H·K 등 위젯 결제가 있었는데도) | 33ms |

- 항목 필드: `transactionKey`, `paymentKey`, `orderId`, `method`, `customerKey`, `useEscrow`, `receiptUrl`, `status`, `transactionAt`, `currency`, `amount`, `mId`. 취소는 별도 행이고 **`amount`가 양수 그대로(39000)** 다. 승인과 취소는 `status`로 구분한다.
- **조치**:
  - 웹훅·거래 조회가 필요한 시험은 API 개별 연동 키(또는 계약 뒤 내 상점 위젯 키)로 한다. 계약 전 위젯 키로는 둘 다 시험할 수 없다.
  - 복구는 여전히 이 API가 아니라 paymentKey 조회로 한다(A5-1). 응답이 느리고(7.6초) 기간 단위라 건별 복구에 맞지 않는다.
  - 정산 대사(R4)는 이 API를 쓸 수 있다. 취소 행의 금액 부호가 없으므로 합계는 `status`별로 따로 낸다.

## 6. orderId 규칙

문서: 6~64자, 영문 대소문자·숫자·`-`·`_`·`=`.

| 주문번호 | 결과 |
|---|---|
| `r003-A_confirm-dup=01`(`_`, `=` 포함) | 정상 결제 |
| `r003-B-…`(64자) | 정상 결제 |
| `abcde`(5자) | 거절 |
| `r003-G-…`(65자) | 거절 |
| `r003.G3`(`.`) | 거절 |
| `r003@G4`(`@`) | 거절 |

- 거절은 모두 `requestPayment()`가 바로(약 0.2초) 던지는 오류였다. 결제창이 열리지 않고 토스 서버에 결제 기록도 남지 않는다. 코드 `INVALID_PARAMETERS`, 메시지 "`orderId`는 영문 대소문자, 숫자, 특수문자(-, _, =)만 허용합니다. 6자 이상 64자 이하여야 합니다."
- **조치**: 결제 시도 ID(토스 orderId)는 이 규칙 안에서 서버가 만든다. A1 규약(추측할 수 없는 무작위 값, UUIDv7 금지)도 지켜야 한다. 예를 들어 UUIDv4(36자, 16진수와 `-`)는 두 규칙을 모두 만족한다. 형식은 ADR-010에서 확정한다.
- 같은 orderId로 결제창을 닫고(`USER_CANCEL`) 다시 열 수 있었다. C는 세 번 닫은 뒤 네 번째에 인증했다. 결제창을 닫아도 주문을 새로 만들 필요가 없다.

## 7. 결제수단별 응답과 화면

**간편결제(카카오페이)**, 1회차 6건 모두:
- `method` "간편결제", `easyPay` `{provider: "카카오페이", amount, discountAmount}`, `card` null.
- 승인 전 조회(`IN_PROGRESS`)에서는 `method`·`easyPay`가 null이다. 결제수단은 승인 뒤에야 알 수 있다.
- 금액 필드: `totalAmount` 39000, `balanceAmount` 39000, `suppliedAmount` 35455, `vat` 3545, `taxFreeAmount` 0. 공급가액과 부가세를 토스가 나눠 준다(39000 / 1.1의 반올림).
- 그 밖에 `version` "2022-11-16", `country` "KR", `currency` "KRW", `type` "NORMAL", `receipt.url`, `checkout.url`, `secret`이 온다.

**카드**, 2회차 3건(H 위젯, W2·I 결제창). 모두 실제 체크카드로 결제했다:
- `method` "카드", `easyPay` null, `card` 객체:

| 필드 | 값 | 비고 |
|---|---|---|
| `number` | `99999999****999*` 모양 | 가운데와 끝을 가린 카드번호. 그래도 공개 저장소에는 두지 않는다 |
| `approveNo` | `00000000` | 카드사 승인번호 자리. 테스트에서는 3건 모두 0이었다 |
| `issuerCode`·`acquirerCode` | 2자리 코드 | 발급사·매입사 |
| `cardType`·`ownerType` | "체크"·"개인" | |
| `installmentPlanMonths`·`isInterestFree`·`interestPayer` | 0·false·null | 일시불 |
| `useCardPoint` | false | |
| `acquireStatus` | "READY" | **취소 응답에서도 READY**였다. 매입 상태는 취소와 따로 움직인다 |
| `amount` | 39000 | |

- 취소 응답의 `cancels[0]`은 간편결제와 같은 모양이다(`cancelAmount`, `cancelStatus` DONE, `canceledAt`, `refundableAmount` 0, 할인 금액 필드들).
- 응답 시간: H 승인 2,367ms·취소 862ms, W2 승인 1,252ms·취소 1,342ms, I 승인 918ms. 간편결제(596~749ms)보다 느리고 들쭉날쭉하다. 승인 호출의 읽기 타임아웃은 이보다 넉넉히 잡는다(값은 ADR-006a).
- 테스트 키라 실제 출금과 카드 앱 승인 알림은 없었다. 다만 카드사 인터넷 결제 비밀번호 등록 단계는 실제처럼 진행되었다. 카드번호 입력 중 뜬 "유출된 비밀번호" 경고는 크롬 비밀번호 관리자의 것이고 이 사이트나 토스와는 관계없다.

**결제창(API 개별 연동 키)과 결제위젯의 차이**
- 성공 URL의 `paymentType`: 위젯은 `NORMAL`, **결제창은 값이 없었다**(W2·I 모두). **조치**: 승인 판단에 `paymentType`을 쓰지 않는다.
- 응답의 `version`: 위젯 키(공용 상점)는 "2022-11-16", API 키(내 상점)는 "2024-06-01"이었다. 버전은 상점 설정을 따르는 것으로 보인다. 이번에 받은 카드 승인·취소 응답은 두 버전의 필드 이름이 같았다. **조치**: 쓰는 필드만 읽고 모르는 필드는 무시한다. 응답의 `version`을 기록해 두면 상점 설정이 바뀌었을 때 알아챌 수 있다.

**아직 확인하지 못한 것**
- 결제수단별로 승인 전 고객 화면이 어떻게 보이는지. 관찰 요청이 늦어 1·2회차 모두 기록하지 못했다. 화면 설계(C절) 때 다시 본다.

## 8. 웹훅 (2회차)

**등록**: 개발자센터 → 웹훅 → 등록. URL(ngrok 고정 주소 + `/webhooks/toss`, POST만 받는다)과 이벤트 `PAYMENT_STATUS_CHANGED`를 골랐다. 내 테스트 상점에만 등록되므로 계약 전 위젯 키 결제는 웹훅이 오지 않는다(§5). 그래서 웹훅 시험은 결제창(API 개별 연동 키)으로 했다.

**받은 것**(연결 시험용 수동 요청은 뺐다)

| 주문 | `data.status` | 언제 | 비고 |
|---|---|---|---|
| W | `EXPIRED` | 결제창을 연 시각(`requestedAt` 10:01:51) 32분 42초 뒤 | 인증하지 않은 결제도 만료되고 웹훅이 온다. `failure.code` `EXPIRED_PAYMENT`, `secret` null |
| W2 | `DONE` | 승인 응답을 받고 약 6초 뒤 | |
| W2 | `CANCELED` | 취소 응답을 받고 약 3초 뒤 | `cancels[]` 포함 |
| I | `DONE` | 승인 응답을 받고 약 3초 뒤 | 500으로 답함 → 재전송 |

- 이번에는 웹훅이 항상 API 응답보다 늦게 왔다. 그래도 먼저 오는 경우를 막을 근거는 없으므로 순서에 기대지 않는다.

**본문**: `{createdAt, eventType, data}`. `data`는 결제 조회 응답과 같은 결제 객체 전체다(`version` "2024-06-01").
- `createdAt`은 시간대 표시가 없는 한국 시각(나노초까지)이고, **재전송해도 바뀌지 않는다**.
- `data.secret`은 같은 결제의 승인 응답 `secret`과 **같았다**(W2·I의 DONE·CANCELED 모두). 만료(W)는 승인된 적이 없어 null이다. `paymentKey`·`lastTransactionKey`도 API 응답과 같았다.

**헤더**
- `User-Agent: tosspayments`
- `Tosspayments-Webhook-Transmission-Id`: `whtrans_`로 시작. **재전송마다 새 값**이다.
- `Tosspayments-Webhook-Transmission-Retried-Count`: 0, 1, 2, 3으로 늘었다.
- `Tosspayments-Webhook-Transmission-Time`: `+09:00`이 붙은 초 단위 시각.
- `Tosspayments-Webhook-Signature`: `v1:`로 시작하는 Base64 값. **첫 전송에만 있고 재전송에는 없었다.**
- 그 밖에 추적 헤더(`traceparent`, `X-B3-*`)가 온다.

**재전송**(우리가 500으로 답했을 때, 시각은 `Transmission-Time` 기준)

| 회차 | W2 `CANCELED` | I `DONE` | 우리 응답 |
|---|---|---|---|
| 0(첫 전송) | 11:53:28 | 11:53:55 | 500 |
| 1 | 11:54:33(+65초) | 11:54:34(+39초) | 500 |
| 2 | 11:58:24(+3분 51초) | 11:58:24(+3분 50초) | 500 |
| 3 | 12:14:24(+16분 0초) | 12:14:24(+16분 0초) | 200 |

- 간격이 약 1분 → 4분 → 16분으로 4배씩 늘었다. 두 주문의 재전송이 같은 초에 왔으므로 토스가 주기적으로 모아서 보내는 것으로 보인다. 그래서 첫 간격이 정확히 1분이 아니다.
- 200으로 답한 뒤 더 오지 않는지는 확인하지 못했다. 다음 재전송 예정 시각(약 64분 뒤) 전에 메모리 부족으로 ngrok이 꺼졌다. 최대 재전송 횟수도 보지 못했다.

**조치**
- 웹훅은 "이 결제를 다시 조회하라"는 신호로만 쓴다. 상태는 paymentKey 조회로 확정한다(이슈 #5 원칙).
- 중복 제거 키는 `paymentKey` + `data.status` + `createdAt`(또는 `lastTransactionKey`)로 한다. **전송 ID는 재전송마다 바뀌므로 쓰지 않는다.**
- **서명 헤더를 필수 조건으로 두지 않는다.** 그러면 재전송을 모두 버리게 된다. 위조 방지는 조회 확정으로 하고, 보조로 `secret`을 승인 때 저장한 값과 대조할 수 있다(만료처럼 null인 경우가 있다).
- 받으면 저장만 하고 바로 200으로 답한다. 처리는 뒤에서 한다. 처리 실패로 500을 주면 다음 기회가 1·4·16분으로 늦어지므로, 놓친 건의 복구는 웹훅 재전송이 아니라 우리 복구 작업자의 조회가 맡는다.
- 만료 웹훅이 오지만, 결제 시도의 만료는 §2 조치대로 우리 시계로 판단한다. 웹훅은 그 판단을 앞당기는 신호로만 쓴다.

## 9. 모바일 결제창 취소 (2회차)

- 기기: Android 15. 주소를 **카카오톡 안에서 열어** 카카오톡 인앱 브라우저로 진행했다. 결제위젯(공용 상점 키)이다.
- **J(결제창 닫기)**: 결제하기를 누른 뒤(11:56:16) 결제창을 닫았다. 우리 페이지에는 **`USER_CANCEL` 오류도 실패 URL 도착도 기록되지 않았다.** PC에서는 닫으면 `requestPayment()`가 `USER_CANCEL`을 던졌다(§6의 C). 휴대폰에 뜬 문구는 기록하지 못했다. 성공 URL이 오지 않아 paymentKey가 없으므로 토스 쪽 상태도 조회할 수 없었다.
- **K(카카오페이)**: 결제하기(11:56:53) → 카카오페이 앱 → 카카오톡 브라우저로 돌아와 성공 URL 도착(11:57:05, 12초), `paymentType` `NORMAL`. 승인 200 `DONE`(580ms). 앱을 오가도 결제 흐름이 끊기지 않았다. "결제 인증 완료" 화면이 보였는지는 기록하지 못했고, 서버 기록으로만 확인했다.
- **조치**:
  - 모바일에서는 결제창을 닫아도 서버와 프런트가 모두 모를 수 있다. 결제 시도는 우리 만료 시간으로 닫는다(§2 조치).
  - 결제 화면으로 돌아오면 "결제가 끝나지 않음" 상태를 보여 주고 다시 시도할 수 있게 한다. 같은 orderId로 다시 열 수 있다(§6).
- **확인하지 못한 것**: 크롬·삼성 인터넷 같은 일반 브라우저, iOS, 모바일 카드 결제.

### 10-2. 제18조(청약철회등의 효과) ②와 지연배상금

- 원문 발췌: "다음 각 호의 어느 하나에 해당하는 날부터 **3영업일 이내**에 이미 지급받은 재화등의 대금을 환급하여야 한다. 이 경우 … 환급을 지연한 때에는 그 지연기간에 대하여 … 대통령령으로 정하는 이율을 곱하여 산정한 지연이자(이하 "지연배상금"이라 한다)를 지급하여야 한다."
- 기산일(각 호): 재화를 공급한 경우 **재화를 반환받은 날**, 용역·디지털콘텐츠는 청약철회등을 한 날, 공급하지 않은 경우 청약철회등을 한 날.
- 이율: 시행령 제21조의3 "**연 100분의 15**".
- ③: 신용카드 등으로 결제한 경우 지체 없이 결제업자에게 대금 청구의 정지·취소를 요청한다(우리 구조에서는 PG 취소 API 호출).
- **조치**: 환급 기한 = 재화를 반환받은 날(회수 도착일. 검수 완료일이 아니다)부터 3영업일(A5-6, 단위 테스트로 고정). 기한을 넘기면 지연배상금 = 환급액 × 15% × 지연일수 / 365(원 단위 계산 규칙은 B6에서 정한다). 출고 전 취소는 "공급하지 아니한 경우"라 취소한 날이 기산일이다.
