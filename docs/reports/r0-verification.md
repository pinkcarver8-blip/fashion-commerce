## 1. 결제 조회 (paymentKey)

`GET /v1/payments/{paymentKey}`.

| 상황 | 실제 응답 | 조치 |
|---|---|---|
| 없는 paymentKey | 404 `NOT_FOUND_PAYMENT` "존재하지 않는 결제 정보 입니다." | 우리 기록과 PG가 어긋난 것. 자동 처리하지 않고 운영자 큐로 보낸다 |
| 인증 직후, 승인 전 | 200 `IN_PROGRESS`, `method`·`approvedAt` = null | 승인을 진행한다(10분 안) |
| 승인 후 | 200 `DONE`, 승인 응답과 같은 본문 | 결제 완료로 확정한다 |
| 취소 후 | 200 `CANCELED`, `cancels[]`에 취소 내역, `balanceAmount` 0 | 취소 완료로 확정한다 |
| 우리 쪽 타임아웃 | 응답 없음(`SocketTimeoutException`) | 같은 멱등키로 재시도 또는 조회(§3 E) |
| 만료 | §2 참조 | |

- `requestedAt`은 인증 완료 시각이 아니라 **결제창을 연 시각**이다. C는 결제하기를 누른 13:44:56(이 PC 시계)에 대해 `requestedAt`이 13:44:59였다. 3초 차이는 시계 차이다.
- `ABORTED`는 이번에 나오지 않았다. 승인 실패를 일부러 만들 방법이 테스트 환경에 없었다.
- 응답 시간: 조회는 105~254ms, 승인은 596~749ms, 취소는 651ms였다.

## 2. 결제 유효 시간 30분과 승인 10분 제한

문서: 인증 후 10분 안에 승인해야 한다. `IN_PROGRESS`에서 30분 동안 승인하지 않으면 `EXPIRED`가 된다.

| 주문 | 경과 | 실제 |
|---|---|---|
| D | 인증(13:46:13) 10분 31초 뒤 승인 | 400 `EXPIRED_PAYMENT` "결제가 만료되었습니다. 다시 시도해주세요." 바로 조회하니 200 **`ABORTED`**, `failure.code` `EXPIRED_PAYMENT` |
| C | 인증(13:45:26) 뒤 승인하지 않고 1분마다 조회 | 10분, 20분, 30분이 지나도 `IN_PROGRESS`. 14:16:42(토스 시각)에 **`EXPIRED`**, `failure` null |

- **10분 제한은 상태를 바꾸지 않는다.** C는 10분이 지나도 `IN_PROGRESS`였다. D는 10분 뒤 승인을 시도한 순간 `ABORTED`가 되었다(그 사이 D는 조회하지 않았으므로 정확한 전환 시점은 승인 시도 이전 어딘가다. C와 비교하면 승인 시도가 계기로 보인다).
- 늦은 승인은 `EXPIRED`가 아니라 **`ABORTED` + `EXPIRED_PAYMENT`** 로 끝난다. 문서의 `EXPIRED`만 보고 만료를 판정하면 놓친다.
- **조치**:
  - 승인은 성공 URL이 도착하면 바로 서버에서 한다.
  - 조회 결과 `ABORTED`·`EXPIRED`는 모두 "승인되지 않음, 돈이 나가지 않음"으로 보고 결제 시도를 실패로 닫고 재고 예약을 푼다. 원인은 `failure.code`로 구분해 기록한다.
  - 복구 작업자가 `IN_PROGRESS`를 만나면 같은 멱등키로 승인을 불러도 안전하다. 10분 안이면 승인되고, 지났으면 `EXPIRED_PAYMENT`로 실패가 확정된다. 기다리지 않고 결과를 정할 수 있다.

**C의 만료 시점**(모두 토스 `Date` 헤더 기준. 이 PC 시계보다 약 3초 빠르다)

| 기준 | 시각 | 마지막 `IN_PROGRESS`(14:15:41)까지 | 첫 `EXPIRED`(14:16:42)까지 |
|---|---|---|---|
| `requestedAt`(마지막으로 결제창을 연 시각) | 13:44:59 | 30분 42초 | 31분 43초 |
| 인증 완료(성공 URL 도착) | 약 13:45:29 | 30분 12초 | 31분 13초 |

- 1분 간격으로 조회해서 두 기준 중 어느 쪽인지는 가를 수 없었다. 어느 기준이든 **30분이 지난 뒤 1분쯤 안에** `EXPIRED`로 바뀌었다. 정각에 바뀌지 않으므로 토스 쪽에서 주기적으로 처리하는 것으로 보인다.
- `EXPIRED`는 `failure`가 null이다. 10분 뒤 승인 시도로 생긴 `ABORTED`는 `failure.code`가 `EXPIRED_PAYMENT`였다.
- **조치**: 우리 결제 시도의 만료(재고 예약 해제)는 토스 상태 전환을 기다리지 않고 우리 시계로 판단한다. 판단 전에 paymentKey로 조회해 `DONE`이 아님을 확인한다. 주문 만료 시간을 30분보다 짧게 잡으면 토스에서는 아직 승인할 수 있는 결제가 우리 쪽에서 먼저 만료될 수 있다. 그래서 만료 처리 직전 조회는 빼지 않는다. 시간 값은 B5·ADR에서 정한다.

## 3. 멱등키

헤더 `Idempotency-Key`. 문서: 최대 300자, 15일간 유효, 같은 키로 다시 요청하면 처음 응답을 돌려준다.

| 시나리오 | 실제 응답 | 조치 |
|---|---|---|
| A. 승인 완료 뒤 같은 키로 재승인 | 200 `DONE`, 첫 응답과 같은 본문. 37ms(첫 요청은 616ms) | 재시도는 같은 키로 한다. 저장된 응답을 받으므로 안전하다 |
| A. 승인 완료 뒤 다른 키로 재승인 | 400 `ALREADY_PROCESSED_PAYMENT` "이미 처리된 결제 입니다." | 새 키로 재시도하면 성공 응답을 못 받는다. 이 코드는 "결과 불명"으로 보고 조회로 확정한다 |
| B. 같은 키로 2건 동시 승인 | 하나는 409 `IDEMPOTENT_REQUEST_PROCESSING` "이전 멱등 요청이 처리중입니다."(69ms), 하나는 200 `DONE` | 409는 실패가 아니다. 잠시 뒤 같은 키로 재시도하거나 조회한다 |
| E. 우리 쪽 읽기 타임아웃(1ms) | 응답 없음. 바로 조회하니 `IN_PROGRESS`, 4초 뒤에도 `IN_PROGRESS`. 같은 키로 재승인하니 200 `DONE`(629ms) | 타임아웃은 "결과 불명"이다. 같은 키로 재시도하면 이중 승인 없이 확정된다 |
| F. 틀린 금액(100원)으로 승인 | 403 `FORBIDDEN_REQUEST` "허용되지 않은 요청입니다." 결제는 `IN_PROGRESS` 그대로 | 금액 불일치 전용 코드가 없다. 403은 우리 요청이 틀린 것이므로 재시도하지 않는다 |
| F. 같은 키로 맞는 금액 재승인 | **403 `FORBIDDEN_REQUEST` 그대로**(51ms). 실패 응답도 저장되어 같은 키로는 본문을 고쳐도 같은 응답이 온다 | 같은 키는 같은 요청에만 쓴다. 키는 요청 내용(주문·금액)이 정해진 뒤 만든다 |
| F. 새 키로 맞는 금액 | 200 `DONE` | 금액은 서버에 저장한 값만 쓰므로 이 경로는 우리 버그가 아니면 생기지 않는다 |

- E에서 1ms 요청이 토스에 닿았는지는 구분할 수 없다. 닿았더라도 처리가 끝나지 않았고, 같은 키 재요청이 정상 처리되었다(37ms 저장 응답이 아니라 629ms 실제 처리).
- **설계 확인**: "승인·취소 재시도에 새 멱등키를 쓰지 않는다"(A5-1)가 맞다. A의 다른 키는 400, F의 같은 키는 저장된 실패를 돌려주므로, 키는 `confirm-{주문ID}`처럼 요청 하나에 하나로 고정한다.

| 상황 | 실제 응답 | 조치 |
|---|---|---|
| 정상 취소 | 200 `CANCELED`. `cancels[0]`에 `cancelAmount` 39000, `cancelStatus` `DONE`, `canceledAt`, `transactionKey`. `balanceAmount`·`suppliedAmount`·`vat` 0 | 환급 완료 시각은 `canceledAt`을 쓴다 |

## 5. 거래 조회 API (위젯 키)

`GET /v1/transactions?startDate&endDate`.

- 결제위젯 시크릿 키로 호출할 수 있었다(200). 날짜는 `yyyy-MM-dd'T'HH:mm:ss`이다.
- 그러나 **결과가 0건**이었다. 기간은 2026-11-17~18로 잡았다. 11-18 11:11(그때까지 승인 2건)과 13:54(승인 6건, 취소 1건) 두 번 모두 빈 배열이었다.
- 원인은 확인하지 못했다. 테스트 환경에서 반영이 늦거나, 테스트 결제가 이 API에 나오지 않을 수 있다.
- **조치**: 복구와 대사를 이 API에 기대지 않는다. 복구는 paymentKey 조회로 한다(A5-1). 정산 대사(R4)를 설계할 때 다시 호출해 보고, 그때도 0건이면 스텁 데이터로만 시험한다.

## 6. orderId 규칙

문서: 6~64자, 영문 대소문자·숫자·`-`·`_`·`=`.

| 주문번호 | 결과 |
|---|---|
| `r003-A_confirm-dup=01`(`_`, `=` 포함) | 정상 결제 |
| `r003-B-…`(64자) | 정상 결제 |
| `abcde`(5자) | 거절 |
| `r003-G-…`(65자) | 거절 |
| `r003.G3`(`.`) | 거절 |
| `r003@G4`(`@`) | 거절 |

- 거절은 모두 `requestPayment()`가 바로(약 0.2초) 던지는 오류였다. 결제창이 열리지 않고 토스 서버에 결제 기록도 남지 않는다. 코드 `INVALID_PARAMETERS`, 메시지 "`orderId`는 영문 대소문자, 숫자, 특수문자(-, _, =)만 허용합니다. 6자 이상 64자 이하여야 합니다."
- **조치**: 결제 시도 ID(토스 orderId)는 이 규칙 안에서 서버가 만든다. A1 규약(추측할 수 없는 무작위 값, UUIDv7 금지)도 지켜야 한다. 예를 들어 UUIDv4(36자, 16진수와 `-`)는 두 규칙을 모두 만족한다. 형식은 ADR-010에서 확정한다.
- 같은 orderId로 결제창을 닫고(`USER_CANCEL`) 다시 열 수 있었다. C는 세 번 닫은 뒤 네 번째에 인증했다. 결제창을 닫아도 주문을 새로 만들 필요가 없다.

## 7. 결제수단별 응답과 화면

**간편결제(카카오페이)**, 1회차 6건 모두:
- `method` "간편결제", `easyPay` `{provider: "카카오페이", amount, discountAmount}`, `card` null.
- 승인 전 조회(`IN_PROGRESS`)에서는 `method`·`easyPay`가 null이다. 결제수단은 승인 뒤에야 알 수 있다.
- 금액 필드: `totalAmount` 39000, `balanceAmount` 39000, `suppliedAmount` 35455, `vat` 3545, `taxFreeAmount` 0. 공급가액과 부가세를 토스가 나눠 준다(39000 / 1.1의 반올림).
- 그 밖에 `version` "2022-11-16", `country` "KR", `currency` "KRW", `type` "NORMAL", `receipt.url`, `checkout.url`, `secret`이 온다.

**아직 확인하지 못한 것(2회차)**
- 카드 결제의 응답(`card` 객체)과 승인 전 화면. 1회차에서 카드로 결제한 건이 없었다.
- 결제수단별로 승인 전 고객 화면이 어떻게 보이는지. 1회차에는 관찰 요청이 늦어 기록하지 못했다.

| ② 제한 | 소비자 책임으로 멸실·훼손(내용 확인을 위한 포장 훼손은 제외), 사용·일부 소비로 가치가 현저히 감소, 시간이 지나 재판매가 곤란할 정도로 가치 감소, 복제 가능한 재화의 포장 훼손, 용역·디지털콘텐츠 제공 개시, 대통령령으로 정하는 경우(주문 제작 + 사전 고지 + 서면 동의, 시행령 제21조) | 의류는 "착용·세탁 등으로 가치가 현저히 감소"(2호)가 주된 거절 사유. **단, ⑥의 표시 조치를 하지 않으면 2~5호로 거절할 수 없다** |
| ③ 표시·광고와 다른 경우 | "재화등을 공급받은 날부터 3개월 이내, 그 사실을 안 날 또는 알 수 있었던 날부터 30일 이내" | 오배송·하자 반품은 7일 기한과 별도 기한으로 받는다 |
| ④ 서면 철회의 효력 | 서면을 발송한 날에 효력 발생 | 반품 신청 시각을 기록한다 |
| ⑤ 증명 책임 | 훼손 책임, 계약 체결·공급 사실과 시기에 다툼이 있으면 **통신판매업자가 증명** | 배송 완료 시각, 검수 결과(사진·메모)를 남긴다 |
| ⑥ 표시 의무 | 청약철회가 불가능한 재화는 그 사실을 포장 등 쉽게 알 수 있는 곳에 명확히 표시 | 상품 상세에 반품 제한 안내를 둔다 |

### 10-2. 제18조(청약철회등의 효과) ②와 지연배상금

- 원문 발췌: "다음 각 호의 어느 하나에 해당하는 날부터 **3영업일 이내**에 이미 지급받은 재화등의 대금을 환급하여야 한다. 이 경우 … 환급을 지연한 때에는 그 지연기간에 대하여 … 대통령령으로 정하는 이율을 곱하여 산정한 지연이자(이하 "지연배상금"이라 한다)를 지급하여야 한다."
- 기산일(각 호): 재화를 공급한 경우 **재화를 반환받은 날**, 용역·디지털콘텐츠는 청약철회등을 한 날, 공급하지 않은 경우 청약철회등을 한 날.
- 이율: 시행령 제21조의3 "**연 100분의 15**".
- ③: 신용카드 등으로 결제한 경우 지체 없이 결제업자에게 대금 청구의 정지·취소를 요청한다(우리 구조에서는 PG 취소 API 호출).
- **조치**: 환급 기한 = 재화를 반환받은 날(회수 도착일. 검수 완료일이 아니다)부터 3영업일(A5-6, 단위 테스트로 고정). 기한을 넘기면 지연배상금 = 환급액 × 15% × 지연일수 / 365(원 단위 계산 규칙은 B6에서 정한다). 출고 전 취소는 "공급하지 아니한 경우"라 취소한 날이 기산일이다.
