# ADR-009. 프론트 구조: 두 앱, 공유 패키지, 스타일 방식

- **상태**: 제안
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-009(이슈 #35), E44, A5-9 S4·S5, 기획서 §9-2, 작업진행.md A1·A2·A8·C·E3("프론트 구조" 행)·E4-1("스타일 방식"), ADR-008·ADR-010

## 맥락
- 스택은 정해져 있다(A1): React 19, TypeScript, Vite, TanStack Query, React Router, Vitest·RTL, Playwright. 저장소 구조도 있다(A2): `store`·`admin` 두 앱과 `packages/ui`·`api-client`·`tokens`, pnpm workspaces. **스타일 방식은 "디자인 확정 뒤 재검토"로 열려 있다**(E4-1).
- 이 ADR이 정할 것: 패키지 사이의 import 규칙, 상태 관리, API 클라이언트와 토큰 처리(ADR-008), 빌드·배포 형태, 그리고 디자인이 나오기 전까지 쓸 스타일 방식이다. R0-07(빈 앱 골격) 전에 정해야 한다.

## 결정
**고객 앱과 관리자 앱을 따로 빌드하고, 공유 코드는 `packages/`에만 둔다. 의존은 "앱 → 패키지" 한 방향이고, store는 관리자 코드를 가져올 수 없다. 서버 데이터는 TanStack Query가 맡고 전역 상태 라이브러리는 두지 않는다. 스타일은 디자인 확정 전까지 CSS Modules + `tokens.css` 변수로 한다.**

**1. 패키지와 의존 방향**

| 패키지 | 담는 것 | 누가 쓰나 |
|---|---|---|
| `frontend/store` | 고객 화면, 모바일 우선 | — |
| `frontend/admin` | 관리자 화면, 데스크톱 전용 | — |
| `frontend/packages/ui` | 버튼·입력·모달 같은 공용 컴포넌트. 업무 로직 없음 | store, admin |
| `frontend/packages/api-client` | fetch 래퍼, 토큰 처리, 생성된 API 타입. **진입점을 `/store`와 `/admin`으로 나눈다** | store는 `/store`만, admin은 `/admin`만 |
| `frontend/packages/tokens` | `tokens.css`(A8) | 모두 |

- 금지: store → admin 앱 또는 `api-client/admin`, 패키지 → 앱, `ui` → `api-client`(화면 부품이 서버를 부르지 않는다). ESLint `no-restricted-imports`로 막는다(R0-08).

**2. 상태 관리**
- 서버에서 온 데이터(상품, 장바구니, 주문)는 **TanStack Query**가 캐시하고 갱신한다.
- 화면 안의 상태(열린 모달, 입력 중인 값)는 React 기본 `useState`·Context만 쓴다. Redux·Zustand는 넣지 않는다.
- 결제·재고 확정 화면에는 낙관적 UI(서버 응답 전에 성공으로 보여 주기)를 쓰지 않는다. 결제 결과 화면은 새로고침해도 서버 상태를 다시 읽어 같은 화면을 보여 준다(C1).

**3. API 클라이언트와 토큰**(ADR-008)
- 요청·응답 타입은 백엔드 springdoc의 OpenAPI 문서에서 생성한다(`openapi-typescript`, 개발 의존성). 실제 호출하는 fetch 래퍼는 직접 쓴다. 생성 도구 버전과 실재 여부는 R0-07에서 확인한다(A5-12).
- 액세스 토큰은 api-client 모듈 안의 변수(메모리)에만 둔다. 401을 받으면 리프레시를 한 번 시도하고 원래 요청을 다시 보낸다. 동시에 여러 요청이 401을 받아도 리프레시는 한 번만 한다.
- 금액은 서버가 준 값을 표시만 한다. 화면에서 계산한 금액을 서버에 보내지 않는다.

**4. 빌드·배포**: 두 앱을 각각 정적 파일로 빌드하고 Nginx가 서빙한다. `/api`는 Nginx가 백엔드로 넘겨 같은 출처가 된다(ADR-008의 CORS 미사용). 개발 중에는 Vite 개발 서버의 프록시가 같은 일을 한다. `VITE_` 환경변수에는 공개 값(토스 클라이언트 키)만 넣는다.

**5. 스타일(임시)**: **CSS Modules + `tokens.css`의 CSS 변수.** Vite가 기본으로 지원해 의존성이 늘지 않고, 런타임 비용이 없다. 클래스 이름이 파일별로 격리된다. 색·간격·글꼴은 토큰 변수만 쓴다(A8). **디자인이 확정되면 다시 검토한다**(E4-2의 ● 항목 그대로, 사용자 확인 필요).

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| 한 앱 + 라우트로 고객·관리자 분리(기획서 v0.2 원안) | 빌드가 하나다 | 관리자 코드와 API 경로가 고객 번들에 섞여 내려간다. 번들 크기와 위생이 나빠진다(E3에서 이미 바꿈) |
| Tailwind CSS | 빠르게 만든다. 공고에 자주 나온다 | 디자인 토큰이 아직 임시라 설정을 두 번 만들게 된다. 디자인 확정 때 재검토 후보로 남긴다 |
| CSS-in-JS(styled-components 등) | 컴포넌트와 스타일이 한 파일 | 스타일을 실행 중에 만들어 런타임 비용이 든다. 의존성이 는다 |
| Redux·Zustand | 전역 상태를 한 곳에서 본다 | 서버 데이터는 TanStack Query가 맡아서 남는 전역 상태가 거의 없다(로그인 여부 정도) |
| API 클라이언트 전체를 코드 생성 | 손으로 쓸 코드가 없다 | 토큰 갱신·오류 처리 같은 핵심 로직이 생성 코드에 묻힌다. 타입만 생성하고 래퍼는 직접 쓴다 |
| Turborepo·Nx | 빌드 캐시 | 앱 둘, 패키지 셋에는 과하다(ADR-010, A1) |

## 결과
- **얻는 것**: 고객 번들에 관리자 코드가 들어가지 않는다. 백엔드 API가 바뀌면 타입 생성에서 바로 드러난다. 디자인이 늦어도 토큰 값만 바꾸면 되므로 개발이 막히지 않는다.
- **감수하는 것**: 앱이 둘이라 설정 파일(Vite, ESLint, 테스트)이 두 벌이다(공용 설정 패키지로 줄일 수 있다). 스타일 방식이 임시라 디자인 확정 뒤 바꾸면 스타일 코드를 옮겨야 한다. 토큰을 쓰도록 강제해서 옮기는 범위를 줄인다.

## 보안·개인정보 영향
- **앱 분리는 보안 경계가 아니다**(A5-9). 관리자 앱도 누구나 내려받을 수 있다. 보안은 서버 권한 검사와 토큰 분리(ADR-008)가 맡는다.
- XSS 방어(S5): `dangerouslySetInnerHTML` 금지 린트, 관리자 앱 CSP와 iframe 삽입 금지(헤더는 배포 창).
- 토큰은 메모리에만 두고 localStorage·sessionStorage에 두지 않는다(ADR-008). `VITE_` 변수에 시크릿 키를 넣지 않는다(A5-10).

## 강제
- **예정(R0-08, ESLint)**: 패키지 import 금지 규칙, `dangerouslySetInnerHTML` 금지, localStorage에 토큰 저장 금지(`no-restricted-syntax`로 `localStorage.setItem` 사용 시 경고).
- **예정(R0-08, CI)**: store 빌드 산출물에 `/api/admin` 문자열이 없는지 검사한다.
- **예정(R1-21)**: 원색 값 직접 사용 금지(토큰만). 기계적 검사(stylelint)를 넣을지는 그때 정한다.
