# ADR-008. 인증·인가: 관리자 계정 분리, 토큰 저장, 쿠키·CORS

- **상태**: 승인
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-008(이슈 #33), E36·E43·E46, A5-9 S1~S6·S9·S12, 작업진행.md A5-9·A5-10·B1, ADR-001·ADR-010

## 맥락
- A5-9는 위협과 대응 원칙을 정했다. 기본 거부(S1), 권한 필드 금지(S2), 관리자 계정·토큰 분리(S3), 짧은 액세스 토큰과 리프레시 회전(S4), 로그인 시도 제한(S6), 소유자 검사(S12)다. 구체적인 토큰 종류, 저장 위치, 쿠키 속성, 보안 설정 구조는 이 ADR에 미뤘다.
- ADR-001·004·006a는 "소유자 검사를 어느 계층에서 하나"와 "인증 주체 클래스를 어디에 두나"를 이 ADR에 미뤘다.
- 데모는 스토어와 관리자가 같은 상위 도메인을 쓴다. 그래서 브라우저가 둘을 같은 사이트로 본다(A5-9 남는 한계).

## 결정
**고객과 관리자를 계정 테이블부터 토큰 서명 키, 쿠키, 보안 설정까지 끝까지 분리한다. 액세스 토큰은 짧은 JWT로 메모리에만 두고, 리프레시 토큰은 HttpOnly 쿠키로 두되 DB에서 회전·폐기한다. 소유자 검사는 고객용 유스케이스의 조회 조건에 넣는다.**

**1. 계정과 보안 설정 분리**(S3)
- 고객은 `member` 모듈의 `member` 테이블, 관리자는 `admin` 모듈의 `admin_account` 테이블이다. 관리자 계정은 API로 만들 수 없고 서버 명령(CLI)으로만 만든다(S2, R1-02).
- Spring Security 필터 체인을 둘로 나눈다. `/api/admin/**`는 관리자 토큰만, 나머지 `/api/**`는 고객 토큰만 받는다.
- 기본은 거부다. 공개 경로는 목록으로만 연다(S1): 상품 조회 GET, 가입·로그인·토큰 갱신, 결제 웹훅 `POST /api/webhooks/toss`(ADR-006b). 웹훅은 `/api/**` 고객 체인 안의 공개 경로이고 토큰을 받지 않는다. actuator·Swagger는 공개 경로에 두지 않는다(S9).

**2. 액세스 토큰**
- JWT(HS256)다. 고객용과 관리자용 서명 키를 따로 두고(환경변수, 256비트 이상, A5-10), 토큰에 용도(`aud`: store / admin)를 넣는다. 각 필터 체인은 자기 키와 용도만 받는다.
- 수명: **고객 15분, 관리자 5분**. 프론트는 메모리(자바스크립트 변수)에만 두고 `Authorization` 헤더로 보낸다. localStorage에는 두지 않는다.

**3. 리프레시 토큰**(S4, E36)
- 32바이트 무작위 값이다. DB에는 해시(SHA-256)만 저장한다. DB가 유출돼도 토큰을 쓸 수 없게 하기 위해서다.
- 쿠키는 `HttpOnly; Secure; SameSite=Strict`다. 이름과 경로를 나눈다: 고객 `store_rt` + `/api/auth`, 관리자 `admin_rt` + `/api/admin/auth`.
- 갱신 요청에는 커스텀 헤더(`X-Requested-With`)를 요구한다. 다른 사이트의 폼 전송은 이 헤더를 붙일 수 없다.
- **쓸 때마다 새 토큰으로 바꾼다(회전).** 이미 바꾼 옛 토큰이 다시 오면 탈취로 보고 그 로그인 계열의 토큰을 모두 폐기한다. 로그아웃과 비밀번호 변경도 폐기한다.
- **여러 탭 동시 갱신은 탭끼리 줄을 세워 푼다(봐주기 없음, 2026-11-24 사용자 결정)**: 쿠키는 같은 브라우저의 모든 탭이 함께 쓴다. 탭 두 개가 동시에 갱신하면 한쪽이 방금 바뀐 옛 토큰을 보내 탈취로 오인된다. 그래서 프론트가 브라우저의 Web Locks 기능으로 "한 번에 한 탭만 갱신"하게 하고, 기다린 탭은 이미 바뀐 새 쿠키로 갱신한다. 서버는 옛 토큰 재사용을 예외 없이 탈취로 처리한다. 이 기능이 없는 브라우저에서는 탭 두 개일 때 로그아웃될 수 있다(안전한 쪽으로 실패). 지원 범위는 미확인, R1-01에서 확인(작업진행.md E4-2).
- 수명: **고객 14일, 관리자 8시간**(하루 근무 단위).

**4. CORS**: 프론트와 API를 같은 출처로 둔다. 개발은 Vite 프록시, 배포는 Nginx가 `/api`를 백엔드로 넘긴다. 그래서 CORS를 기본적으로 열지 않는다. 다른 출처가 꼭 필요해지면 경로별로 정확한 출처만 허용하고 와일드카드는 쓰지 않는다(S4).

**5. 소유자 검사 위치**(S12, E46, ADR-001·004·006a가 미룬 것)
- 고객 요청을 받는 각 모듈의 유스케이스(서비스 계층)에서 한다. 조회 조건에 소유자를 넣는다. 예: "외부 주문번호 = ? **그리고** 회원 ID = ?".
- **데이터를 가진 모듈이 소유자 조건부 조회를 공개 API로 내놓는다.** 주문은 order가 가지므로 order 공개 API에 "주문번호 + 회원 ID로 찾기(잠금 포함·미포함)"를 두고, 주문을 다루는 고객 유스케이스(payment의 성공 URL, claim의 고객 취소, shipping의 배송 조회)는 이것만 쓴다. 관리자 유스케이스(admin 모듈)는 소유자 조건이 없는 조회를 쓴다.
- 남의 주문이면 403이 아니라 **404**로 답한다. 그 주문이 있다는 사실도 알려 주지 않기 위해서다.
- B1은 `member`가 "본인 데이터 접근 검사"를 한다고 적었다. 이 결정은 검사를 각 데이터 소유 모듈로 옮긴다. `member`는 로그인한 회원 ID를 알려 주는 일만 한다.

**6. 인증 주체**: 고객·관리자 주체 클래스(ID와 용도만)는 공통 패키지 하나에 둔다. 모듈들은 이 패키지에만 의존한다. 패키지 이름은 R0-06에서 정한다.

**7. 비밀번호와 로그인 제한**: Spring Security 기본 인코더(위임 방식)를 쓴다. 기본 해시가 bcrypt라는 것은 Spring Security 7(Boot 4.1)에서 아직 확인하지 않았다(미확인, R1-01에서 확인. 작업진행.md E4-2). 해시 방식을 나중에 바꿔도 기존 비밀번호가 동작한다. 로그인 실패는 **계정 + 접속 IP 조합**으로 Redis에 센다. 접속 IP는 우리 Nginx가 넣은 값만 믿는다(Spring의 신뢰 프록시 설정. 요청자가 보낸 `X-Forwarded-For`를 그대로 쓰면 IP를 바꿔 가며 제한을 피할 수 있다). 고객도 그 조합이 5회 실패하면 15분 막고(2026-11-24 사용자 결정, 보안 우선), 관리자는 그 조합이 5회 실패하면 그 조합만 15분 막는다(S6). 계정 전체를 잠그지 않는 이유: 남이 일부러 다섯 번 틀려 진짜 관리자를 못 들어오게 만들 수 있다. 여러 IP에서 한 계정을 노리는 시도는 계정별 실패 수 경고 로그로 드러내고, 대응(TOTP 등)은 S11에서 한다. 실패 메시지는 "아이디 또는 비밀번호가 맞지 않습니다" 하나로 통일한다.

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| 서버 세션 + 세션 쿠키 | 구현이 단순하고 즉시 폐기된다 | 같은 상위 도메인에서는 SameSite가 스토어발 요청을 막지 못한다(A5-9 한계). 헤더 토큰은 다른 사이트에서 자동으로 붙지 않아 CSRF에 더 강하다 |
| 액세스 토큰을 localStorage에 | 새로고침해도 남는다 | XSS 한 번에 바로 탈취된다. 메모리 + 리프레시 쿠키로 새로고침을 해결한다 |
| RS256(공개키 서명) | 다른 서비스가 공개키로만 검증한다 | 검증하는 곳이 이 앱 하나다. 키 관리만 늘어난다 |
| 계정 테이블 하나 + 역할 칼럼 | 테이블이 하나다 | 역할 칼럼 하나가 바뀌면 고객이 관리자가 된다(S2). 관리자 도메인 분리(A5-9 실제 운영 방안)로 옮기기 어렵다 |
| 남의 주문에 403 | 의미가 정확하다 | 주문번호가 존재한다는 사실이 새어 나간다. 열거 공격의 단서가 된다(S12) |

## 결과
- **얻는 것**: 고객 토큰으로는 관리자 API에 들어갈 길이 구조적으로 없다(키·용도·필터 체인이 다르다). 토큰이 탈취돼도 피해 시간이 짧고, 재사용을 감지해 폐기한다. 소유자 검사가 조회 조건에 들어가 빠뜨리기 어렵다.
- **감수하는 것**: 액세스 토큰 갱신 흐름(만료 → 리프레시 → 재시도)을 프론트가 구현해야 한다. 리프레시 토큰 테이블과 회전 로직이 필요하다. JWT는 수명 안에서는 폐기할 수 없어서, 액세스 토큰 수명이 곧 최대 노출 시간이다(관리자 5분).

## 보안·개인정보 영향
- 이 ADR 자체가 보안 결정이다. 남는 한계는 A5-9 그대로다. 관리자 앱에 XSS가 생기면 메모리 토큰도 탈취될 수 있고(CSP·원시 HTML 금지로 확률을 낮춘다), 같은 상위 도메인이라 SameSite 보호가 스토어와 관리자 사이에서는 작동하지 않는다(헤더 토큰으로 보완).
- 리프레시 토큰은 해시로만 저장하고, 비밀번호는 위임 인코더의 해시, 토큰 서명 키는 환경변수에만 둔다(A5-10). 로그에 토큰과 비밀번호를 남기지 않는다.
- 로컬 개발의 `Secure` 쿠키는 브라우저의 localhost 예외에 기댄다(미확인, R1-01에서 확인. E4-2). 동작하지 않으면 개발 프로필에서만 끄고, 그 설정이 운영 프로필에 들어가지 않는지 테스트한다.
- 갱신 응답을 받기 직전에 연결이 끊기면, 브라우저에는 옛 토큰이 남아 다음 갱신 때 탈취로 처리돼 로그아웃된다. 드물고 안전한 쪽으로 실패하므로 받아들인다.

## 강제
- **예정(R1-03)**: 엔드포인트 자동 점검 테스트(공개 목록 밖은 비로그인 401, 고객 → 관리자 API 403, 관리자 토큰 → 고객 API 401). 새 API도 자동 포함된다(S1).
- **예정(R1-01·R1-02)**: 리프레시 회전·재사용 폐기 테스트(E36). 옛 리프레시 토큰을 다시 쓰면 시간과 상관없이 계열 전체가 폐기된다. 프론트 테스트: 두 탭이 동시에 401을 받아도 갱신 요청은 차례로 한 번씩만 나간다(Web Locks). 로그인 시도 제한 테스트(S6): 계정 + IP 조합이 5회 실패하면(관리자·고객 모두) 그 조합만 막히고 다른 IP에서는 로그인된다.
- **예정(R1, 주문·결제·배송 API마다)**: 다른 회원 → 404 테스트(S12, E46). PR 템플릿 확인 목록이 이미 요구한다.
- **예정(R0-06, ArchUnit)**: 관리자 컨트롤러는 admin 모듈과 `/api/admin` 경로에만 있다(ADR-001).

## 재검토 조건
- 배포 창(T1): 관리자 도메인 분리, IP 제한, TOTP(S10·S11)를 판단할 때.
- 액세스 토큰 갱신 실패가 사용자 경험 문제로 드러날 때: 고객 수명을 다시 본다.

## 실제 운영과의 차이
- 실제 운영이라면 관리자는 별도 등록 도메인, 사내 SSO와 필수 MFA, 네트워크 접근 제한 뒤에 둔다(A5-9 "실제 운영 시의 방안"). 이 ADR의 분리 구조는 그 전환을 쉽게 하려는 것이다.
