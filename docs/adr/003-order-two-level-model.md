# ADR-003. 주문 2단 모델·판매자 스냅샷·R4 이관 계획

- **상태**: 승인
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-003(이슈 #21), E18, 불변식 I4·I5, 기획서 §6-2·§6-8·§13 R4, 작업진행.md B1·B2·B6·A5-4·D6, 검토보고서 RP-8, ADR-001·ADR-010

## 맥락
- 기획서 §6-2는 R1~R3을 주문 → 주문상품 2단으로 시작하고, R4에서 판매자주문 계층을 더하는 이관을 하기로 정했다. R4까지 판매자는 "직매입 자사" 하나뿐이라서, 3단 구조는 조회만 복잡하게 만든다.
- 검토 질문 RP-8: "R1~R3에서 판매자 스냅샷 말고도 미리 둬야 이관이 쉬워지는 것이 있는가?" R0-06(ERD 초안)보다 먼저 답해야 한다. 테이블이 생긴 뒤에는 마이그레이션이 앞으로만 추가되기 때문이다(A5-4).
- 정할 것은 세 가지다. ① 판매자를 R1부터 어떻게 표현하나 ② 배송비를 어느 단위에 저장하나 ③ R4 이관 검증 6개를 R1~R3 스키마가 어떻게 받쳐 주나.

## 결정
**주문 → 주문상품 2단으로 만든다. 판매자는 R1부터 실제 테이블 한 행으로 두고, 주문상품에는 판매자 ID를 스냅샷으로 남긴다. 배송비는 주문 단위로 저장한다. 판매자주문 계층과 관련 칼럼은 R4 전에 미리 만들지 않는다.**

1. **판매자 테이블**: `seller` 테이블을 R1에 만들고 "직매입 자사" 한 행을 시드로 넣는다. R1~R3에는 `catalog` 모듈이 이 테이블을 소유한다. R4에서 `seller` 모듈(B1)로 옮길 때는 패키지만 옮기고 테이블은 그대로 둔다.
2. **두 곳의 판매자 ID**: 상품의 `seller_id`는 현재 판매자이고 `seller`를 FK로 참조한다(같은 모듈 안). 주문상품의 `seller_id`는 주문 시점의 스냅샷이고 **FK를 걸지 않는다**. 판매자가 바뀌거나 비활성이 돼도 주문 기록이 따라 바뀌거나 막히면 안 된다. 다른 모듈 테이블이라는 점도 있다(ADR-001: 모듈 간 ID 참조).
3. **배송비는 주문 단위**: 주문에 `shipping_fee`를 저장한다. 주문상품에는 단가·수량·할인(R2b부터 쿠폰 안분액)·결제 금액까지만 둔다. 금액 관계는 `주문 결제 금액 = Σ 주문상품 결제 금액 + 배송비`다. **기획서 §6-2와 B2("배송비를 주문상품 단위까지")를 바꾸는 결정이다.** 배송비 계산 규칙은 order가 가진다. 장바구니 화면의 배송비 미리보기(R1-05)는 프론트가 order의 주문서 미리보기 API를 불러서 보여 준다(order는 `order → cart`로 장바구니를 읽는다). cart가 order를 부르면 순환이 되므로 cart에는 배송비 규칙을 두지 않는다(ADR-001).
4. **미리 두지 않는 것**: 판매자주문 테이블(빈 테이블 포함), 주문상품의 `seller_order_id` 칼럼, 판매자 유형·상품 유형(B2), 주문상품 상태 칼럼. 부분취소는 주문상품을 고치지 않고 취소 원장에 남긴다(B2·B6).
5. **R4 이관 순서**(expand/contract, A5-4): ① `seller_order` 생성(유니크 `(order_id, seller_id)`)과 주문상품 `seller_order_id`(NULL 허용) 추가 → ② 백필: 주문마다 주문상품의 `seller_id`로 묶어 판매자주문을 만들고 배송비·배송·취소 상태를 옮긴다 → ③ 검증(아래 표) → ④ `seller_order_id`를 NOT NULL + FK로. 주문상품의 기존 칼럼은 건드리지 않는다.

**R4 이관 검증 6개 대응표**

| R4 검증 | R1~R3에서 받쳐 주는 것 | 검사 방법(R4) |
|---|---|---|
| 건수·금액 합계 보존 | 주문상품 내용은 생성 뒤 바뀌지 않는다(B2) | 이관 전후 주문·주문상품 건수와 금액 합계 비교 |
| 판매자별 배송·취소 상태 | R4 전에는 주문마다 판매자가 하나다. 취소 원장은 주문상품 ID를 가리킨다(R2b 부분취소) | 판매자주문 상태 = 원래 주문 상태, 취소 원장 합계 = 판매자주문별 취소 합계 |
| 할인·배송비 배분 | 할인은 주문상품에 안분돼 있다(R2b). 배송비는 주문에 한 값이다 | Σ 판매자주문 배송비 = 주문 배송비, Σ 판매자주문 할인 = Σ 주문상품 할인 |
| 재실행 안전성 | 판매자주문 유니크 `(order_id, seller_id)` | 백필을 두 번 실행해도 행 수와 합계가 같다 |
| 주문 합계 보존 | 위 금액 관계를 R1부터 검사한다 | 주문 결제 금액 = Σ 판매자주문 결제 금액 |
| 판매자 스냅샷 유지 | 주문상품 `seller_id`는 FK 없는 스냅샷이다 | 이관 전후 주문상품 `seller_id`가 같고, 판매자주문 `seller_id`와 일치 |

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| 처음부터 3단 | R4 이관이 없다 | R1~R3의 모든 조회와 상태 전이가 판매자주문을 거친다. R3에서 멈추면 끝까지 필요 없는 구조다(기획서 §6-2) |
| 판매자 테이블 없이 상수 ID(1) | 테이블이 하나 줄어든다 | 상품 `seller_id`를 FK로 검사할 수 없다. R4에서 테이블을 만들고 기존 ID와 맞춰야 한다. 한 행짜리 테이블의 비용이 이보다 작다 |
| 배송비를 주문상품에 안분해 저장 | 기획서 원문 그대로다. 주문상품만 보고 금액을 안다 | 배송비는 상품이 아니라 배송 묶음의 값이다. 안분 기준과 단수 처리가 생기고, 부분취소 때(E18) 안분액을 다시 계산해야 한다. R4에서는 배송비가 판매자주문으로 옮겨 가므로 주문상품 안분은 결국 버려진다 |
| 빈 판매자주문 테이블과 NULL 칼럼을 미리 | R4 마이그레이션 한 단계가 줄어든다 | 쓰는 코드가 없는 테이블은 R4 백필이 어차피 필요하다. 조회마다 "비어 있는 계층"을 의식해야 한다 |
| 주문상품 `seller_id`에 FK | DB가 존재하는 판매자인지 검사한다 | 스냅샷이 현재 판매자 데이터에 묶인다. 모듈 간 참조는 ID로만 한다(ADR-001) |

## 결과
- **얻는 것**: R1~R3 조회와 상태 전이가 2단으로 단순하다. R4 이관은 "판매자주문 계층을 더하고 값을 옮기는" 작업으로 범위가 좁고, 검증 6개가 각각 R1부터 지키는 규칙에 기대어 있다. 배송비 단수 처리 문제가 없다.
- **감수하는 것**: R4에서 마이그레이션 네 단계와 이관 검증 테스트가 필요하다. 주문상품만으로는 "배송비를 포함한 상품별 실결제액"을 알 수 없다(필요하면 계산해서 보여 준다). 기획서·B2 문구를 고쳐야 한다.

## 보안·개인정보 영향
판매자 테이블에는 R4 전까지 자사 한 행만 있고 개인정보가 없다. 입점 판매자의 사업자 정보와 정산 계좌는 R4에서 다루며, 그때 암호화와 접근 권한을 따로 정한다. 주문의 소유자 검사(A5-9 S12)는 이 결정과 관계없다.

## 강제
- **예정(R1-06 서버 금액 계산, R1-08 주문 생성)**: 주문상품 엔티티에 내용 변경 메서드를 두지 않는다. Lombok `@Setter`는 컴파일 뒤에 남지 않는 표시라 ArchUnit으로 잡을 수 없고, `lombok.config`의 `flagUsage = error`로 컴파일 단계에서 막는다(ADR-010 보충). 손으로 만든 변경 메서드는 그것으로도 못 잡으므로 "주문상품 클래스에는 생성자 밖에서 필드를 쓰는 메서드가 없다"는 ArchUnit 규칙(필드 쓰기 접근 검사)을 R0-06에 따로 둔다. 주문 생성 테스트에서 `주문 결제 금액 = Σ 주문상품 결제 금액 + 배송비`를 확인한다. 상품 판매자를 바꿔도 기존 주문상품 `seller_id`가 그대로인지 테스트한다.
- **예정(R4)**: 위 대응표의 검사 6개를 이관 검증 테스트로 만든다.
