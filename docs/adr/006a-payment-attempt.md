# ADR-006a. 결제 시도 모델·조건부 전이

- **상태**: 제안
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-006a(이슈 #27), E08·E09·E12·E47·E48·E51, 불변식 I3·I4, 기획서 §6-5, 작업진행.md B3·B5·A5-1·A5-5, 검토보고서 RP-2, 입력 [`docs/reports/r0-verification.md`](../reports/r0-verification.md) §1·§2·§3·§6·§7, ADR-004·ADR-005·ADR-010

## 맥락
- B5가 정한 흐름: 주문당 결제 시도가 여러 개일 수 있고, 주문의 `current_attempt_id`가 가리키는 시도만 승인한다. paymentKey는 `CONFIRMING` 전이와 같은 트랜잭션에 저장한다. 승인은 트랜잭션 밖에서 고정 멱등키로 부른다.
- 이 ADR이 정할 것: 시도 테이블과 상태, 성공 URL 처리 순서, 승인 응답을 성공·실패·불명으로 가르는 기준, 타임아웃 값. 복구 작업자·보상 취소·웹훅은 ADR-006b가 맡는다.
- 검토 질문 RP-2: 이전 결제 창의 늦은 성공을 승인하지 않는 UX 트레이드오프를 받아들일 수 있나?
- R0-03 실측: 타임아웃 뒤 같은 키로 재승인하면 이중 승인 없이 `DONE`이 된다. 같은 키 동시 요청 하나는 `409 IDEMPOTENT_REQUEST_PROCESSING`이다. 다른 키로 재승인하면 `400 ALREADY_PROCESSED_PAYMENT`다. 실패 응답도 키에 저장된다. 카드 승인은 최대 2.4초 걸렸다. 카드 거절 응답은 테스트 환경에서 만들 수 없었다.

## 결정
**결제 시도는 주문과 별도 테이블이고, 주문의 현재 시도 하나만 `CONFIRMING`으로 갈 수 있다. 승인 응답은 `200 DONE`만 성공으로 보고, 실패는 R0-03에서 확인한 근거로만 판정한다. 나머지는 모두 "결과 불명"으로 두고 같은 멱등키 재시도와 paymentKey 조회로 확정한다.**

**1. 테이블** `payment_attempt(id, attempt_uid, order_id, amount, status, payment_key, failure_code, pg_version, created_at, …)`
- `attempt_uid`는 토스 `orderId`로 쓰는 UUIDv4다(ADR-010). 멱등키는 `confirm-{attempt_uid}`이고 재시도마다 새로 만들지 않는다(E51).
- `amount`는 시도를 만들 때 주문 결제 금액으로 고정한다. 승인 요청에는 이 값만 보낸다.
- `payment_key`는 유니크(NULL 허용)다. 웹훅·복구 작업자가 이 값으로 시도를 찾는다.
- 응답 중 쓰는 필드(상태, 수단, 승인 시각, `version`)만 저장하고 카드번호 등은 저장하지 않는다.

**2. 시도 상태(R1)**

| 현재 → 다음 | 언제 |
|---|---|
| (생성) → `CREATED` | 주문 생성(B5-1), 또는 현재 시도가 끝난(`FAILED`) 뒤 다시 결제할 때. 주문이 `PAYMENT_PENDING`일 때만 |
| `CREATED` → `CONFIRMING` | 성공 URL. 현재 시도이고 재예약 성공 |
| `CREATED` → `REJECTED` | 성공 URL이 왔는데 주문이 `PAYMENT_PENDING`이 아니다(종결 등) |
| `CREATED` → `FAILED` | 성공 URL 도착했지만 재예약 실패(E12). 승인 API를 부르지 않는다 |
| `CONFIRMING` → `APPROVED` / `FAILED` / `UNKNOWN` | 승인 결과(아래 표) |
| `UNKNOWN` → `APPROVED` / `FAILED` | 복구 작업자(ADR-006b) |

- **결제창을 다시 열 때는 현재 `CREATED` 시도를 그대로 다시 쓴다.** 같은 토스 orderId로 결제창을 닫았다 다시 열 수 있다(R0-03 §6. 단, 실측은 인증하지 않고 닫은 경우뿐이다. 인증까지 끝났는데 성공 URL이 오지 않은 뒤 다시 여는 경우와 두 탭이 동시에 인증하는 경우는 미확인, R1-09 착수 때 실측. 작업진행.md E4-2). 새 시도는 현재 시도가 `FAILED`로 끝났을 때만 만든다. **대비책**: 토스가 같은 orderId의 재인증을 거부하면, 현재 `CREATED` 시도를 `REJECTED`로 닫고 새 시도를 만든다. 둘 다 payment 모듈 안의 일이라 순환이 생기지 않는다. 그래서 주문마다 `CREATED` 시도는 많아야 하나이고, 이전 시도를 닫으러 다른 모듈을 부를 일이 없다. **기획서 §6-5 1번·B5 1번("다시 결제하면 새 시도")을 바꾸는 결정이다.**
- **주문 만료 시각**: 결제창을 열 때마다(시도 생성이든 재사용이든) payment가 주문 행을 잠그고 주문이 `PAYMENT_PENDING`일 때만 `payment_expires_at`을 "지금 + 40분"으로 갱신한다(ADR-005 정책값, `payment → order` 호출, ADR-001). 주문이 이미 만료됐으면 결제창을 열지 않고 "주문이 만료됐다"를 보여 준다. 주문 만료 배치는 주문의 이 칼럼만 본다. 결제 모듈의 값을 주문 모듈이 읽으러 가지 않게 하기 위해서다.
- 전이 규칙(잠금, 표 한 곳, 멱등, 이력)은 ADR-004와 같다. 보상 취소 상태(`ORPHANED` 등)는 ADR-006b가 더한다.

**3. 성공 URL 처리 순서**(한 트랜잭션)
1. 주문 행을 잠근다(ADR-005 잠금 순서). 이때 order 공개 API의 소유자 조건부 조회(주문번호 + 로그인한 회원 ID, ADR-008)를 쓴다. 남의 주문이거나 없으면 404로 답하고 아무것도 바꾸지 않는다(S12).
2. 금액을 `amount`와 대조한다. 다르면 거부하고 경고 로그를 남긴다. 시도 상태는 그대로 둔다(E08).
3. 시도가 `CREATED`가 아니면 아무것도 바꾸지 않고 현재 상태를 돌려준다(새로고침·중복 호출, E47).
4. 주문이 `PAYMENT_PENDING`이 아니면(만료 등) `REJECTED`로 닫는다. 현재 시도가 아니면(이미 끝난 옛 시도) 3에서 걸러진다.
5. 예약이 풀렸으면 주문상품 기준으로 다시 잡는다(ADR-005, SKU ID 순). 여러 SKU 중 하나라도 실패하면 이 트랜잭션 전체를 되돌린다(앞서 잡은 SKU도 함께 풀린다). 그다음 새 트랜잭션에서 주문 행을 잠그고 시도를 `FAILED`(재고 소진)로 바꾼 뒤 끝낸다. 승인 API는 부르지 않는다.
6. 주문 `CONFIRMING`, 시도 `CONFIRMING`, `payment_key` 저장. 커밋한다.
7. **트랜잭션 밖에서** 승인 API를 부르고, 결과를 새 트랜잭션(주문 행 잠금)에서 반영한다. 성공이면 주문 `PAID`, 시도 `APPROVED`, 예약 소진.
8. **요청 안에서는 첫 호출만 기다린다.** 첫 호출의 결과가 불명이면 바로 "결제 확인 중"으로 응답하고, 같은 키 재시도와 조회(아래 4)는 서버 안의 비동기 작업으로 이어 간다. 결과 화면은 주문 상태를 주기적으로 다시 읽는다(C1 "새로고침해도 같은 상태"). 서버가 그 사이 죽으면 복구 작업자가 맡는다(ADR-006b).

**4. 승인 응답 분류**(R0-03 실측만 근거, A5-5)

| 응답 | 판정 | 조치 |
|---|---|---|
| 200 `DONE` | 성공 | `APPROVED` |
| 400 `EXPIRED_PAYMENT`(조회하면 `ABORTED`) | 실패 | `FAILED`, 주문 `PAYMENT_PENDING` |
| 403 `FORBIDDEN_REQUEST`(금액 등 요청 오류) | 실패 + 오류 로그(알람은 R2a) | 우리 버그다. 같은 키에 실패가 저장되므로 재시도하지 않는다 |
| 409 `IDEMPOTENT_REQUEST_PROCESSING` | 불명 | 잠시 뒤 같은 키로 재시도 |
| 400 `ALREADY_PROCESSED_PAYMENT` | 불명 | paymentKey로 조회해 확정 |
| 타임아웃, 5xx, 그 밖의 코드 | 불명 | 같은 키로 재시도 → 그래도 불명이면 조회 |
| 조회 결과 `DONE` / `ABORTED`·`EXPIRED` / 그 밖 | 성공 / 실패 / 불명 | 불명이면 시도 `UNKNOWN`, 주문 `CONFIRMING` 유지, 예약 유지. 복구 작업자가 맡는다 |

- 처음 보는 코드를 실패로 처리하지 않는 이유: 실패로 닫으면 주문이 `PAYMENT_PENDING`으로 돌아가 새 시도가 생길 수 있다. 실제로는 승인됐다면 이중 결제가 된다. 카드 거절 같은 실패 코드는 실측한 뒤 표에 더한다(R2a 조치표).
- **값**: 승인 연결 타임아웃 3초, 읽기 타임아웃 10초(카드 승인 최대 실측 2,367ms의 4배 이상, R0-03 §7). 같은 키 재시도는 2회(1초, 3초 뒤). 모두 설정값이다.
- **최악의 시간**: 고객이 기다리는 시간은 첫 호출 최대 13초(= 연결 3 + 응답 10)다. 뒤에서 이어 가는 재시도까지 합친 최대는 약 43초(= 3회 × (3 + 10초) + 대기 1초 + 3초)이고, 그 뒤 조회 한 번(실측 105~254ms, R0-03 §1)이 더해진다.

**5. RP-2에 대한 답: 받아들인다.** 이미 끝난 옛 시도(`FAILED`)나 만료된 주문에 늦게 온 성공은 승인하지 않는다(옛 시도는 3, 만료 주문은 4). 결제창을 다시 여는 것은 같은 시도를 다시 쓰므로 이 경우에 해당하지 않는다. 승인 API를 부르지 않은 결제는 돈이 나가지 않고 토스에서 30분 뒤 `EXPIRED`가 된다(R0-03 §2). 고객에게는 "이 결제는 완료되지 않았습니다. 현재 결제 창에서 다시 결제해 주세요"를 보여 준다. 결제 화면에는 "결제 창은 하나만 열어 주세요"를 안내한다.

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| 주문당 결제 시도 하나(주문 칼럼에 paymentKey) | 테이블이 하나 줄어든다 | 재결제할 때 이전 결과를 덮어쓴다. 늦게 온 이전 승인이 어느 결제였는지 알 수 없다(B5-1 이유) |
| 늦은 성공도 승인하고 현재 시도를 취소 | 고객이 다시 결제하지 않는다 | 한 주문에 승인이 둘 생길 수 있어 보상 취소가 정상 경로가 된다. 정합성을 편의보다 앞세운다(RP-2) |
| 모르는 4xx는 실패로 | 단순하다 | 실제로 승인된 결제를 실패로 닫으면 이중 결제로 이어진다. 조회 한 번(105~254ms, R0-03 §1)이 더 싸다 |
| 결제창을 다시 열 때마다 새 시도(B5 원안) | 시도 하나가 결제창 한 번과 대응해 단순하다 | 이전 `CREATED` 시도를 닫아야 하는데, 주문 만료(order 모듈) 때 닫으려면 order → payment 호출이 생겨 순환이 된다(ADR-001). 같은 orderId로 다시 열 수 있으니(R0-03 §6) 새로 만들 이유가 없다 |
| 재시도까지 모두 요청 안에서 기다림 | 응답 한 번에 결과가 확정된다 | 최악 약 43초 동안 결제 결과 화면이 멈춘다. Nginx 같은 프록시의 대기 한도와도 부딪힌다 |
| 트랜잭션 안에서 승인 호출 | 코드가 한 덩어리다 | 외부 호출 동안 주문 행 잠금과 DB 연결을 잡는다. 승인 뒤 커밋이 실패하면 돈은 나갔는데 기록이 없다(E10). 외부 호출은 트랜잭션 밖(A5-1) |

## 결과
- **얻는 것**: 주문마다 승인될 수 있는 시도가 언제나 하나다(I4의 전제). 새로고침·중복 탭·늦은 성공이 모두 같은 규칙으로 처리된다. 서버가 죽어도 paymentKey가 남아 복구할 수 있다(E48). 승인 결과를 섣불리 실패로 닫지 않는다.
- **감수하는 것**: 이전 창에서 결제를 마친 고객은 다시 결제해야 한다. 처음 보는 실패 코드는 "결과 불명"이 되어 고객이 "결제 확인 중"을 더 오래 볼 수 있다. 승인 결과 반영에 트랜잭션이 하나 더 든다.

## 보안·개인정보 영향
- 금액은 서버 저장값만 쓰고 성공 URL의 금액은 대조에만 쓴다(E08). 대조 실패는 위변조 시도로 보고 경고 로그를 남긴다.
- 성공 URL 처리는 로그인한 고객의 주문인지 확인한 뒤에 한다(S12, 위치는 ADR-008). `attempt_uid`는 추측할 수 없지만 소유자 검사를 대신하지 않는다(ADR-010).
- 시크릿 키는 서버 환경변수에만 두고 로그에 남기지 않는다(A5-10). 응답 원문은 저장하지 않고 필요한 필드만 저장한다. 카드번호는 가려져 있어도 저장하지 않는다(R0-03 §7).

## 강제
- **예정(R1-09·R1-10, PG 스텁 통합 테스트)**: 이슈 #27의 시나리오 6개. 스텁 응답은 `tools/pg-stub`의 R0-03 실측 응답만 쓴다(A5-5).
- **예정(R1-09, 단위 테스트)**: 시도 전이표 전 쌍, 멱등키가 `confirm-{attempt_uid}`로 고정되는지.
- **예정(R1-18)**: I4 검사(PAID 주문 ↔ `APPROVED` 시도 정확히 하나, 금액 일치).
- **예정(R2a)**: 새 멱등키로 재시도하면 실패하는 테스트(E51).

## 재검토 조건
- 카드 거절 등 실패 응답을 실측했을 때: 응답 분류표에 더한다(R2a 조치표).
- 고객 문의나 시연에서 "이전 창 결제 거부"가 큰 불편으로 드러날 때.
- 승인 응답 시간이 읽기 타임아웃 10초에 가까워질 때.

## 논의 기록

## 실제 운영과의 차이
- 실제 카드는 인증만 하고 승인하지 않은 결제가 카드 앱에 잠시 "승인 대기"처럼 보일 수 있다(미확인). 결제수단별 고객 화면은 R0-03에서 확인하지 못했다(§7 미확인). R1-16·R1-17 착수 때 확인한다(작업진행.md E4-2).
