# ADR-006b. 복구 작업자·보상 취소

- **상태**: 승인
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-006b(이슈 #31), E09·E10·E11·E48·E49·E50·E52, 불변식 I3·I4·I5, 기획서 §6-5, 작업진행.md B0·B5(6~8번)·B6·A5-1, 검토보고서 RP-5·RP-6, 입력 [`docs/reports/r0-verification.md`](../reports/r0-verification.md) §1·§2·§4·§8, ADR-004·ADR-006a

## 맥락
- ADR-006a는 결과를 모르는 승인을 `UNKNOWN`(주문은 `CONFIRMING`)으로 남긴다. 이 ADR은 그 뒤를 정한다. 누가 언제 조회해서 확정하는지, 돈은 나갔는데 주문이 받을 수 없을 때 어떻게 돌려주는지, 웹훅을 어떻게 받는지다.
- B5 7번은 "승인 성공 후 DB 저장 실패(E10)"와 "종결 주문에 승인 도착(E50)"을 모두 보상 취소 대상으로 적었다.
- R0-03 실측: paymentKey 조회 결과는 `IN_PROGRESS`·`DONE`·`CANCELED`·`ABORTED`·`EXPIRED`, 없는 키는 404다. `IN_PROGRESS`에 같은 키로 승인을 다시 부르면 10분 안이면 승인되고, 지났으면 실패가 확정된다. 다른 키로 재취소하면 `400 ALREADY_CANCELED_PAYMENT`다. 웹훅은 재전송마다 전송 ID가 바뀌고, 서명 헤더는 첫 전송에만 있다. **계약 전 위젯 키 결제에는 웹훅이 오지 않는다**(§5).
- 검토 질문 RP-5: R1 단순판 경계(DONE·명확한 미승인만 처리, 나머지는 유지 + 경고)가 충분한가? RP-6: 실시간으로 막을 네 가지(초과판매, 이중 승인, 정상 결제 중 예약 해제, 만료 주문 부활)에 빠진 것이 있는가?

## 결정
**결과 확정은 "paymentKey로 조회해서 반영하는 함수" 하나가 맡고, 복구 작업자와 웹훅이 둘 다 이 함수를 부른다. 주문이 아직 받을 수 있으면 확정하고, 받을 수 없을 때만 보상 취소한다. PG 취소는 고객 취소와 보상 취소 모두 `pg_cancel` 기록 하나로 처리한다.**

**1. 결과 확정 함수** `reconcile(paymentKey)`
- 트랜잭션 밖에서 조회하고, 결과를 새 트랜잭션(주문 행 잠금 → 조건 재확인)에서 반영한다.

- **먼저 거르는 것**: 시도가 이미 `APPROVED`이고 조회 결과가 `DONE`이면 아무것도 하지 않는다(주문이 `PAID` 이후 어느 상태든). 승인 응답 3~6초 뒤에 오는 정상 `DONE` 웹훅(R0-03 §8)이 여기에 해당한다. 시도가 이미 `CANCELLED`이고 결과가 `CANCELED`인 경우도 같다(ADR-004 규칙 3 멱등).

| 조회 결과 | 시도가 `CONFIRMING`·`UNKNOWN`이고 주문이 그 시도로 `CONFIRMING` | 그 밖(시도가 `CREATED`·`FAILED`·`REJECTED`이거나, 주문이 종결) |
|---|---|---|
| `DONE` | 시도 `APPROVED`, 주문 `PAID`, 예약 소진 | 시도 `ORPHANED` → 보상 취소 + 오류 로그(E50). 정상 흐름에서는 생기지 않아야 하는 경우다 |
| `ABORTED`·`EXPIRED` | 시도 `FAILED`, 주문 `PAYMENT_PENDING` | 시도 `FAILED`(이미 닫혔으면 그대로) |
| `IN_PROGRESS` | 같은 키 `confirm-{attempt_uid}`로 승인 재호출 → ADR-006a 분류 | 아무것도 하지 않음(승인하지 않으면 토스가 30분 뒤 만료) |
| `CANCELED` | `pg_cancel`을 완료로 표시(아래 3). 보상 취소면 시도 `CANCELLED`, 고객 취소면 claim이 다음 확인 때 마무리(아래 4) | 같음 |
| 404, 조회 실패, 그 밖 | 유지 + 경고 로그 | 유지 + 경고 로그 |

- **E10(승인 뒤 DB 저장 실패)은 보상 취소하지 않는다.** 승인 결과를 반영하다 실패해도 주문은 `CONFIRMING`에 남고, `CONFIRMING`은 만료되지 않는다(ADR-005). 그래서 복구 작업자가 조회해 `PAID`로 마무리하면 고객은 정상적으로 주문을 받는다. **B5 7번, E10, 기획서 §6-5 7번을 바꾸는 결정이다.** 보상 취소는 주문이 받을 수 없는 경우(`ORPHANED`)에만 한다.

**2. 시도 상태 추가**(ADR-006a에 더함): `CONFIRMING`·`UNKNOWN`·`CREATED`·`FAILED`·`REJECTED` → `ORPHANED`(조회 결과 `DONE`인데 위 표의 "그 밖"일 때. PG는 승인, 주문은 받을 수 없음) → `CANCEL_REQUESTED` → `CANCELLED`. `APPROVED`는 `ORPHANED`로 가지 않는다(위의 먼저 거르는 것). B3 시도 그림의 `APPROVED → ORPHANED`를 바꾸는 결정이다. 결과 불명이 길어지면 R2a에서 `CANCEL_UNKNOWN`과 운영자 큐를 더한다.

**3. PG 취소 기록** `pg_cancel(id, uid, attempt_id, source, amount, status, requested_at, canceled_at, …)`
- payment 모듈이 소유한다. `source`는 `CUSTOMER`(claim의 고객 취소)나 `COMPENSATION`(보상 취소)이다. claim은 payment 공개 API로 만들고 결과를 묻는다(ADR-001 `claim → payment`). payment는 claim을 부르지 않는다.
- **취소 요청을 먼저 기록하고 커밋한 뒤** 트랜잭션 밖에서 취소 API를 부른다(A5-1). 멱등키는 `cancel-{uid}`이고 `uid`는 UUIDv4다. 숫자 ID를 쓰면 claim과 payment의 번호가 겹치거나, 개발 DB를 초기화한 뒤 토스(15일 보관)에 남은 옛 키와 겹칠 수 있다.
- **시도 하나에 진행 중이거나 완료된 취소는 하나뿐이다.** R1은 전체취소만 있으므로 `pg_cancel`에 `attempt_id` 유니크를 건다. 고객 취소와 보상 취소가 겹쳐도 두 번째 취소 기록이 만들어지지 않는다. 부분취소(R2b)에서 이 제약을 다시 정한다.
- 결과: `200 CANCELED`면 완료(`canceled_at` = 응답의 `canceledAt`, 환급 완료 시각). `400 ALREADY_CANCELED_PAYMENT`면 조회로 `CANCELED`를 확인한 뒤 완료한다(R0-03 §4). 타임아웃·5xx면 같은 키로 재시도하고, 그래도 모르면 `REQUESTED`에 남겨 복구 작업자가 맡는다(E49).
- **명확한 실패는 아직 없다.** 실측한 취소 실패 코드가 없다(`tools/pg-stub/responses`에 취소는 200·400 이미 취소됨·404뿐). 그래서 ADR-006a의 원칙대로 그 밖의 응답은 실패가 아니라 불명으로 두고, R1에서는 `CANCEL_REQUESTED → PAID`(취소의 명확한 실패) 전이가 일어나지 않는다. 404는 우리 기록과 PG가 어긋난 것이라 유지 + 오류 로그다. 실패 코드를 실측하면 표에 더한다(R2a).

**4. 복구 작업자**(R1 단순판). 모듈 호출 방향(ADR-001)에 맞춰 둘로 나눈다.
- **기준 시각**: "2분 넘게"는 그 상태로 바뀐 시각(`status_changed_at`)부터 잰다. 생성 시각으로 재면 `CONFIRMING`이 된 직후 요청 안의 처리와 겹친다.
- **payment 작업자**: 2분 넘게 `CONFIRMING`·`UNKNOWN`인 시도와, 2분 넘게 `REQUESTED`인 **보상 취소**(`COMPENSATION`) `pg_cancel`을 맡는다. 시도는 `reconcile`로, 보상 취소는 같은 키 재요청이나 조회로 확정한다.
- **claim 작업자**: 2분 넘게 `CANCEL_REQUESTED`인 주문(고객 취소)을 맡는다. payment 공개 API로 그 `pg_cancel`의 결과를 묻거나 같은 키로 다시 요청하게 하고, 결과에 따라 주문 `CANCELLED` + 재고 복구 + 환급 완료 시각, 또는 명확한 실패면 `PAID` 복귀를 처리한다(ADR-004, B6). 주문 상태와 재고 복구는 claim의 일이고 payment는 claim을 부를 수 없기 때문이다(ADR-001).
- 둘 다 1분마다 실행한다. 2분은 요청 안의 처리가 끝날 시간보다 길게 잡은 값이다. 승인 쪽 최악은 약 43초(= 3회 × (연결 3 + 응답 10초) + 대기 1초 + 3초, ADR-006a)이고 취소도 같은 타임아웃 값을 쓴다.
- 건마다 따로 처리하고, 주문 행 잠금 뒤 조건을 다시 확인한다. PG 호출은 고정 멱등키라서, 같은 건을 두 번 처리해도 결과가 같다. R1은 앱 인스턴스가 하나라 작업자마다 하나씩만 돈다.
- 30분 넘게 확정되지 않은 건은 경고 로그를 남긴다(E52). 알람과 운영자 큐는 R2a다.

**5. 웹훅** `POST /api/webhooks/toss`(공개 경로로 명시, A5-9 S1). `/api` 아래에 두어 배포 프록시(ADR-009의 Nginx `/api` 규칙)와 보안 설정(ADR-008)의 경로 규칙 하나로 처리한다. 토스 개발자센터에 등록한 주소도 이 경로로 바꾼다.
- 본문에서 `paymentKey`·`data.status`·`createdAt`·`eventType`만 꺼내 `pg_webhook_event`에 저장하고 바로 200으로 답한다. 유니크 키 `(payment_key, status, created_at)`로 중복을 거른다(B5 8번). 전송 ID는 재전송마다 바뀌므로 쓰지 않는다.
- `createdAt`은 시간대 표시가 없는 한국 시각(나노초)이다(R0-03 §8). Asia/Seoul로 해석해 UTC `DATETIME(6)`(마이크로초까지)로 저장한다(ADR-010). 같은 웹훅의 재전송은 값이 같으므로 잘라도 중복 판정이 흔들리지 않는다.
- **남용 방어**: paymentKey는 고객 브라우저의 성공 URL에 보이므로, 자기 paymentKey로 `createdAt`만 바꿔 웹훅을 계속 보낼 수 있다. 그래서 웹훅 경로에 IP별 요청 한도(Redis)를 두고, 같은 paymentKey의 처리 대기는 한 건으로 합치고, 시도가 이미 확정(`APPROVED`·`CANCELLED`·`FAILED`)이고 웹훅 상태가 우리 기록과 같으면 조회하지 않는다.
- 뒤에서 처리할 때는 **우리 DB에 있는 paymentKey만** `reconcile`을 부른다. 모르는 키는 기록만 남긴다. 가짜 웹훅을 대량으로 보내 우리가 토스 조회를 남발하게 만드는 것을 막는다.
- 서명 헤더는 필수 조건으로 두지 않는다(재전송에는 없다). 웹훅 내용은 믿지 않고 조회 결과만 믿는다.
- 계약 전 위젯 키로는 웹훅이 오지 않는다. 그래서 R1 시연에서 놓친 결과를 잡는 주된 수단은 복구 작업자다. 웹훅 경로는 API 개별 연동 키(결제창)로 시험한다.

**6. RP-5에 대한 답**: 충분하다. R0-03에서 `IN_PROGRESS`에 같은 키로 승인을 다시 부르는 것이 안전하다는 것을 확인했다(§2·§3). 그래서 단순판도 `IN_PROGRESS` 건은 기다리지 않고 확정한다. 남는 것(404, 처음 보는 응답)은 유지 + 경고이고, R2a 대사와 운영자 큐가 받는다.

**7. RP-6에 대한 답**: 하나를 더한다. **이중 환불**(같은 취소로 PG를 두 번 부르거나 재고를 두 번 복구)이다. 막는 장치는 세 겹이다. ① 같은 취소 기록의 재시도는 고정 키 `cancel-{uid}`로 한 번만 처리된다. ② 한 시도에 취소 기록이 둘 생기는 것은 `pg_cancel.attempt_id` 유니크가 막는다(위 3). ③ 재고 이중 복구는 원장 유니크 키(ADR-005)가 막는다. 남는 어긋남은 I5 검사(R1-18)가 잡는다. 목록에 명시해 테스트 대상으로 만든다.

**8. RP-7(PG 스텁을 WireMock으로 만들지, 직접 만들지)**: 이 ADR에서 정하지 않는다. 스텁을 실제로 만드는 R1-09에서 정하고 작업진행.md E4-2에 등록했다. 어느 쪽이든 응답은 `tools/pg-stub/responses`의 R0-03 실측만 쓴다(A5-5).

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| E10도 보상 취소(B5 원안) | 승인 직후 실패를 즉시 정리한다 | 주문이 정상적으로 받을 수 있는데 돈을 돌려주고 주문을 실패시킨다. 고객은 결제했는데 주문이 없다 |
| 웹훅 내용을 믿고 바로 반영 | 조회 한 번을 아낀다 | 위조와 역순 도착을 막을 수 없다. 서명 헤더는 재전송에 없다(R0-03 §8) |
| 서명 헤더 필수 | 위조를 바로 거른다 | 재전송을 모두 버리게 된다(R0-03 §8) |
| payment 작업자 하나가 고객 취소까지 마무리 | 작업자가 하나다 | 주문 `CANCELLED`와 재고 복구는 claim의 일인데 payment는 claim을 부를 수 없다(ADR-001, 순환) |
| 취소 기록을 claim·payment에 따로 | 모듈별로 단순하다 | 멱등키 번호 공간이 둘이 되어 겹칠 수 있다. PG 취소 호출 코드가 두 벌이 된다 |
| 멱등키에 숫자 ID | 짧다 | 개발 DB 초기화 뒤 번호가 다시 쓰이면 토스에 남은 옛 응답을 받는다(키 15일 보관) |

## 결과
- **얻는 것**: 결과 확정 경로가 하나라서, 성공 화면·웹훅·복구 작업자가 서로 다른 판단을 내리지 않는다. 승인 뒤 서버가 죽어도 고객 주문이 살아남는다. 같은 결제에 취소 기록이 두 번 생기지 않는다(유니크 제약). 정상 승인 뒤 늦게 온 웹훅이 취소를 일으키지 않는다.
- **감수하는 것**: 결과 확정이 최대 약 3분(= 대상 기준 2분 + 작업자 주기 1분) 늦을 수 있다. 작업자가 둘(payment, claim)이다. R2a 전에는 오래 풀리지 않는 건이 경고 로그로만 남는다. 웹훅을 받을 때마다 조회 한 번이 든다.

## 보안·개인정보 영향
- 웹훅 경로는 인증 없는 공개 경로다. 본문을 믿지 않고 조회로 확정하며, 모르는 paymentKey는 조회하지 않는다. 본문 크기를 제한하고 필요한 필드만 저장한다. 원문(카드 정보 등)은 저장하지 않는다.
- 시크릿 키는 서버 환경변수에만 둔다. 웹훅·조회 로그에 키와 카드번호를 남기지 않는다(A5-10).
- 보상 취소는 사람이 아니라 시스템이 돈을 움직이므로 항상 오류 로그와 `pg_cancel` 기록을 남긴다.

## 강제
