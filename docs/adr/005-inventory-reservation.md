# ADR-005. 재고 3계층·원장·만료 분리·TTL·잠금 순서

- **상태**: 제안
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-005(이슈 #25), E01·E02·E05·E12·E47, 불변식 I1·I2·I3, 기획서 §6-4, 작업진행.md B4·B5·B6·A5-2, 검토보고서 RP-3, 입력 [`docs/reports/r0-verification.md`](../reports/r0-verification.md) §2, ADR-001·ADR-004

## 맥락
- 기획서 §6-4와 B4가 정한 것: 재고 3계층(판매가능·예약·물리), 원장, 예약 만료와 주문 만료의 분리, 조건부 원자 UPDATE, "예약 해제와 `CONFIRMING` 전이는 둘 중 하나만 이긴다". 이 ADR에 미룬 것은 저장 방식, 잠금 순서, TTL 값이다.
- 검토 질문 RP-3: 주문 행 잠금과 SKU 행 잠금의 획득 순서를 명시해야 하나? 배치는 건별 트랜잭션이 맞나?
- R0-03 실측(§2): 토스는 인증 뒤 30분이 지나고 1분쯤 안에 결제를 `EXPIRED`로 바꾼다. 10분 승인 제한은 상태를 바꾸지 않고, 늦은 승인은 `ABORTED` + `EXPIRED_PAYMENT`로 끝난다. 승인 API를 부르지 않은 결제는 돈이 나가지 않는다.
- ADR-004는 모든 주문 전이를 "주문 행을 잠근 뒤 도메인 메서드로" 하기로 했다. B4의 주문 만료 "조건부 UPDATE"와 맞춰야 한다.

## 결정
**SKU마다 재고 행 하나에 세 수량을 저장하고, 예약은 `available >= n` 조건부 원자 UPDATE로 잡는다. 모든 증감은 같은 트랜잭션에서 원장에 한 줄씩 남긴다. 주문이 걸린 작업은 언제나 주문 행을 먼저 잠그고, 그다음 SKU 행을 ID 오름차순으로 건드린다.**

**1. 재고 행** `sku_stock(sku_id, available, reserved, on_hand)`
- `available`(판매가능)은 고객에게 보이는 수량, `reserved`는 예약 중인 수량, `on_hand`(물리)는 창고에 있는 수량이다.
- 결제는 끝났지만 아직 출고되지 않은 수량은 `on_hand − available − reserved`로 계산한다.
- DB CHECK 제약: `available >= 0`, `reserved >= 0`, `on_hand − available − reserved >= 0`(I1).

| 일 | 변화 | 주체 |
|---|---|---|
| 입고·조정 | `available`·`on_hand` +n(조정은 ±) | admin → inventory |
| 예약 | `available` −n, `reserved` +n. `WHERE available >= n`, 영향 행 0이면 재고 부족 | order(주문 생성), payment(`CONFIRMING` 재예약) |
| 예약 해제 | `reserved` −n, `available` +n | order(만료 배치) |
| 예약 소진(승인 성공) | `reserved` −n | payment |
| 출고(`SHIPPED`) | `on_hand` −n | shipping → inventory(ADR-001 표에 더함) |
| 취소 복구(출고 전) | `available` +n | claim |

**2. 예약 기록** `stock_reservation(id, order_id, sku_id, qty, status, expires_at)`
- 상태는 `ACTIVE → RELEASED | CONSUMED` 한 번만 바뀐다. `WHERE status = 'ACTIVE'` 조건부 UPDATE로 바꾸고, 영향 행이 0이면 이미 처리된 것이므로 아무것도 하지 않는다(I3).
- 재예약(`CONFIRMING` 전이 안)은 새 `ACTIVE` 행을 만든다. SKU와 수량은 요청이 아니라 **주문상품에서** 가져온다(E47, ADR-003의 "주문상품 내용 불변").

**3. 원장** `stock_ledger(sku_id, d_available, d_reserved, d_on_hand, reason, ref_type, ref_id, created_at)`
- 추가만 한다. SKU별 증감 합계 = 재고 행의 현재 값(I2).
- 유니크 키 `(ref_type, ref_id, reason, sku_id)`. 같은 근거로 두 번 기록하려 하면 DB가 막는다. 취소 복구가 "정확히 한 번"(B6)인 근거다.

**4. 잠금 순서(RP-3 답: 명시한다)**
- 규칙: **주문 행(`SELECT … FOR UPDATE`) → SKU 행(ID 오름차순)**. 거꾸로 잡는 코드는 없다. 주문이 걸리지 않은 입고·조정은 SKU 행만 잡는다.
- 주문 생성은 주문 행이 아직 없으므로 SKU 행만 ID 순으로 잡는다(E02).
- 주문이 걸린 흐름은 모두 같다: `CONFIRMING` 전이 + 재예약, 승인 성공 + 소진, 예약 만료 해제, 주문 만료, 취소 복구.

**5. 만료 배치(RP-3 답: 주문마다 트랜잭션 하나)**
- 배치는 대상 주문 ID를 잠금 없이 조회한 뒤, 주문마다 새 트랜잭션에서 주문 행을 잠그고 **조건을 다시 확인한 다음** 처리한다. 한 건이 실패해도 나머지는 진행되고, 결제 경로가 오래 기다리지 않는다.
- **예약 만료**: 예약이 만료됐고 주문이 `CONFIRMING`이 아니면 그 주문의 `ACTIVE` 예약을 해제한다. 주문은 `PAYMENT_PENDING`으로 남는다(E05).
- **주문 만료**: `PAYMENT_PENDING`이 정책 시간을 넘으면 남은 예약을 해제하고 `EXPIRED`로 바꾼다. **주문 행을 잠그고 처리한다. B4·기획서 §6-4의 "조건부 UPDATE로 처리"를 바꾸는 결정이다**(ADR-004 전이 규칙과 맞춘다).
- 주문 만료 전에 PG 조회는 하지 않는다. `PAYMENT_PENDING`에서는 승인 API를 부른 시도가 없다. 승인은 `CONFIRMING` 전이 뒤에만 하기 때문이다(B5). 그러니 돈이 나간 결제가 있을 수 없다. 늦게 온 성공 URL은 `REJECTED`로 닫힌다(B5-3-5). paymentKey가 있는 시도의 조회는 ADR-006b가 맡는다.

**6. 정책값**(설정 파일, 드롭 R3에서 조정)
- **예약 TTL 20분**(예약 생성 시각부터). 결제창 체류 약 10분 + 여유. 승인은 성공 URL 도착 즉시 하므로(R0-03 §2) 10분 승인 제한을 TTL에 더하지 않는다. 토스 30분보다 짧다.
- **주문 만료 40분**(현재 결제 시도의 생성 시각부터). 토스 30분 + 전환 지연 약 1분(R0-03 실측) + 여유. 고객이 어느 시도에서든 인증까지 마쳤다면, 우리 주문이 만료되기 전에 토스 쪽이 먼저 결과를 낸다. 주문 생성 시각부터 세면 재결제한 고객의 인증이 우리 만료 뒤에 도착할 수 있어서 시도 기준으로 센다.

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| `available`을 저장하지 않고 `on_hand − reserved − 판매확정`으로 계산 | 값이 하나 줄어든다 | 예약 때 조건부 원자 UPDATE 한 문장으로 끝낼 수 없다. 계산하려면 행을 먼저 잠가야 한다 |
| SKU 행 비관적 잠금(`FOR UPDATE`) 후 차감 | 흐름을 읽기 쉽다 | 조건부 UPDATE가 같은 일을 잠금 시간 없이 한다. 핫 SKU 비교(비관적 락, `SKIP LOCKED`)는 R3에서 측정한다(B4) |
| Redis로 먼저 차감하고 DB에 반영 | 드롭 처리량 | Redis는 재고의 진실 원천이 아니다(기획서 §9-4). 두 저장소의 불일치를 대사해야 한다 |
| 예약 만료와 주문 만료를 하나로 | 배치가 하나다 | v0.1 버그(정상 결제 중 예약 해제)를 다시 만든다(기획서 §6-4) |
| 만료 배치 전체를 한 트랜잭션으로 | 코드가 짧다 | 대상이 많으면 주문 행 잠금이 오래 유지돼 결제 경로가 막힌다. 한 건 실패가 전체를 되돌린다 |
| 주문 만료를 조건부 UPDATE로(B4 원안) | 잠금이 없다 | 남은 예약 해제와 함께 해야 하고, ADR-004의 "전이는 잠금 후 도메인 메서드로"와 어긋난다 |

## 결과
- **얻는 것**: 초과판매는 조건부 UPDATE와 CHECK 제약으로 두 번 막힌다. 교착은 잠금 순서 규칙 하나로 막는다. 예약·복구의 "정확히 한 번"은 예약 상태 조건부 UPDATE와 원장 유니크 키가 DB 수준에서 지킨다. I1~I3을 SQL로 검사할 수 있다.
- **감수하는 것**: 재고 변경마다 원장 쓰기가 한 번 더 생긴다. 판매 확정 수량이 계산값이라 화면에 보일 때 식을 알아야 한다. TTL 20분 안에 결제하지 못한 고객은 `CONFIRMING`에서 재고를 다시 잡아야 하고, 그 사이 다른 사람이 사 가면 결제할 수 없다(E12, 정책 선택).

## 보안·개인정보 영향
재고 수량과 원장에는 개인정보가 없다. 입고·조정은 관리자만 하고 원장의 주체 기록(ref)으로 추적한다. 고객 API는 판매가능 여부만 보여 주고 정확한 수량을 노출할지는 R1-04 화면에서 정한다.

## 강제
- **예정(R1-07, DB 마이그레이션)**: CHECK 제약 3개, 원장 유니크 키.
- **예정(R1-07, 동시성 테스트)**: 이슈 #25의 시나리오 5개(E01, E02, E05, I3, I2).
- **예정(R1-18)**: 불변식 검사 I1~I3 SQL.
- **리뷰**: SKU 행을 잡은 뒤 주문 행을 잠그는 코드가 있으면 거부한다. 기계적 검사가 가능한지는 R1-07에서 본다.

## 재검토 조건

- 체크아웃 이탈 데이터가 생기면 TTL 20분·만료 40분을 다시 본다.
