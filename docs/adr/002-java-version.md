# ADR-002. Java 버전: Java 21 LTS로 시작한다

- **상태**: 승인
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-002(이슈 #13), 입력 R0-04([`docs/reports/r0-querydsl.md`](../reports/r0-querydsl.md)), 기획서 §9-2·§18 Q7, 작업진행.md A1·E4-1

## 맥락
- 기획서 §9-2는 "Java 21 LTS(25 LTS도 가능, R0의 ADR-002로 확정)"이고, 사용자 결정 Q7의 기본값은 21이다.
- 백엔드 골격(R0-07)과 CI(R0-08)를 만들기 전에 버전을 정해야 한다. Gradle toolchain, CI의 JDK, 정적 분석·커버리지 도구의 판이 이 버전을 따른다.
- 두 후보 모두 LTS다. JDK 21 GA는 2023-09-19, JDK 25 GA는 2025-09-16이다(OpenJDK GitHub 저장소 `openjdk/jdk`의 `jdk-21-ga`·`jdk-25-ga` 태그 날짜, 2026-11-23 확인).
- Spring Boot 4.1.3은 "Java 17 이상, Java 27까지 호환"이라고 적는다(Spring Boot 공식 문서 System Requirements, 2026-11-23 확인). 그러므로 Boot만 보면 21과 25 모두 된다.
- R0-04는 Boot 4.1.3 + Hibernate 7.4 + QueryDSL 포크 7.7 + MySQL 8.4 조합을 **Java 21에서** 빌드하고 동작을 확인했다. 25에서는 확인하지 않았다.

## 결정
**Java 21 LTS로 시작한다.** 패치판은 최신을 쓴다(이 PC는 21.0.12).
- 언어 수준과 컴파일 대상은 21이다. 25 이후의 언어 기능은 쓰지 않는다.
- 가상 스레드는 지금 계획에 없다. 쓰기로 하면 이 ADR을 다시 연다(재검토 조건).

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| Java 25 LTS | 최신 LTS다. JDK 24에 들어간 JEP 491(Synchronize Virtual Threads without Pinning)을 포함하므로, `synchronized` 안에서 막혀도 가상 스레드가 플랫폼 스레드를 붙잡지 않는다 | 이 이점은 가상 스레드를 쓸 때만 의미가 있는데 계획에 없다. R0-04 조합을 25에서 다시 확인해야 하고, ArchUnit·JaCoCo·Spotless 등의 25 지원 판도 하나씩 확인해야 한다. 얻는 것보다 확인할 것이 많다 |
| Java 17 LTS | Boot 4.1의 최소 버전이다 | 21보다 오래된 LTS를 고를 이유(옛 운영 환경 호환)가 이 프로젝트에 없다. R0-04도 21에서 확인했다 |

JEP 491이 JDK 24에 들어갔다는 것은 OpenJDK 저장소에서 구현 커밋(`78b80150e0`, "8338383: Implement JEP 491")이 `jdk-24-ga`에는 있고 `jdk-23-ga`에는 없음으로 확인했다(2026-11-23). openjdk.org와 oracle.com 문서는 이번 확인 도구에서 열리지 않았다.

## 결과
- **얻는 것**: R0-04에서 검증한 조합을 그대로 쓴다. 이 PC에 설치된 JDK로 바로 시작한다. 함께 쓰는 도구의 판을 고를 때 걱정이 적다.
- **감수하는 것**: 25의 개선(JEP 491 등)을 쓰지 못한다. 나중에 25로 올리면 그때 빌드·테스트를 다시 확인해야 한다.

## 보안·개인정보 영향
- 개인정보에는 영향이 없다(실행 환경 버전만 정한다).
- 보안은 버전보다 패치판이 중요하다. 21의 최신 패치판을 쓰고, R0-08의 공급망 검사(Dependabot 등, A5-12)로 함께 관리한다.

## 강제
- **예정(R0-07)**: Gradle toolchain `languageVersion = 21`. 다른 JDK로 Gradle을 실행해도 21로 컴파일한다.
- **예정(R0-08, CI)**: CI의 `setup-java`를 21로 고정한다. CI가 JDK 21로 빌드하는지 로그로 확인한다.

---

## 재검토 조건
- 가상 스레드를 쓰기로 할 때(예: 부하 테스트에서 스레드 풀이 병목으로 나올 때). 그때는 JEP 491 때문에 25를 먼저 검토한다.
- 함께 쓰는 라이브러리(Boot, Hibernate, QueryDSL 포크 등)가 21 지원을 끝낼 때.

## 논의 기록
- AI 제안: 21. 25만 주는 이점은 가상 스레드를 쓸 때 생기는데 계획에 없고, 21은 R0-04에서 이미 검증했다. 재검토 조건에 "가상 스레드를 쓰기로 할 때"를 둔다.
- 사용자: 21로 정했다(2026-11-23, E4-1 Q7).
