# ADR-004. 주문 상태 머신

- **상태**: 제안
- **날짜**: 2026-11-23
- **결정자**: 사용자 / **작성자**: Claude Code(Claude Opus 5.5)
- **관련**: 작업 ID R0-05-004(이슈 #23), E05·E45·E47·E49, 불변식 I6, 기획서 §6-3, 작업진행.md B3·B5·B6·B7·A5-3, 검토보고서 RP-4, ADR-001

## 맥락
- 기획서 §6-3과 B3에 상태 그림 초안이 있다. 상태 이름과 "그 상태를 주문에 둘지 다른 기록에 둘지"는 ADR에서 확정하기로 했다. 결제 시도 상태는 ADR-006a가 맡는다.
- 규칙은 정해져 있다. 전이 규칙은 코드 한 곳에서만 정의한다. 허용되지 않은 전이는 거부한다. 종결 상태(`EXPIRED`·`CANCELLED`)는 되살리지 않는다(A5-3).
- 검토 질문 RP-4: 취소 진행 상태를 주문 상태로 둘지, 별도 취소 요청 엔티티의 상태로만 둘지.
- 상태를 바꾸는 주체가 여러 모듈이다(payment·claim·shipping·order 배치, ADR-001). 이들이 동시에 같은 주문을 건드린다(E05 예약 만료와 결제, E45 취소와 출고).

## 결정
**R1 주문 상태는 아래 10개이고, 허용 전이표 하나가 order 모듈에만 있다. 모든 전이는 주문 행을 잠근 뒤 `Order`의 도메인 메서드로만 일어나고, 같은 트랜잭션에서 상태 이력을 한 줄 남긴다.**

**상태**: `PAYMENT_PENDING`, `CONFIRMING`, `PAID`, `EXPIRED`(종결), `CANCEL_REQUESTED`, `CANCELLED`(종결), `PREPARING`, `SHIPPED`, `DELIVERED`, `PURCHASE_CONFIRMED`

- **`CREATED`는 두지 않는다.** 주문 생성, 재고 예약, 결제 시도 생성은 한 트랜잭션이다(B5-1). 그래서 커밋된 주문은 언제나 `PAYMENT_PENDING`이고, `CREATED`는 아무도 볼 수 없는 상태다. **B3·기획서 §6-3 그림을 바꾸는 결정이다.**

**허용 전이표**

| 현재 → 다음 | 일으키는 쪽 | 조건 |
|---|---|---|
| (생성) → `PAYMENT_PENDING` | payment(주문·시도 생성 유스케이스) | B5-1 |
| `PAYMENT_PENDING` → `CONFIRMING` | payment(성공 URL) | 현재 시도일 때만. 재예약 성공 시에만(B5-3-2) |
| `CONFIRMING` → `PAID` | payment(승인 결과, 웹훅, 복구 작업자) | 승인 완료 |
| `CONFIRMING` → `PAYMENT_PENDING` | payment | 명확한 실패. 새 시도 가능 |
| `PAYMENT_PENDING` → `EXPIRED` | order(주문 만료 배치) | 만료 시각 경과. `CONFIRMING`은 만료하지 않는다(E05) |
| `PAID` → `CANCEL_REQUESTED` | claim(고객 취소 요청) | 본인 주문(S12). 이때부터 출고 준비가 막힌다(E45) |
| `CANCEL_REQUESTED` → `CANCELLED` | claim(PG 취소 결과, 복구 작업자) | PG 취소 성공 |
| `CANCEL_REQUESTED` → `PAID` | claim | PG 취소의 명확한 실패 |
| `PAID` → `PREPARING` | shipping(운영자 출고 준비) | E45 |
| `PREPARING` → `SHIPPED` | shipping(송장 발번) | |
| `SHIPPED` → `DELIVERED` | shipping(배송 상태 폴링) | |
| `DELIVERED` → `PURCHASE_CONFIRMED` | order(고객 수동 확정, R1) | 자동 확정 배치는 E24와 함께 나중에 |

**전이 규칙**
1. **잠금**: 전이는 주문 행을 `SELECT … FOR UPDATE`로 읽은 뒤 한다. 재예약·예약 해제처럼 다른 행도 잡는 경우의 잠금 순서는 ADR-005가 정한다.
2. **한 곳**: `OrderStatus`에 허용 전이표를 두고, 상태를 바꾸는 방법은 `Order`의 도메인 메서드뿐이다. 상태 필드에 setter를 두지 않는다(ADR-010).
3. **멱등**: 이미 목표 상태면 아무것도 바꾸지 않고 "바뀌지 않음"을 돌려준다. 부수 효과(취소 요청 기록, 재고 복구)는 실제로 바뀌었을 때만 일어난다.
4. **허용되지 않은 전이**: 사용자·운영자 요청이면 409(상태 충돌, ADR-010 오류 형식)로 거부한다. 외부 신호(웹훅, 배송 폴링, 복구 작업자)면 무시하고 경고 로그를 남긴다. 역순 도착 방어다(B7). 단, 종결 주문에 승인이 도착한 경우는 무시하지 않고 결제 시도 쪽에서 보상 취소한다(ADR-006a·b).
5. **이력**: `order_status_history`(주문 ID, 이전·다음 상태, 원인, 주체 유형·ID, 시각)에 추가만 한다. 불변식 I6 자동 검사(R1-18)가 이 표를 읽는다.

**RP-4에 대한 답: 취소 진행은 둘 다에 둔다. 역할이 다르다.**
- 주문의 `CANCEL_REQUESTED`는 **잠금 역할**이다. 출고 준비(`PAID → PREPARING`)와 같은 주문 행에서 조건부로 경쟁하므로 한쪽만 이긴다(E45).
- claim의 취소 요청 기록은 **세부 기록**이다. 요청 시각(환급 기한 기산점, B6), 멱등키 `cancel-{cancelRequestId}`, PG 결과를 담는다. 상태 전이와 같은 트랜잭션에서 만든다.

**R2b로 미루는 것**: `PARTIALLY_CANCELLED`, 반품·교환 상태. 주문상품 단위 클레임이라 주문 상태로 둘지 claim 상태로 둘지는 R2b ADR에서 정한다.

## 검토한 대안
| 대안 | 장점 | 기각 이유 |
|---|---|---|
| 취소 진행을 claim 기록에만 둔다 | 주문 상태가 하나 줄어든다 | 출고 준비가 다른 테이블을 확인해야 한다. 두 테이블에 걸친 경합을 막으려면 잠금이 더 복잡해진다 |
| 조건부 UPDATE(`WHERE status = ?`)로 전이 | 잠금 없이 한 문장으로 끝난다 | 전이 규칙이 SQL 문장마다 흩어져 "코드 한 곳"(A5-3)을 지키기 어렵다. 재예약처럼 같은 트랜잭션에서 다른 일을 해야 하는 전이에는 어차피 잠금이 필요하다(RP-3) |
| 낙관적 잠금(`@Version`) | 잠금 대기가 없다 | 충돌하면 예외 → 재시도 로직이 모든 호출자에게 생긴다. E45처럼 진 쪽을 안내해야 하는 경합에서는 비관적 잠금이 더 단순하다 |
| 상태 패턴(상태마다 클래스) | 상태별 동작을 나눠 둔다 | 상태 10개에 동작은 대부분 "전이 가능 여부"뿐이다. 표 하나가 읽고 테스트하기 쉽다 |
| `CREATED` 유지 | 기획서 그림 그대로다 | 커밋된 데이터에 나타나지 않는 상태다. 전이표와 테스트에 쓸모없는 행이 생긴다 |

## 결과
- **얻는 것**: 상태 규칙이 표 하나로 보이고, 모든 쌍을 테스트로 덮을 수 있다. 경합(E05·E45)은 주문 행 잠금 하나로 직렬화된다. 이력 표로 I6을 자동 검사하고 장애를 추적한다.
- **감수하는 것**: 모든 전이가 주문 행을 잠그므로 같은 주문에 대한 요청은 줄을 선다. 한 주문에 동시 요청이 몰리는 경우는 드물어서 받아들인다. `PREPARING` 뒤에는 고객이 스스로 취소할 수 없다(출고 전 취소는 `PAID`일 때만). 상태 이력 때문에 전이마다 쓰기가 한 번 더 생긴다.

## 보안·개인정보 영향
- 고객 취소(`PAID → CANCEL_REQUESTED`)와 구매확정은 본인 주문인지 검사한 뒤에만 부른다(A5-9 S12). 검사 위치는 ADR-008에서 정한다.
- 운영자 전이(출고 준비 등)는 admin 모듈 진입점으로만 열린다(ADR-001).
- 상태 이력에는 주체 ID만 남기고 이름·연락처는 남기지 않는다.

## 강제
- **예정(R1-08 무렵, 단위 테스트)**: 전이표의 모든 (현재, 다음) 쌍을 시험해 허용된 쌍만 성공하는지, 종결 상태에서 나가는 전이가 모두 실패하는지 확인한다.
- **예정(R1-14, 동시성 테스트)**: 고객 취소와 출고 준비를 동시에 보내 한쪽만 성공하는지 확인한다(E45).
- **예정(R1-18)**: 상태 이력의 모든 행이 전이표 안에 있는지 불변식 검사(I6).
- **예정(R0-06, ArchUnit)**: 엔티티 `@Setter` 금지(ADR-010)로 상태 필드 직접 변경을 막는다.
