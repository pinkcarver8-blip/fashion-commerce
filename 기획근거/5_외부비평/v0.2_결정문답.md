### 3. 가장 크게 바뀌는 두 곳

#### R1 범위
```
v0.1 R1 ─ 기능 13개를 한 번에
┌──────────────────────────────────────────────────────────────┐
│ 회원 │ 카탈로그·필터·검색 │ 장바구니 │ 주문서 │ 재고 예약·원장   │
│ 주문 멱등 │ 결제·웹훅·보상취소 │ 쿠폰 │ 모의 배송 │ 전체·부분취소 │
│ 관리자 화면 │ FE 테스트 │ 보안·불변식 │ README·영상            │
└──────────────────────────────────────────────────────────────┘

v0.2 R1 ─ 구매 여정 하나와 그 실패 경로
 상품 목록·상세 → 장바구니 → 주문 → 재고 예약 → 결제 ─┬─ 성공 → 주문 완료 → 전체취소·환급
                                                        ├─ 실패·이탈 → 예약 해제
                                                        ├─ 타임아웃 → 복구 작업자 → 조회로 확정
                                                        └─ 웹훅 중복·역순 → 멱등 처리
 + CI 녹색 + 불변식 3개 + README

 R2로 이동: 쿠폰, 부분취소, 모의 배송·배송 조회, 클레임 관리자 화면, 필터·검색
```

#### 결제 상태 설계
```
v0.1
 PAYMENT_PENDING ──승인 성공──> PAID
        └──10분 만료·실패──> EXPIRED        (만료 배치가 예약 재고 해제)

v0.2
 PAYMENT_PENDING ──(현재 시도일 때만, 조건부)──> CONFIRMING ──승인──> PAID
        │                                      (paymentKey 저장)
        │                                          └──결과 불명──> UNKNOWN
        │                                                 └─ 복구 작업자가 조회 → PAID 또는 해제
        │                                                    (30분이 지나도 불명이면 운영자에게)
        └──(만료 배치: PENDING일 때만)──> EXPIRED  ← 되살리지 않음

 만료된 주문에 승인된 돈이 있으면 결제 시도 단위로 처리:
   주인 없는 승인 → 취소 요청 → 취소 완료
                             └ 결과 불명 → 운영자 큐
```

v0.2에서 다시 정의하는 불변식은 이렇습니다.
- **예약 재고:** 결과가 확정된 예약은 정확히 한 번 해제되거나 소진된다. 결과가 미확정이면 조회로 해소하고, 상한 시간을 넘기면 알람을 보낸다.
- **결제:** PAID 주문은 성공한 결제 시도 하나와 대응한다. PG의 승인 거래는 모두 내부 결제 시도에 연결되고 금액이 같다. 취소는 별도 원장으로 대사한다.

상태 이름과 그 상태를 주문에 둘지 결제 시도에 둘지는 R0의 ADR에서 확정합니다.

### 5. v0.2로도 해결되지 않는 것
- **대형 커머스의 신입 공고 원문은 여전히 0건입니다.** 정합성을 깊게 파는 건 계속 베팅입니다.
- **같은 모델이라 치우쳤을 가능성은 그대로입니다.** ChatGPT 비평으로 일부 보완했지만, 실제 면접관이나 현직자 피드백을 대신하지는 못합니다.
- **토스 동작 세 가지는 테스트 키로 직접 확인해야 결론이 납니다.** 상태별 조회 응답, 30분을 언제부터 세는지, 위젯 키로 거래 조회가 실제로 되는지입니다.
- **§18의 Q1 목표 회사군과 Q2 첫 지원 시점이 아직 정해지지 않았습니다.** R1을 어디서 자를지가 Q2에 달려 있습니다.

제가 보기에 가장 큰 대가는 두 가지입니다. R1은 작아지지만 쉬워지지는 않는다는 점, 그리고 합의 항목을 재투표 없이 바꾼다는 점입니다. 두 번째가 마음에 걸리시면 바뀌는 세 항목만 세 에이전트에게 재투표를 받을 수 있습니다. 지시하시기 전까지는 아무것도 만들지 않겠습니다.

## 2. 코디네이터 답변

대부분은 맞다고 봅니다. 다만 세 군데는 v0.2 목록이 과하거나 방향이 틀렸고, 제 조사 기준으로 더 중요한 두 가지는 목록에 아예 빠져 있습니다. ChatGPT와 세 번 주고받는 동안 저도 양보를 너무 쉽게 한 부분이 있었습니다.

### 1. 제 조사로 봐도 맞는 변경

**R1 축소.** 맞습니다. 다만 근거는 ChatGPT와 다릅니다.
- 제 조사의 핵심 결론은 "AI로 만든 것을 검증하고 설명할 수 있어야 한다"였습니다. 신입 공고도 "프로젝트 완주", "기술적 판단을 설명"을 반복해서 요구했습니다.
- 그런데 v0.1의 R1은 기능 13개를 한 번에 만듭니다. 바이브 코딩 속도로 13개를 만들면 기능마다 검증과 이해가 얕아집니다. 기획서의 핵심 메시지와 정면으로 충돌하는 구조였습니다.
- 커머스 신입 채용은 공채·인턴 시즌에 크게 의존합니다. 그래서 일찍 공개할 수 있는 정지점이 필요합니다.
- 기간은 신경 쓰지 말라고 하셨지만, 이건 기간 문제가 아니라 순서 문제입니다. 기능은 R2~R3에서 다시 늘어나므로 최종 범위는 줄지 않습니다.

**결제 TTL과 법령 수정.** 선택의 문제가 아니라 v0.1의 오류였습니다.
- 정상적으로 결제하는 중에도 예약이 풀릴 수 있는 설계는 버그입니다.
- 환급 기한의 기산점이 빠진 것도 사실 오류입니다.
- 이 부분은 ChatGPT의 비평이 실제로 가치가 있었습니다.

**주문 모델 2단 전환.** 맞다고 봅니다.
- 3단 구조가 필요한 건 R4부터인데, 그때까지 판매자가 하나뿐이라 3단 구조는 모든 조회를 복잡하게 만들 뿐입니다.
- R3에서 멈추면 영원히 필요 없는 구조입니다.

**나머지(부하 기준선, QueryDSL 확인, 표현 정정).** 비용이 거의 없고 정확해지므로 이견이 없습니다.

### 2. 과하다고 보는 것: 제가 너무 양보한 부분

**① 결제 복구 설계를 R1에 전부 넣는 것**
- 세 번의 라운드에서 ChatGPT가 구멍을 하나 찾으면 제가 막았고, 그때마다 설계가 커졌습니다. 이런 비평은 구조적으로 끝이 없습니다. 분산 시스템의 예외 상황은 무한하고, 비평하는 쪽은 언제나 하나를 더 찾을 수 있습니다.
- v0.1은 일부러 "실시간 경로는 기본만 처리하고, 남는 불일치는 일일 대사로 잡는다"는 구조였습니다. 실제 커머스·PG 운영도 대사를 최후 방어선으로 둡니다. 이 원칙은 맞았습니다.
- 그리고 제 조사에서 결제 정합성의 깊이는 신입 요건이 아니라 베팅이었습니다(신입 공고 36건 중 PG사 1건). 그러니 R1의 중심을 베팅으로 가득 채우는 건 균형이 맞지 않습니다.
- 제 권고는 이렇게 나누는 것입니다.

| 단계 | 내용 | 이유 |
|---|---|---|
| R1: 정합성 핵심 | 예약 TTL 기산점 수정, 조건부 상태 전이, 승인 전 paymentKey 저장, 같은 멱등 키로 재시도하고 조회로 확정, 단순 복구 작업자 | 없으면 버그가 되는 것들 |
| R2: 복구 완성 | 보상 취소 실패 경로, 운영자 큐, 응답별 조치표 전체 | R2에는 Toxiproxy가 있어서 이 상황을 실제로 재현하고 테스트할 수 있음 |

**② 차별화 축 ④에서 "생산성"을 지우는 것**
- 이건 제가 틀리게 양보했습니다. 제 조사에서 AI 생산성은 시장이 실제로 요구하는 것이었습니다. 스타트업 공고는 "AI 도구로 빠르게 실서비스까지"를 반복했고, 무신사와 컬리는 AI 도구 활용 자체를 전형에서 평가합니다.
- ChatGPT가 지적한 건 측정 방법이 엉터리라는 점이지, 속도를 주장하지 말라는 게 아니었습니다. 지표만 바꾸면 됩니다.
  - 버릴 것: 오류 건수, 통과율, 비율 통계처럼 직접 세서 보고하는 숫자
  - 남길 것: git·CI 기록으로 객관적으로 보이는 일정. 예를 들어 "이 기능을 며칠 만에 설계부터 배포까지 했다"를 비교 주장 없이 사실로만 적습니다.
  - 가장 강한 증거: 병행 트랙 ②의 시간 제한 과제입니다. 생산성은 포트폴리오에서 주장하기보다 채용 과제에서 회사가 직접 보는 쪽이 강합니다.
- 그래서 축 ④는 원래 합의대로 "AI 활용 생산성·검증 프로세스"로 두는 게 맞다고 봅니다.

**③ 표제 변경**
- 틀린 지적은 아니지만 중요도가 낮습니다. "운영 가능한"은 "운영했다"가 아니라 "운영할 수 있다"는 뜻이라, 운영 증거가 생기는 R2~R3부터는 써도 됩니다.
- 그러니 표제는 릴리스마다 실제 증거에 맞추면 충분합니다.

### 3. 목록에 없지만 더 중요한 것

**① Q3(R1 클라우드 리허설)를 다시 검토할 때입니다.**
- 제 조사에서 가장 근거가 강했던 건 배포·운영 경험입니다(FE 공고 7/11, BE 7~9/13). 그런데 사용자 조건 때문에 이 증거가 R2~R3로 밀려 있었습니다.
- R1이 작아지면 첫 정지점에 이 증거가 없다는 게 더 큰 약점이 됩니다. 반대로 리허설 부담은 더 작아집니다. 그래서 지금은 R1 끝에 짧게 배포해 보는 쪽을 권합니다.
- 단, AWS 크레딧 기간이 가입 시점부터 흐르는 문제가 있어서 Q2와 묶어서 판단해야 합니다.
  - 첫 지원이 6개월 안이면 리허설을 권합니다.
  - 그보다 멀면 계정 없이 미루거나, Lightsail을 1~2주만 유료로 쓰는 쪽을 권합니다. 비용은 약 1만 원입니다.

**② 세 번의 비평이 모두 프로젝트 내부 설계에만 쏠렸습니다.**
- 제 조사에서 합격을 가장 크게 좌우한 관문은 코딩테스트였습니다. 무신사 신입 전형은 1차 코딩테스트에서 약 76%가 탈락했습니다.
- 그런데 기획서 §14의 병행 트랙은 "1:1:1"이라는 비율만 있고 마일스톤이 없습니다.
- 결제 상태 설계를 세 번 다듬는 동안, 실제 탈락 위험이 가장 큰 부분은 한 번도 다뤄지지 않았습니다. v0.2에서 가장 손봐야 할 곳은 사실 여기라고 봅니다. 다만 Q1 목표 회사군 답이 있어야 구체화할 수 있습니다.

### 4. 합의 절차에 대해
제 판단대로 하면, 합의 항목 중 실제로 바뀌는 건 R1 범위와 주문 모델 두 개뿐입니다. 축 ④는 원래 합의대로 둡니다. 두 변경은 ChatGPT의 근거가 아니라 원래 조사 결과로 설명할 수 있어서, §19에 그 근거와 함께 기록하면 충분하다고 봅니다.

정리하면, 제가 권하는 v0.2는 지난번 비교표에서 세 가지를 조정한 것입니다.
1. 결제 복구 설계를 R1과 R2로 나눈다.
2. 축 ④에 "생산성"을 남긴다.
3. Q3와 병행 트랙을 다시 열어 둔다.

결정하시기 전까지는 아무것도 고치지 않겠습니다.

다만 범위가 슬금슬금 다시 늘어나는 건 이런 식으로 시작됩니다. 그래서 순위를 매겼습니다. 하나만 고르라면 1번 FE 품질입니다. 노리시는 직무가 풀스택이라 첫 정지점에서 프론트엔드 증거가 없는 게 가장 큰 구멍이기 때문입니다.

전체 계획에서 아예 빠지는 건 세 가지뿐입니다.

- **AI 오류 건수·통과율 같은 스스로 세는 지표:** 제가 권한 안 기준입니다. 축 ④와 객관적인 일정 기록은 남습니다.

1. **R2까지 가야 13개가 다 생깁니다.** R1에서 멈추면 쿠폰, 부분취소, 필터·검색, 실제 배송조회, 클레임 화면이 없는 상태로 공개됩니다. 그래서 R1에 무엇을 살릴지가 중요합니다.
2. **R2가 무거워집니다.** v0.1 R2에 원래 있던 모니터링, 장애 주입, Outbox, 대사, 반품·교환, 런북, E2E 테스트 위에 R1에서 옮겨 온 기능 6묶음이 얹힙니다. "어느 릴리스에서 멈춰도 성립한다"는 원칙을 R2에도 지키려면, v0.2를 쓸 때 R2를 둘로 나누는 게 맞다고 봅니다.

## 5. 사용자 질문

그럼 v0.2는 v0.1의 R1을 R2로 넘긴 것일뿐 결과는 똑같다고 봐야하는 거네?

## 5. 코디네이터 답변

기능 목록만 보면 맞습니다. R2가 끝나면 거의 같은 기능이 생깁니다. 하지만 결과물은 같지 않습니다. v0.2에는 두 종류의 변경이 섞여 있고, 말씀하신 "넘긴 것"은 그중 한 종류입니다.

### v0.2 = 순서 변경 + 설계 수정

| 종류 | 내용 | 최종 결과에 미치는 영향 |
|---|---|---|
| **순서 변경** (넘긴 것) | 쿠폰, 부분취소, 필터·검색, 실제 배송조회, 클레임 화면, 보상 취소 실패 경로를 R1에서 R2로 옮김 | R2가 끝나면 v0.1과 같아짐 |
| **설계 수정** (바뀐 것) | 예약 TTL 기산점 버그 수정, 결제 시도 ID·조건부 상태 전이·paymentKey 선저장, 불변식 재정의, 주문 2단 구조와 R4 이관, 환급 기한 기산점(제18조 ② 3호), 부하 측정 방식, QueryDSL 빌드 확인, 본인 주문 권한 검사와 취소·출고 경합 추가, 과장된 표현 정정 | 최종 결과가 달라짐. v0.1대로 R2까지 가면 결제 도중 예약이 풀리는 버그와 모호한 불변식이 그대로 남음 |

중요한 건 **이 두 종류를 분리할 수 있다는 점**입니다. 설계 수정은 버그와 오류를 고치는 것이라, 어떤 순서로 가든 반드시 해야 합니다. 그래서 "v0.1의 순서는 그대로 두고 설계만 고치는" 선택지도 가능합니다.

### 그렇다면 순서 변경은 의미가 있나
의미는 있지만 조건부입니다.

| 상황 | 순서 변경의 가치 |
|---|---|
| 첫 지원이 가깝거나 아직 모름 | **큼.** R1에서 멈춰도 공개할 수 있는 포트폴리오가 일찍 생깁니다 |
| 첫 지원이 멀고, R3까지 확실히 간다 | **작음.** 남는 이점은 두 가지뿐입니다. 하나는 검증 관문이 13개 다음이 아니라 7개 다음에 한 번 더 온다는 점입니다. 다른 하나는 쿠폰과 부분취소를 함께 만들어서 다시 만들 일이 없다는 점입니다 |

### 그래서 실제 선택지는 둘입니다

| | A. v0.1 순서 + 설계 수정 | B. v0.2 전체 |
|---|---|---|
| 최종 결과 | 같음 | 같음 |
| 첫 공개 가능 시점 | 늦음(기능 13개 뒤) | 빠름(약 7개 뒤) |
| R2 무게 | 원래대로 | 무거워서 둘로 나눠야 함 |
| 맞는 경우 | 첫 지원이 멀고 R3까지 확실히 갈 때 | 지원 시점이 가깝거나 불확실할 때 |

저는 여전히 **B를 권합니다.** Q2(첫 지원 시점)에 아직 답이 없어서, R1에서 멈춰야 할 가능성을 배제할 수 없기 때문입니다. B의 대가는 R2를 나누는 정도로 작습니다. 그래서 B는 일찍 지원하게 될 경우에 대비한 싼 보험에 가깝습니다.

다만 첫 지원이 멀고 R3까지 갈 게 확실하다면 A도 똑같이 좋은 선택입니다. 그때는 순서 변경에 큰 의미를 둘 필요가 없습니다.

파일은 그대로입니다.
