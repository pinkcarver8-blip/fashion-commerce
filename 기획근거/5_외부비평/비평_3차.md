# 외부 비평 3차 (ChatGPT, 2026-11-07)

> 세션 기록(2026-11-07)에서 원문 그대로 옮겼다(제목 수준만 한 단계 낮췄다). 비평문은 사용자가 붙여 넣은 글이고, 답변은 코디네이터(Claude)의 답이다. 이 기록을 바탕으로 쓴 결과는 `프로젝트_기획서_v0.2.md` §19-6·§19-7에 있다.

## 사용자가 붙여 넣은 비평

아래 글은 네 반격글에 대한 ChatGPT의 재반격이야. 읽어보고 반박하고 싶은 부분 있으면 공격해.

---

이번 반격은 앞선 것보다 정확합니다. 제가 고쳐야 할 지적도 있습니다. 특히 k6 환경에 대한 제 비판은 잘못 읽었고, 법령은 R0에 원문 확인이 있는데 제가 놓쳤습니다. 컨셉도 채용에 유리하다는 근거로 정당화된다고 과장했습니다. 최신 프롬프트가 구버전과 다르다는 설명도 반영하겠습니다. 제 이전 프롬프트 비평은 첨부된 구버전에만 해당합니다.

그래도 이 반격문에는 중요한 사실 오류 하나와 설계상 남은 구멍이 있습니다.
1. “거래 조회 API도 위젯 키로 되는지 불명”은 공식 문서와 다릅니다
Toss API 키 문서는 주문서형·결제창형 키인 test_gsk/`live_gsk`가 paymentKey 조회, 거래 조회, 정산 조회를 지원한다고 명시합니다. gsk로 호출할 수 없는 것은 별도의 orderId 결제 조회 API입니다. 따라서 이 반격문의 첫 번째 “새 제약”은 절반만 맞습니다. orderId 조회 제한은 맞지만, 거래 대사까지 test_sk가 필요한지는 불명이라는 주장은 공식 문서로 해소됩니다. Toss API 키 안내, 결제·거래 조회 API

또 paymentKey 조회 API는 문서상 승인된 결제를 조회하는 API입니다. 조회 결과가 없다는 사실만으로 승인 여부가 확정됐다고 처리하면 안 됩니다. “승인 성공은 조회로 확인, 미확정은 만료 상태나 거래 기록을 확인”처럼 각 결과의 의미와 다음 조치를 정해야 합니다. Toss Core API
2. 30분은 운영자 에스컬레이션 기준으로 쓸 수 있지만, 확정 시각으로 보장하면 안 됩니다
Toss 문서는 한 곳에서 인증 뒤 승인 API를 호출해야 하는 10분을 설명하고, Core API에서는 30분이 지나면 EXPIRED가 된다고 설명합니다. 서로 다른 시계라는 해석은 타당합니다. 다만 반격문도 인정하듯 30분을 언제부터 세는지는 확인이 필요합니다. 그러므로 “30분 뒤면 항상 DONE 또는 EXPIRED로 확정된다”는 보장으로 쓰기보다, 30분은 우선 알림·운영자 확인의 기준으로 두고 실제 상태를 조회해 처리하는 편이 안전합니다. 결제 흐름 안내, Core API 상태 설명

10분도 단순히 “재시도 가능한 시간”이라고만 부르면 부족합니다. 첫 승인 요청의 결과가 타임아웃으로 불명확하면 같은 결제 시도와 같은 멱등 키로 재시도해야 합니다. 새 키로 다시 승인하거나 승인 여부를 확인하지 않고 재시도하는 경우는 별도 실패 시나리오로 검증해야 합니다.
3. 만료 주문 결제를 자동 취소한다는 원칙은 맞고, 취소 실패 경로가 남았습니다
“만료 주문은 되살리지 않고 승인된 결제는 보상 취소한다”는 원칙은 명확합니다. 하지만 보상 취소도 PG 호출이므로 타임아웃·서버 종료·중복 웹훅이 생길 수 있습니다. 취소 요청을 먼저 기록하고, 동일한 멱등 키로 재시도하며, 취소가 끝나기 전에는 배송을 막아야 합니다. 최종 취소 여부가 계속 불명확하면 COMPENSATION_PENDING 같은 상태와 운영자 처리 큐가 필요합니다. “자동 취소하고 알람”만으로는 완료 조건이 아닙니다.
4. 같은 주문에 예약을 다시 잡는다면 결제 시도와 예약을 묶어야 합니다
주문이 PAYMENT_PENDING으로 남아 있고 재고 예약만 만료된 경우, 같은 주문에서 다시 예약하는 설계는 가능합니다. 다만 이전 결제 시도의 늦은 콜백이 새 예약에 붙지 않도록 결제 시도 ID와 예약 ID 또는 예약 세대를 연결해야 합니다. 새 예약의 SKU·수량이 기존 주문 내용과 같고, 금액도 최초 결제 요청 때 저장한 값과 일치할 때만 승인으로 넘어가야 합니다. 이 구분이 빠지면 “주문은 부활하지 않는다”는 규칙만으로는 늦은 성공 URL과 새 예약의 연결을 막지 못합니다.
5. AI PR 기록은 전체 기록을 빠짐없이 남기는 절차가 있어야 의미가 있습니다
PR 전체 수와 AI 사용 기록을 함께 공개하면 일부 성공 사례만 골랐다는 의심을 줄이는 데 도움이 됩니다. 다만 전체 기록의 완전성은 숫자 공개만으로 증명되지 않습니다. PR 템플릿에 AI 사용 여부와 검증 결과를 필수로 기록하고, 그 기록을 생산성 비율로 포장하지 않는다는 선을 분명히 하면 좋겠습니다. 이 부분은 반격문이 제 지적을 잘 보완했습니다.

최신 프롬프트에 관한 평가는 구버전만 보고 이어가지 않겠습니다. 현재 작업 폴더의 prompt.md는 프로젝트 프롬프트가 아니라 비평문으로 덮여 있습니다. 사용자가 말씀하신 최신 지시가 별도로 있다면, 그 내용이 있어야 최신본에 대한 비평을 판단할 수 있습니다.

## 코디네이터 답변

이번에는 제가 틀린 게 하나 분명히 있습니다. 나머지 지적 다섯 개 가운데 셋은 일부를 반박하고, 둘은 받아들입니다. 파일은 그대로입니다.

### 인정: 거래 조회 API는 제가 틀렸습니다
- 토스 API 키 문서를 직접 열어 보니, 결제위젯 키(`gsk`)로 호출할 수 있는 API에 "결제 승인, 결제 취소, paymentKey로 결제 조회, 거래 조회, 정산 조회"가 적혀 있습니다.
- 저는 레퍼런스 페이지 한 곳만 보고, 거기에 언급이 없다는 이유로 "문서에 나오지 않는다"고 단정했습니다. 한 페이지에서 확인하지 못한 걸 문서 전체에 없는 것처럼 쓴 실수입니다.
- 결과적으로는 좋은 소식입니다. 결제위젯을 계속 써도 일일 대사가 가능합니다. 남는 제약은 orderId 조회 하나뿐이라서, "`CONFIRMING`으로 바꿀 때 paymentKey를 같은 트랜잭션에 저장한다"는 규칙 하나로 해결됩니다.
- paymentKey 조회에 대한 경고도 맞습니다.
  - 문서 설명은 "승인된 결제를 paymentKey로 조회합니다"인데, 같은 문서에 "실패한 결제를 조회할 때 확인할 수 있습니다"라는 필드 설명도 있어서 서로 엇갈립니다.
  - 그래서 응답마다 다음 조치를 표로 정하겠습니다. 응답은 승인 완료(DONE), 인증만 끝남(IN_PROGRESS), 만료(EXPIRED), 중단(ABORTED), 결과 없음(404), 타임아웃 여섯 가지입니다.
  - 이 표는 R0에서 테스트 키로 실제 응답을 확인해 채웁니다. 판단이 안 서는 경우에는 거래 조회를 두 번째 근거로 씁니다.

### 반박

**① "30분을 확정 시각으로 보장하면 안 된다"**
- 저는 보장으로 쓰지 않았습니다. 지난 답변에 "30분이 지나면 최종 상태여야 하고, 그래도 조회가 실패하면 운영자에게 넘긴다", "언제부터 세는지는 테스트 키로 확인한다"고 적었습니다. 30분은 운영자에게 넘기는 기준이었고, ChatGPT의 제안과 같습니다.
- 다만 소제목에 "확정되는 시점"이라고 쓴 표현은 오해를 살 만했습니다. 그 부분만 인정합니다.

**② "10분 안의 재시도는 같은 멱등 키로 해야 한다"**
- 이미 기획서에 있습니다.
  - 288행: 모든 POST 요청에 멱등 키를 붙인다.
  - 339행(E09): 같은 멱등 키로 재시도하고, 409를 처리하고, 결제 조회로 상태를 확정한다.
- 새 구멍이 아닙니다. 다만 "새 키로 재시도했을 때"를 일부러 실패시키는 테스트로 넣자는 건 좋은 제안이라 받아들입니다.

**③ 보상 취소가 실패하는 경로**
- 핵심은 받아들입니다.
  - 취소 요청을 먼저 기록한 뒤 호출합니다.
  - 같은 멱등 키로 재시도합니다. 취소 API의 멱등 키는 "중복 취소 없이 안전하게 처리된다"고 문서에서 확인했습니다.
  - 그래도 결과가 불명확하면 운영자 처리 큐로 보냅니다.
- 두 부분은 반박합니다.
  - **"취소가 끝나기 전에 배송을 막아야 한다"는 이미 막혀 있습니다.** 만료된 주문은 상태 머신에서 출고 준비(`PREPARING`)로 갈 수 없습니다. 출고 준비로 갈 수 있는 건 결제 완료(`PAID`) 주문뿐입니다.
  - **`COMPENSATION_PENDING`을 주문 상태로 두면 안 됩니다.** "만료된 주문은 되살리지 않는다"는 원칙과 충돌합니다. 이 상태는 결제 시도에 둬야 합니다.
    - 주문은 `EXPIRED`로 그대로 둡니다.
    - 결제 시도는 "주인 없는 승인 → 취소 요청 → 취소 완료"로 흐릅니다.
    - 취소 결과가 계속 불명확하면 결제 시도를 "취소 결과 불명" 상태로 두고 운영자 큐로 보냅니다.

**④ "결제 시도와 예약 세대를 묶어야 한다"**
- 늦게 도착한 콜백이 새로 잡은 예약에 붙으면 안 된다는 문제 제기는 맞습니다. 하지만 "예약 세대"라는 새 개념 없이 규칙 두 개로 막을 수 있습니다.
  1. **주문은 현재 결제 시도 하나만 가리킵니다.** `CONFIRMING`으로 바꾸는 조건에 "현재 시도 ID가 일치할 것"을 넣습니다. 그러면 이전 시도의 늦은 성공 콜백은 `CONFIRMING`으로 갈 수 없고, 승인 API도 호출되지 않습니다.
  2. **재고를 다시 잡는 일은 이긴 시도의 `CONFIRMING` 전이 안에서만 합니다.** 주문 상품은 생성 시점 그대로 바뀌지 않으므로 SKU와 수량이 기존 주문과 달라질 수 없습니다. 금액은 원래 흐름(6-5의 3단계) 그대로, 결제 시도마다 저장한 값과 대조합니다.
- 이 방식에도 대가가 있습니다. 고객이 이전 탭에서 결제를 마치면 그 결제는 승인되지 않고 실패 안내를 받습니다. 정합성을 편의보다 앞세운 선택이고, ADR에 그렇게 기록하겠습니다.
- ChatGPT가 든 조건(SKU·수량·금액 일치)은 이 설계에서 자동으로 지켜지지만, 정말 지켜지는지 테스트로 확인하겠습니다.

### 받아들이는 것
- **AI 기록의 완전성:** 맞습니다. 숫자를 공개하는 것만으로는 기록이 빠짐없다는 증명이 안 됩니다. 여기에 하나를 더하겠습니다. PR 템플릿의 "AI 사용 여부·검증 결과" 칸이 비어 있으면 CI가 PR을 실패시키게 합니다. 그러면 완전성을 커밋 이력으로 확인할 수 있습니다. 생산성 비율로 포장하지 않는다는 원칙도 그대로 유지합니다.
- **최신 프롬프트 평가 유보:** 반박할 게 없습니다. ChatGPT가 최신 지시를 봐야 한다면, 대화 중에 추가로 주신 지시 원문을 여기에 텍스트로 정리해 드릴 수 있습니다. 파일은 만들지 않습니다.

### 비평 라운드를 계속할지에 대한 제 의견
이번 라운드에서 남은 차이는 토론으로 정할 수 없고, 테스트 키로 직접 호출해 봐야 결론이 나는 것들입니다.
- paymentKey 조회가 상태별로 어떤 응답을 주는가
- 30분을 언제부터 세는가
- 위젯 키로 거래 조회를 실제로 호출할 수 있는가

비평을 한 번 더 받아도 얻을 게 많지 않다고 봅니다. 이 세 가지를 R0의 확인 항목으로 넘기고, 지금까지 합의된 수정을 v0.2에 반영하는 단계로 가시길 권합니다. 결정은 사용자께서 하시고, 지시하시기 전까지는 아무것도 고치지 않겠습니다.
