- 작성일: 2026-11-07 (모든 채용공고·검색 건수·요금은 이 날짜에 확인한 값)

## 0. 조사 개요

### 0-1. 조사 방법
1. WebSearch(검색 결과 요약)와 WebFetch(본문 직접 열람)를 함께 썼습니다. 수치를 인용한 자료는 가능한 한 원문을 열었습니다.
2. 채용 시장은 세 층으로 나눠 봤습니다. (a) 플랫폼 키워드 검색 건수(사람인, 잡코리아의 2026-11-07 스냅샷) (b) 실제 공고 원문(무신사, 컬리, F&F, 와이톤, 도이치모터스, 모든세븐) (c) 플랫폼 리포트, 기사, 공공기관 보고서.
3. 레퍼런스 사이트는 각 사 기술 블로그 원문을 우선했습니다(컬리, 올리브영, 우아한형제들, Shopify, Amazon). 열람이 막힌 곳(쿠팡 Medium, 무신사 기술블로그)은 검색 요약과 채용공고로 보완했습니다.
4. PG와 택배 연동은 공식 개발 문서(토스페이먼츠, 포트원, 스윗트래커, CJ대한통운 안내)를 기준으로 했습니다.
5. 같은 주제의 자료끼리 수치를 맞대어 보고, 일치·충돌을 표시했습니다.

### 0-3. 조사의 한계
- **키워드 검색 건수의 질이 낮습니다.** 사람인·잡코리아의 "통합검색" 건수에는 비개발 공고, 교육과정 광고, 중복 공고가 섞입니다(예: 잡코리아 "바이브 코딩" 1페이지 20건 중 개발 직무는 6건 [S7]). 상대 비교용으로만 썼습니다.
- **원티드, 점핏, 프로그래머스 커리어, 로켓펀치, 링크드인은 목록을 읽지 못했습니다**(JS 렌더링). 원티드는 리포트와 개별 공고 원문으로 보완했지만, 나머지 플랫폼은 사실상 빠졌습니다.
- **외주 플랫폼 데이터가 얇습니다.** 위시켓(목록 1페이지, 매거진 2편), 크몽(보도 1건)만 확인했습니다. 이랜서, 프리모아(인증서 오류로 열람 실패), 숨고는 확인하지 못했습니다.
- **플랫폼 자체 발표가 많습니다.** 원티드, 잡코리아, 크몽, 위시켓 수치는 자사 데이터이고 홍보 목적일 수 있습니다.
- **레퍼런스 사이트의 실제 화면(UI)을 직접 돌아보지 않았습니다.** 페이지 흐름·사용자 여정은 기술 블로그, Baymard 연구, 채용공고 설명으로 재구성했습니다.
- **NCP 요금, RDS 스토리지·ALB·EBS 서울 단가는 공식 표에서 확인하지 못했습니다.** 해당 수치는 "미확인" 또는 "가정"으로 표시했습니다.
- **기술 블로그는 성공 사례 위주입니다.** 일부는 2018~2021년 글이라 현재 구조와 다를 수 있습니다.

### 나-2. 이번 프로젝트에 적용할 구체적 제안 3가지

**제안 N-1. 탐색·전시 계층을 "카테고리 트리(표시용) + 속성 facet(검색 인덱스) + 읽기 모델"로 분리한다**
- 내용: 카테고리는 사람이 탐색하는 트리(대·중·소)로 두고, 필터는 상품 속성(브랜드, 사이즈, 색상, 가격대, 소재 등)을 검색 인덱스의 facet으로 둡니다. 목록·상세·검색은 읽기 모델(캐시, OpenSearch)에서 서빙하고, 가격·재고·판매상태는 주문서 진입과 주문 시점에 원본 DB로 재검증합니다(배민 Zero Payload 원리).
- 근거: 쿠팡 카탈로그·택소노미 [S102], 배민스토어 CQRS [S110], 올리브영 품절 → OpenSearch [S107], Baymard 상품 리스트 이탈률 차이 [S118].
- 포트폴리오 포인트: "목록은 캐시여도 되지만 결제 금액은 캐시면 안 된다"는 경계를 설계 문서와 테스트로 보여줍니다.

**제안 N-2. 거래 계층을 "주문 상태 머신 + 재고 3계층 + 멱등·웹훅·대사"로 설계하고, 체크아웃은 폼 요소를 최소화한다**
- 내용: 재고를 판매가능재고(가상재고), 예약재고(결제 대기 hold, TTL), 물리재고(입고·출고)로 나눕니다. 주문은 명시적 상태 머신(생성 → 결제대기 → 결제완료 → 출고준비 → 배송중 → 배송완료 → 구매확정, 분기: 취소·부분취소·반품)으로 관리합니다. 모든 외부 호출(PG)에 멱등키를 쓰고, 웹훅은 서명 검증 후 재조회하며, 매일 PG 거래와 내부 주문을 대사합니다. 체크아웃 화면은 Baymard 기준(폼 요소 12개 안팎)을 목표로 합니다.
- 근거: 컬리 VSMS 정렬 잠금 [S103], 우아한 선물하기 [S109], 올리브영 이중 카운터 [S106], Amazon 멱등 API [S117], 토스페이먼츠 멱등키·웹훅 [S130][S132], Baymard 체크아웃 [S119].

**제안 N-3. 아키텍처는 "모듈러 모놀리스 + Outbox 이벤트 경계"로 시작하고, "사용자 여정 기반 부하테스트"로 목표치를 숫자로 검증한다**
- 내용: 처음부터 MSA로 쪼개지 않습니다. 도메인 모듈(catalog, cart, order, payment, inventory, shipping, settlement)의 경계를 코드로 강제하고, 모듈 간 비동기 통신은 Transactional Outbox로 시작합니다(필요해지면 Kafka로 교체). 부하테스트는 단일 API가 아니라 "탐색 → 상세 → 장바구니 → 주문 → 결제" 여정 시나리오로 하고, 목표는 "가정 피크 × 4"처럼 산식으로 정합니다(컬리 VSMS 방식).
- 근거: Shopify 모듈러 모놀리스 [S114][S115], 쿠팡은 규모가 커진 뒤 MSA 전환 [S101], 컬리 Dual Write 실패 [S104], Zalando 사용자 여정 시뮬레이터 [S116], 컬리 VSMS 목표 산정(피크 300 TPS × 4 = 1,200 TPS) [S103].
- 판단: 신입 1인 프로젝트에서 MSA는 운영 부담만 키우고 "왜 쪼갰는가"에 답하기 어렵습니다. "쪼갤 수 있게 설계했고, 이 지표가 이 값을 넘으면 쪼갠다"는 기준을 문서로 제시하는 편이 설득력이 높습니다.

## (다) "진짜" 이커머스의 돌발 상황과 기술 문제

### 다-1. 먼저 짚을 전제: 흔한 주제는 이미 포화 상태다
- "재고 1개에 동시 주문 → 락 전략"은 인프런 강의 「재고시스템으로 알아보는 동시성이슈 해결방법」 한 강좌의 수강생만 3,654명(수강평 352개)입니다. synchronized, 비관적 락, 낙관적 락, Named Lock, Redis Lettuce·Redisson을 그대로 다룹니다 [S41].
- 커머스 백엔드 부트캠프(루프팩 BE L2, Java·Kotlin 레포가 공개됨 [S42])의 수강생 PR에서는 PG 장애 격리(Resilience4j 서킷브레이커·재시도), 콜백 유실 시 PENDING 고착, 결제 실패 시 재고·쿠폰 복구, 복구 스케줄러가 공통 과제로 보입니다 [S43](미러 사이트 요약, 신뢰도 하).
- **함의(판단):** "락을 걸었다", "서킷브레이커를 달았다"만으로는 차별화가 어렵습니다. 평가받는 지점은 ① 여러 대안을 **같은 조건에서 측정해 비교**했는가 ② 외부 시스템(PG, 택배)이 끼어든 **종단 간 정합성**을 지켰는가 ③ 장애를 **재현·주입**해 복구를 증명했는가 ④ 결정 근거를 **문서(ADR)**로 남겼는가로 옮겨갑니다. 이 판단은 면접관 발언으로 직접 확인한 것이 아니라 포화 정도에서 나온 추론입니다(직접 근거는 약함).

### 다-3. 국내 PG·택배 연동의 실제 방식 요약
- **토스페이먼츠(공식 문서):** 클라이언트 위젯 렌더링 → 결제 요청 전 서버에 orderId·amount 저장 → successUrl로 paymentKey·orderId·amount 수신 → 서버에서 `POST /v1/payments/confirm`(Basic 인증, 시크릿 키) → 10분 안에 승인. 모든 POST API에 `Idempotency-Key`(최대 300자, 15일 유효). 웹훅은 10초 안에 200 응답이 필요하고 최대 7회 재전송 [S130][S131][S132][S133]. 계약 전에는 문서용 테스트 키로 연동해볼 수 있습니다 [S134].
- **포트원 V2(공식 문서):** Standard Webhooks 서명 검증, 최대 5회 재시도, 리다이렉트와 순서 비보장, 웹훅 내용을 그대로 믿지 말고 단건 조회로 재확인 [S135].
- **택배:** 송장 발번은 택배사 계약이 전제입니다(CJ대한통운 Open API는 영업 승인 후 포털 제공 [S137]). 배송 추적은 스윗트래커 같은 추적 API(키 발급 필요, 콜백 방식)를 씁니다 [S136]. **포트폴리오에서는 실제 발번이 불가능하므로 어댑터 패턴 + 모의 택배사로 대체하고, 그 사실을 문서에 명시하는 것이 정직합니다(판단).**

**교차검증 결과:**
- **일치(타당):** React와 Spring Boot는 국내 채용(사람인·잡코리아), 외주(위시켓), 대형 커머스 공고(무신사·컬리)가 모두 가리키는 주류입니다. **이 조합은 2026년 11월 한국 기준으로 타당합니다.**

| NCP 참고 | Standard-g3 2vCPU 8GB 1대 + 서버 내 MySQL | 82,240원 + VAT ≈ 90,500원 + 공인 IP(미확인) | 약 9만 원 이상 | 신규 크레딧 10만 원으로 약 1개월. 요금 미검증 |

**크레딧 효과:** AWS 최대 $200(6개월)이면 B1을 약 3.4개월, A1을 6개월 전부 덮을 수 있습니다. 단 무료 플랜은 6개월 뒤 계정이 종료되므로, 유료 플랜으로 전환할지 미리 정해야 합니다 [S150].

**AWS vs NCP (취업 관점):** 채용공고 건수가 AWS 1,501(사람인)·1,404(잡코리아) 대 네이버클라우드 263·NCP 77로 차이가 큽니다 [S68][S70][S82][S83]. NCP는 공공·금융 SI에서 의미가 있지만(판단, 근거 약함), 커머스 취업 포트폴리오에는 AWS가 낫습니다. NCP 요금은 공식 계산기로 직접 확인해야 합니다.

### 마-4. 로컬에서 클라우드로 넘어가는 시점과 기준 (판단, "미룰 수 있을 때까지 미룬다" 반영)
1. **로컬 단계(대부분의 기간):** Docker Compose(MySQL, Redis, OpenSearch, 앱 2개 인스턴스 + Nginx)로 개발합니다. 다중 인스턴스 동시성(분산락, 세션)도 로컬에서 앱 2개로 1차 검증할 수 있습니다. 통합 테스트는 Testcontainers로 합니다.
2. **PG 웹훅·택배 콜백 때문에 클라우드로 갈 필요는 없습니다.** 터널링 도구(cloudflared, ngrok 등)로 로컬에 공개 URL을 붙여 웹훅을 받을 수 있습니다(도구 존재는 B의 사전 지식, 이번 세션에서 미검증).
3. **클라우드 전환 트리거(하나라도 해당하면 전환):**
   - ① 지원서 제출 4~6주 전: 시연 URL과 안정 운영 기록(가동 시간, 알람 이력)이 필요해질 때
   - ② 부하테스트 수치를 포트폴리오 근거로 쓸 때: 로컬에서는 부하발생기와 대상 서버가 같은 노트북 자원을 나눠 써서 수치를 믿기 어렵습니다
   - ③ CI/CD로 배포 자동화와 무중단 배포를 보여줄 때
4. **비용 통제:** 첫날 예산 알림을 설정하고, Terraform 같은 IaC로 "만들고 지우기"를 한 명령으로 하며, 부하테스트 인프라는 테스트 직후 삭제합니다. 인스턴스를 꺼도 IPv4 요금은 계속 나간다는 점에 주의합니다 [S153].

- **플러스 알파 = 정산·대사 도메인 깊이 + 셀러 백오피스까지 포함한 3면(구매자·판매자·운영자) 풀스택**
- 근거: 와이톤 자격요건 [S19], 무신사 주문·결제·세일·쿠폰 도메인 [S31], 정산 기한 법 개정 [S139], 토스 부분취소·과세 규칙 [S133].

**내용**
- 핵심 기능: 판매자 입점·심사, 판매자별 상품·재고 관리, 주문 → 판매자주문 → 주문상품 3단 구조, 판매자별 배송비 묶음, 플랫폼 부담·판매자 부담 쿠폰 안분, 부분취소·부분반품, 판매자 송장 등록(모의 택배사), 구매확정(수동 + 자동), 정산 배치(수수료, 환불 차감), 정산 내역서, PG 대사, 운영자 CS 화면
- 다룰 기술 문제: #17·#34·#35·#36·#37·#38·#30을 중심으로 하고, #18·#21·#24~#27은 제안 1과 같습니다. 여기에 멀티테넌시 권한(판매자 데이터 격리, 와이톤 우대사항 [S19])이 더해집니다.
- 스택: 제안 1과 같습니다. 정산은 Spring Batch(재실행 안전, 멱등)를 추가합니다(근거는 판단). OpenSearch는 선택입니다.

**방향**
- 진행 전략: 금액 계산 규칙을 먼저 테스트 케이스로 고정합니다(예: "3만 원 쿠폰, 판매자 2곳, 1곳 부분취소 시 각자 정산액"). 그 뒤 화면을 만듭니다.
- 단계: 금액 도메인 모델과 테스트 → 주문 분리·결제 → 배송·구매확정 → 취소·반품 → 정산 배치·대사 → 셀러·운영자 백오피스 → 부하·장애 시나리오
- 포트폴리오에서 보여줄 방식: "주문 1건의 돈이 어떻게 갈라지는가" 다이어그램, 금액 규칙 테스트 표, 정산 배치 재실행 안전성 데모, 대사 불일치 처리 데모

**제안의 한계**
- 시각적 임팩트와 트래픽 스토리가 약합니다. 백오피스 화면이 많아 작업량이 큽니다.
- 정산 규칙은 실제 기업마다 달라서, 포트폴리오의 규칙은 가정에 기반합니다.
- 법 개정안은 법사위·본회의가 남아 있어 내용이 바뀔 수 있습니다 [S139].
- 정산 경험을 우대하는 신입 공고의 수는 확인하지 못했습니다(**미확인**).

**사용자에게 던지는 질문 5개**
1. 백오피스(관리자 화면)를 많이 만드는 작업에 흥미가 있으신가요, 아니면 지루하게 느껴지시나요?
2. 판매 모델을 오픈마켓(위탁)으로 할지, 직매입과 섞을지 선호가 있나요?
3. 수수료율·정산 주기 같은 가상의 비즈니스 규칙을 직접 정하는 데 동의하시나요?
4. 금융·핀테크·커머스 백오피스 쪽 회사도 지원 대상에 넣을 생각이 있나요?
5. 정산 배치는 백엔드 비중이 매우 높습니다. 프론트 작업 비중이 줄어도 괜찮으신가요?

**순위를 매긴 이유:** 차별화 정도는 셋 중 가장 높을 수 있습니다. 하지만 (가)의 핵심 신호인 "AI 활용 + 대용량 트래픽"과의 연결은 제안 1보다 약하고, 정산 경험을 원하는 신입 공고 수를 확인하지 못해서 2순위로 두었습니다.

### 제안 3 (3순위) — "AI 네이티브 커머스": 뷰티 버티컬에 자연어 검색·리뷰 요약·MCP 쇼핑 에이전트를 얹은 풀스택

**조사 결과**
- 원티드 공고에서 "AI Native" 키워드가 8배 증가했고, Agentic·Multi-Agent 키워드가 급증했습니다 [S11].
- 무신사는 자체 MCP로 대화형 커머스와 리뷰 약 2,100만 건 요약을 운영합니다 [S30].
- 와이톤은 LLM 게이트웨이를 운영하고 [S19], F&F는 RAG·에이전트를 자격요건으로 [S21], 도이치모터스는 LLM·RAG를 우대로 [S20] 둡니다.
- 잡코리아는 AI 직무 분류를 12개로 늘렸습니다 [S6].
- 다만 이런 공고는 대부분 경력직입니다.

**조사 근거:** [S6][S11][S19][S20][S21][S30][S5] / 레퍼런스 [S107](품절 → OpenSearch), [S118](탐색 UX)

**프로젝트 주제:** "성분·피부타입 기반 탐색과 리뷰 기반 AI 큐레이션이 있는 뷰티 커머스. 자연어 검색(키워드 + 벡터 하이브리드), 리뷰 요약, MCP 서버로 외부 AI 에이전트가 상품 검색·장바구니 담기를 할 수 있게 한다"

**사이트 컨셉:** 컨셉 후보 3(2-B절)

**플러스 알파와 그 근거**
- **플러스 알파 = LLM 기능의 "제품화" 역량**입니다. 하이브리드 검색 품질 측정, LLM 호출 비용·지연·실패 관리(게이트웨이, 캐시, 폴백), 프롬프트 주입 방어, MCP 서버 설계를 포함합니다.
- 근거: 무신사 MCP [S30], 와이톤 LLM 게이트웨이 [S19], F&F [S21].

**내용**
- 핵심 기능: 제안 1의 코어(단, 드롭 대신 정기 세일 + 선착순 쿠폰), 성분·피부타입 facet, 자연어 검색, 리뷰 작성·요약, 개인화 추천(규칙 기반에서 시작), MCP 서버(검색·상품 조회·장바구니 담기 도구), AI 기능 관측 대시보드(토큰 비용, 지연, 실패율)
- 다룰 기술 문제: #5·#6·#7·#15·#18·#24~#27, 그리고 LLM 고유 문제(비결정성 테스트, 비용 상한, 프롬프트 주입, 에이전트가 장바구니에 담을 때의 권한·확인 단계)
- 스택: 제안 1 + OpenSearch(키워드 + k-NN 벡터) + LLM API(공급자 추상화). Spring AI 같은 프레임워크 채택 여부는 이번 세션에서 확인하지 못했습니다(**미확인**). 선택적으로 Next.js 스토어프론트(무신사·컬리 FE 신호 [S32][S33])를 둡니다.

**방향**
- 진행 전략: 코어 커머스 정합성(P0)을 먼저 끝냅니다. AI 기능은 "끄면 일반 검색으로 폴백"되게 설계해 코어를 해치지 않게 합니다.
- 포트폴리오에서 보여줄 방식: 검색 품질 비교표(키워드 vs 하이브리드), LLM 비용·지연 대시보드, MCP 데모 영상, 프롬프트 주입 방어 테스트

**제안의 한계**
- AI 기능이 평가자에 따라 "장식"으로 보일 수 있고, 커머스 기본기 증명이 얇아질 위험이 가장 큽니다.
- LLM API 비용이 듭니다(금액 미산정).
- AI 관련 공고는 대부분 경력직이라 신입 연결 근거가 약합니다.
- 신입 AI 엔지니어 채용이 ML 배경을 요구하는지는 확인하지 못했습니다(**미확인**).
- 뷰티 성분 데이터 확보 방법도 미확인입니다.

**사용자에게 던지는 질문 5개**

2. "AI 기능을 만드는 개발자"와 "AI로 개발하는 개발자" 중 어느 쪽 정체성이 목표에 더 가깝나요?

**순위를 매긴 이유:** 트렌드 키워드와 가장 잘 맞지만, 근거 공고가 경력직 위주이고 기본기 증명을 희석할 위험이 커서 3순위입니다. 제안 1의 2단계 확장으로 쓰는 편이 위험 대비 효과가 좋다고 판단합니다.

## 3. 자기 검증
