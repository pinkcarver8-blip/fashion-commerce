# 서브 에이전트 A 조사 보고서 (1차, 독립 조사)

- 작성: 서브 에이전트 A
- 작성일: 2026-11-07 (모든 채용공고·검색 결과의 확인 시점도 2026-11-07)
- 범위: prompt.md 1~2번 + 3번 "첫 번째 순서", 그리고 코디네이터 추가 지시 (마) 배포 비용, (바) 사이트 컨셉, 사용자 프로필 반영
- 다른 에이전트(B, C) 파일은 열람하지 않음

## 0. 조사 개요

### 0-1. 조사 방법
1. WebSearch(검색 결과 요약)로 후보 자료를 찾고, 중요한 자료는 WebFetch로 본문을 직접 열었다. 출처 목록(4장)에 "열람" / "검색요약"을 구분해 적었다.
2. 채용 시장은 세 층으로 봤다. ① 채용 플랫폼 키워드 검색 결과(잡코리아·사람인·점핏), ② 개별 채용공고 원문(무신사·컬리·F&F 등), ③ 기사·설문·통계(한국노동연구원, 한국은행, 원티드, 그렙, Stack Overflow 등).
3. 기술 스택은 잡코리아 기술 키워드 18개의 공고 수(2026-11-07 스냅샷), 위시켓 외주 통계 2건, 주요 커머스 공고의 스택, 글로벌 설문, 공식 문서(버전·지원 종료일)를 교차해서 봤다.
4. 레퍼런스(나)와 돌발 상황(다)은 각 사 기술 블로그·공식 문서(토스페이먼츠, 포트원, MySQL, AWS, Shopify 등)를 우선했다.
5. 비용(마)은 AWS·NCP 공식 페이지를 먼저 보고, 서울 리전 단가가 공식 페이지에서 렌더링되지 않을 때는 제3자 가격 집계 사이트를 쓰고 그렇게 표시했다.

### 0-2. 실제로 확인한 자료 수 (정직한 집계)
출처 번호 기준이다. 한 출처가 여러 영역에 쓰였으면 영역마다 센다. 그래서 영역별 합계는 전체 고유 출처 수보다 크다.

| 영역 | 고유 출처 수 | 본문 직접 열람 | 검색 결과 요약만 | 비고 |
|---|---|---|---|---|
| (가) 채용 역량 | **57** | 39 | 18 | 열람 39건 중 2건은 인코딩 깨짐, 1건은 본문 미로딩, 1건은 건수만 확인 |
| (나) 레퍼런스 구조 | 24 | 18 | 6 | 10개 사 + UX 연구(Baymard) |
| (다) 돌발 상황·연동 | 26 | 21 | 5 | PG·택배 공식 문서 포함 |
| (라) 기술 스택 | **30** (페이지 기준 47) | 24 (페이지 41) | 6 | 잡코리아 키워드 18개 페이지를 출처 1개(S92)로 묶음 |
| (마) 배포 비용 | 11 | 7 | 4 | NCP 단가는 공식 페이지에서 수치 확인 실패 |
| 전체 고유 출처 | **103** (S92를 18페이지로 풀면 120페이지) | 69 | 34 | |

- **사용자가 요구한 "(가) 100여 개, (라) 100여 개"는 채우지 못했다.** (가)는 57개, (라)는 독립 출처 30개(페이지 47개)다. 숫자를 부풀리지 않으려고 같은 플랫폼의 검색 페이지는 하나로 묶었다.
- 접속을 시도했지만 실패해서 집계에서 뺀 곳: 원티드 웹 검색(JS 렌더링으로 0건 표시), 점핏 웹 검색(0건 표시), 크몽 검색(목록 미로딩), 이랜서(목록 미로딩), 프리모아(인증서 오류), 쿠팡 엔지니어링 Medium(403), theteams(403), 잡플래닛 기사(403), JetBrains 블로그(403), NCP 요금표(수치 미렌더링), instances.vantage.sh(리전 불명확), 무신사 뉴스룸(리다이렉트).
- 점핏 공개 API는 2회 조회한 뒤, 반복 조회가 자동화 차단 우회로 판단되어 중단했다. 그래서 점핏 자료는 표본 16건 수준에 그친다.

### 0-3. 조사의 한계
1. **키워드 검색 건수는 정밀 통계가 아니다.** 잡코리아 검색은 본문 전체를 매칭하므로 비개발 공고, 교육 과정 광고, 중복 공고가 섞인다. 하루치 스냅샷이고 헤더와 본문 숫자가 다른 경우도 있었다(예: React 896/893).
2. **국내 개발자 설문의 2026년판(프로그래머스, 인프런, 점핏)을 찾지 못했다.** 글로벌 설문(Stack Overflow, JetBrains, State of AI)은 한국 시장을 대표하지 않는다.
3. **홍보성 자료가 많다.** 무신사·CJ올리브네트웍스·넥슨의 채용 방식은 회사가 낸 보도자료를 기반으로 한 기사다. 그렙(프로그래머스 AI 역량평가) 자료는 서비스 공급사 자신의 주장이다. HeroDevs(Spring Boot EOL)도 연장 지원을 파는 회사다.
4. **쿠팡·무신사·29CM 기술 블로그 본문은 직접 읽지 못했다**(Medium 403, 검색 미노출). 무신사는 채용공고 원문과 기사로 대신했다.
5. **NCP 요금은 서울 리전 공식 수치를 확인하지 못했다.** AWS 서울 단가도 일부는 제3자 집계 사이트 값이다.
6. 한국 패션 이커머스 반품률처럼 컨셉 판단에 쓸 만한 국내 통계는 확인하지 못했다.

## 1. 영역별 조사 결과

### (가) 2026년 11월 한국에서 "바이브 코딩 개발자"로 취업하려면

#### 가-1. 전제 검증: "바이브 코딩 개발자"는 실제 직무명인가
- **일부 중소기업·스타트업 공고 제목에만 등장한다.** 잡코리아에서 '바이브 코딩'으로 검색하면 173~176건[S1], 사람인 '바이브코딩'은 190건[S2]이다. 그런데 잡코리아 1페이지 20건 중 개발 직무가 분명한 것은 7건 정도다(비오앰 "AI Native/바이브 코딩 기반 풀스택", 메타빌드 "AI 기반 바이브 코딩 개발자", 빅레그 "AI 바이브코딩 기획자/개발자 의류 쇼핑몰", F&F "Java/Spring 백엔드 신입/경력" 등). 나머지는 퍼포먼스 마케터, 기획자, 디자이너, 무료 취업교육 광고였다[S1]. 점핏에서 '바이브코딩'을 검색하면 55건이 나왔고, 1페이지 16건 중 신입 공고는 1건이었다. 나머지는 최소 경력 1~13년이었다[S6].
- **주요 기업에서는 직무명이 아니라 "AI 도구 활용 역량"이 자격요건·우대사항·전형에 녹아 있다.**
  - 무신사 Backend Engineer(경력 5년+)의 **자격요건**: "AI 기반 도구를 활용하여 개발 생산성과 문제 해결 역량을 강화한 경험이 있으신 분"[S9]
  - 무신사 Product Engineer(Catalog)의 우대사항: "AI 코딩 도구를 개발 프로세스에 적극적으로 활용하여 개발 생산성이나 코드 품질을 실질적으로 개선한 경험". 직무 소개에는 "결과물의 품질은 직접 검증하고 책임집니다"라고 적혀 있다[S10]
  - 컬리 커머스 백엔드: "생성형 AI를 활용한 과제 전형(사전 과제 또는 코딩테스트)이 함께 진행됩니다"[S12]
  - F&F 백엔드(3년+): "AI 보조 도구를 활용한 개발 생산성 향상"에 적극적인 태도, RAG·프롬프트 엔지니어링·AI 에이전트 학습·적용 경험[S14]
  - 원티드 공고 72,793건(2025.1~2026.4)을 분석한 결과, 2026-07-31 기준으로 **공고 3건 중 2건에 AI 관련 키워드가 한 번 이상 등장**했다. 'AI Native' 키워드는 8배 늘어 증가율이 가장 높았다. Codex, Claude Code, AI 코딩이 핵심 키워드로 꼽혔다[S18]
  - 반대 사례: 당근 채용 페이지에는 AI 코딩 도구 언급이 없고, 신입·주니어 표기도 없다(인턴 1건뿐)[S8]
- **결론**: 목표 포지션을 "바이브 코딩 개발자"로 잡는 것은 위험하다. 공고 수가 적고, 질 낮은 공고(마케터 겸직, 저연봉)가 섞여 있다. 시장 언어로는 **"AI 도구를 검증하며 쓰는(AI-native) 풀스택/백엔드 개발자"**가 맞다. '바이브 코딩'은 직무명이 아니라 일하는 방식이다.

#### 가-4. "AI를 쓴다"보다 "AI 결과물을 검증하고 서비스로 만든다"가 평가된다
여러 독립 출처가 같은 방향을 가리킨다. 이 보고서의 핵심 근거다.
- 크몽: 바이브코딩 '후속 개발' 문의가 2026년 2분기에 2025년 4분기 대비 약 550% 늘었다. 의뢰 단계는 **배포·출시**가 가장 많았고, 그다음이 **DB·데이터 구조 설계**, **버그 수정·안정화** 순이었다. **업종은 커머스·유통이 최다**, 고객은 소상공인과 예비창업가가 많았다[S40] 열람. 다른 매체는 550%를 전년 대비로 보도해서 기준 기간이 엇갈린다.
- 오늘의집 '올리고': 사내 구성원이 AI로 앱을 만들어도 서비스로 올리려면 **인프라, 인증, DB 스키마 검토, 보안 검토**라는 4개 허들이 있었다. 이를 하네스(규칙·템플릿·자동 검사)와 사람의 승인으로 풀었다. 앱 51개 중 24개를 운영에 배포했다[S66] 열람.

- Veracode(2025.7): 80개 과제, 100개 이상 LLM에서 AI 생성 코드의 45%에 보안 취약점이 있었고, Java의 실패율은 70% 이상이었다. 2026년판 수치는 56%와 62%로 서로 충돌해 미확정이다[S36] 검색요약.
- 보안 스타트업 텐자이는 주요 코딩 에이전트 결과물에서 "주문 수량은 양수여야 한다" 같은 규칙이 빠져 **음수 주문**이 가능한 취약점을 찾았다(서울경제TV가 The Information을 인용)[S53] 열람. 이커머스 프로젝트에 바로 해당하는 사례다.

#### 나-2. 공통 구조(교차 확인)
- **페이지 흐름**: 홈(기획전·개인화) → 카테고리/검색(필터·정렬) → 상품 목록(PLP) → 상품 상세(PDP: 옵션 선택, 재고, 배송 예정일, 리뷰) → 장바구니(쿠폰, 배송비 미리보기) → 주문서(배송지, 결제수단, 약관) → PG 결제 → 완료 → 마이페이지(주문 상태, 배송 조회, 취소·반품). 10곳 모두 이 기본 골격 위에 차별 요소를 얹는다.
- **읽기 경로와 쓰기 경로를 분리한다**: 쿠팡 core serving layer, 11번가 전시 캐시, 컬리 CQRS. 탐색(읽기)은 캐시와 비정규화로 처리하고, 주문·재고(쓰기)는 트랜잭션 정합성으로 처리한다.
- **이벤트 기반 후속 처리**: 배민, 컬리, 올리브영, 11번가 모두 "주문 확정 후 알림·배송·정산"을 이벤트로 분리한다. 정합성 장치로는 컬리의 Outbox가 구체적이다.
- **트래픽 스파이크 대비는 기능이 아니라 운영 절차다**: 무신사 이벤트 연동 사전 확장, Shopify 게임데이·스케일 테스트, Zalando 상황실·기능 끄기 스위치.
- **충돌하는 점**: 재고 동시성에서 Redis 원자 연산을 쓰는 흔한 블로그 방식과 달리, Shopify는 "예약과 원장이 다른 시스템에 있어 원자적으로 묶을 수 없다"는 이유로 Redis를 버리고 MySQL을 택했다[S73]. "Redis 분산락이 정답"이라는 통념과 충돌하는 1차 자료다.

#### 나-3. 이번 프로젝트에 적용할 제안 3가지
1. **모듈러 모놀리스로 시작하고 도메인 경계를 코드로 강제한다.** Spring Boot 단일 앱 안에 `catalog / inventory / order / payment / shipping / (settlement)` 모듈을 나누고, 모듈 간 의존 규칙을 아키텍처 테스트(예: ArchUnit)로 막는다. MSA 분리는 "측정된 이유"가 생길 때만 한다.
   - 근거: Shopify는 모놀리스로 플래시 세일을 처리한다[S73][S74]. 컬리는 "MSA 여부보다 내부 역할 분리 품질이 AI Context 품질을 좌우한다"고 썼다[S60]. 1인 프로젝트에서 MSA는 운영 비용만 키운다(추론).
2. **읽기/쓰기 경로를 분리하고 각각 다른 품질 목표를 둔다.** 탐색(PLP·PDP·검색)은 캐시와 응답 시간 목표, 주문·재고·결제는 "초과판매 0건, 결제-주문 불일치 0건" 같은 정합성 목표를 둔다.
   - 근거: 쿠팡[S69], 11번가[S63], 컬리 CQRS[S60], Shopify의 "품절로 잘못 보여도 손실, 두 번 팔아도 손실"[S73].
3. **'핵심 여정(critical journey)' 단위로 장애를 설계하고 부하를 테스트한다.** 탐색 → 장바구니 → 주문 → 결제 → 환불 여정마다 장애 주입(지연, 의존 서비스 다운, 웹훅 중복)과 폴백(예: 추천 실패 시 기본 목록, 배송 예정일 조회 실패 시 기본값)을 정의하고, k6 시나리오도 여정 단위로 만든다.
   - 근거: Shopify critical journeys·게임데이[S74], Zalando 폴백·여정 단위 확장[S75], 쿠팡 Valve[S69], Baymard 체크아웃 이탈 사유[S76].

#### 다-2. 국내 PG·택배 연동 실제 방식 (공식 문서 기준)
- **토스페이먼츠 결제위젯**[S78]: ① 결제 요청 전 서버에 orderId·amount 임시 저장 → ② `requestPayment()` → ③ successUrl로 `paymentKey, orderId, amount` 수신, 금액 일치를 "반드시 확인" → ④ 서버가 시크릿 키(Basic 인증)로 **결제 승인 API** 호출(요청 후 **10분 이내**) → ⑤ paymentKey·orderId 저장. 테스트 키로 개발할 수 있지만 **가상계좌는 상점 전용 테스트 키(계약 후)가 필요**하다.
- **토스페이먼츠 멱등키**[S79]: 모든 POST API에 `Idempotency-Key`(최대 300자), 유효 기간 15일, 처리 중 재요청이면 `409 IDEMPOTENT_REQUEST_PROCESSING`.
- **토스페이먼츠 웹훅**[S80]: 10초 안에 200 응답, 실패 시 최대 7회 재전송(1~4096분 간격, 약 3일 19시간), 로컬 URL은 등록 불가이므로 ngrok 등 사용. 이 페이지에서는 서명 검증 방식을 확인하지 못했다.
- **포트원 V2 웹훅**[S81]: Standard Webhooks 서명 검증 + 결제 단건 조회로 금액 대조를 권장한다. 최대 5회 재전송, **전송 순서 미보장**, 모르는 type은 무시하라고 안내한다.
- **택배**: CJ대한통운 송장 출력·연동은 계약 고객 대상이고, 계약 정보가 다르면 출력이 제한될 수 있다. 상태는 30분~3시간 주기로 갱신되고 반품은 연동되지 않는다(고도몰 도움말 기준)[S83]. 스윗트래커 배송추적 API는 계약 파트너에게 ID·키를 발급하고, `add_invoice`로 운송장을 등록하는 방식이다(v1.5~1.6 문서, 2021년 자료)[S84]. 스마트택배 조회 API는 `t_key, t_code, t_invoice` 파라미터를 쓴다(무료 여부와 호출 제한은 확인하지 못함)[S85].
- **시사점**: 포트폴리오에서 실제 송장 발행은 불가능하다고 보는 것이 안전하다(사업자·계약 필요). 그래서 **어댑터 패턴 + 모의 택배사 + (가능하면) 실조회 API**로 "실제 연동 구조를 이해하고 있다"를 보여주는 방향이 현실적이다.

#### 라-4. 대안 검토
- **Next.js + NestJS/Node**: NestJS 80건, Node.js 315건으로 국내 커머스 백엔드에서는 Spring보다 적다. 커머스 대기업 공고(무신사·컬리)는 Java/Spring이다. 대안으로서 우위가 없다.
- **Kotlin + Spring**: 206건. 무신사(Java/Kotlin)와 오늘의집(Kotlin)이 쓴다. 바꿀 이유는 약하다. Java로 시작하고 Kotlin은 선택으로 둔다.
- **PostgreSQL**: 글로벌로는 1위지만 한국 커머스 공고에서는 MySQL이 약간 많다. 재고 실험(SKIP LOCKED 등)은 둘 다 가능하다. **MySQL 유지**.
- **결론: 사용자의 기본 조합은 타당하다.** 바꿀 것은 "버전(Boot 4, MySQL 8.4)"과 "TypeScript, Redis, Docker, 테스트 체계 추가"다. 스택 자체로는 차별화되지 않는다는 점에 유의해야 한다. React + Spring Boot는 국비 부트캠프의 표준 커리큘럼이다[S93].

## 2. 최종 제안 3개

> 사용자 프로필 전제: 부트캠프 수료, 바이브 코딩 3~6개월, 목표는 풀스택 + 플러스 알파, 기간 제약 없음, 클라우드 최대한 늦게 도입, 기초 AWS 배포 경험 있음. 기존 박스오피스 프로젝트는 연결하지 않는다. 하향 조정 없이 최대 퍼포먼스를 목표로 한다.

### 제안 1 (1순위): "검증 가능한 바이브 코딩으로 만든 드롭형 패션 커머스" — 커머스 코어 정합성 + AI 하네스

**조사 결과**
- 국내 커머스 공고의 공통 스택은 Java/Spring/JPA/MySQL/Redis(+Kafka)이고, 무신사 Catalog PE는 동시성 제어·캐싱·RDBMS 정합성·커머스 도메인을 자격요건으로 명시한다.
- AI 도구 활용은 이미 자격요건·전형 단계에 들어와 있고(무신사, 컬리, CJ올리브네트웍스, 넥슨, 그렙), 평가의 핵심은 "결과 검증·책임"이다.
- 바이브 코딩 결과물이 실제로 무너지는 지점은 배포, DB 설계, 안정화(크몽), 인프라·인증·DB·보안(오늘의집), 취약점(Veracode), 비즈니스 규칙 누락(음수 주문)이다.

**조사 근거**: [S9][S10][S12][S18][S26][S33][S36][S40][S43][S45][S48][S49][S53][S60][S66][S73][S78][S79][S80][S82]

**프로젝트 주제**: 주간 한정 드롭과 상시 판매가 공존하는 가상 패션 편집숍. 드롭 순간의 동시 주문부터 결제, 배송, 반품·환불까지 '돈과 재고가 한 건도 어긋나지 않는다'를 **수치와 테스트로 증명**하고, 그 전 과정을 AI 에이전트로 개발하되 **AI가 지켜야 할 규칙·검사 장치(하네스)**를 설계해 공개한다.

**플러스 알파와 근거**
- 플러스 알파 = **① AI 하네스 엔지니어링**(규칙·컨텍스트·자동 검사·사람의 승인 지점 설계) + **② 커머스 정합성 실증**(락 전략 비교 실험, 장애 시나리오별 재현 테스트).
- 근거: 무신사 PE "AI 에이전트와 함께… 결과물의 품질은 직접 검증하고 책임"[S10], 컬리 "AI 답변을 신입의 제안처럼 검증"과 AI Context 설계[S60], 오늘의집 하네스[S66], 그렙 평가 기준 '결과 검증·보안'[S26], 동시성 제어 자격요건[S10].
- 왜 플러스 알파인가: "동시성 재고"는 부트캠프·강의에서 흔한 주제다(검색 결과에 인프런 강좌·블로그 다수). 주제가 아니라 **비교 실험의 수치와 검증 체계의 공개**가 차별화 요소다.

**내용**
- 핵심 기능: 회원·비회원 주문, 카테고리/검색/필터, PDP(옵션 SKU), 장바구니, 쿠폰(선착순 포함), 주문서, 토스페이먼츠 테스트 결제, 주문 상태 머신, 배송(모의 택배사 + 송장 이벤트), 취소/부분취소/반품/환불, 드롭(대기열 + 구매 한도), 관리자(상품·재고·주문·드롭 일정)
- 다룰 기술 문제(우선순위)
  - P0: 재고 예약·확정·해제(예약 TTL을 승인 10분 시한에 맞춤), **락 전략 6종 비교 실험**(다-1 표), 멱등키, 서버측 금액 재계산, 웹훅(재조회 검증 + 멱등 + 순서 역전 처리), 부분 취소 금액 계산, 결제 성공-DB 실패 보상과 대사 배치
  - P1: 드롭 대기열, rate limit, 핫 SKU 경합 완화(행 분할 + SKIP LOCKED), 캐시(TTL 지터, 키 정규화), Outbox(폴링) 기반 후속 처리(알림, 배송 요청)
  - P2: 검색 고도화(ngram → OpenSearch + nori), 관측성, 장애 주입, 부하 테스트(로컬 → 클라우드 재측정), 클라우드 배포
- 스택: React(19 계열) + Vite 8 + **TypeScript** + TanStack Query + React Router / Spring Boot 4.0.x + Java 21(25 검토) + JPA + QueryDSL + Flyway / **MySQL 8.4 LTS** / Redis / Docker Compose / JUnit 5 + Testcontainers + k6 / Actuator + Prometheus + Grafana / GitHub Actions / 토스페이먼츠 테스트 키 + ngrok. Kafka는 P2 이후 선택.

**방향**
- Phase 0 — 하네스 먼저: 도메인 용어집, 불변식 목록(예: 재고 ≥ 0, 결제액 = 주문액 − 할인), ADR 템플릿, AI 작업 규칙 문서(버전 고정, 금지 패턴, 테스트 먼저), 아키텍처 테스트, CI(테스트·정적 분석·비밀값 스캔)
- Phase 1 — 해피패스 E2E: 탐색 → 주문 → 결제 → 배송 → 구매확정
- Phase 2 — 실패 카탈로그: 다-1의 P0 시나리오마다 "재현 테스트 → 해결 → ADR" 세트를 만든다
- Phase 3 — 드롭과 성능: 대기열, 부하 테스트, 병목 분석
- Phase 4 — 배포와 공개: 마-3 기준으로 클라우드 전환, 데모 URL, 문서 공개
- 포트폴리오에서 보여줄 것: ①1장짜리 README(문제 → 결정 → 수치), ②**정합성 보고서**(락 전략별 TPS, p95/p99, 초과판매 0건 검증, 데드락 수), ③장애 시나리오 카탈로그와 테스트 링크, ④**AI 협업 로그**(AI가 틀렸던 사례와 그것을 잡아낸 장치), ⑤데모 영상

**제안의 한계**
1. 실사용자가 없으므로 모든 부하는 합성 트래픽이다. "장애 경험"이 아니라 "장애 시뮬레이션"이다.
2. PG는 테스트 환경이라 가상계좌 일부는 테스트할 수 없고(계약 필요), 송장은 모의다.
3. 근거 공고 상당수가 경력 5년 이상 공고다. 신입 평가자가 이 깊이를 가산점으로 보는지는 직접 검증하지 못했다.
4. Spring Boot 4는 출시 1년 미만이다. AI 도구가 3.x 방식 코드를 낼 위험이 있다. 하네스에서 버전을 고정해야 하고, 이 과정 자체도 검증 사례가 된다.
5. 무신사·29CM의 '클론'으로 보일 위험이 있다. 컨셉 문구와 차별 요소(드롭 정책, 공개 실험 보고서)로 관리해야 한다.

1. 목표 회사군은 어디인가(커머스 플랫폼 / IT 스타트업 / SI·대기업 IT 계열사)? 전형(코딩테스트 vs AI 과제)과 스택 강조점이 달라진다.

### 제안 2 (2순위): "멀티셀러 마켓플레이스 + 정산·대사 파이프라인" — 돈의 흐름 정합성과 이벤트 기반 아키텍처

**조사 결과**
- 커머스 기업에서 정산·PG 대사·대규모 배치는 별도 조직·직무로 존재한다(무신사페이먼츠).
- 컬리는 3P 입점과 3PL 확장 과정에서 외부 데이터 동기화를 Outbox + 재시도 토픽으로 풀었다.
- PG(토스페이먼츠)도 지급대행·셀러·에스크로 이벤트를 제공한다. 마켓플레이스 정산을 PG 기능과 연결해 설계할 수 있다.

**조사 근거**: [S11][S12][S61][S80][S81][S86][S65][S94]

**프로젝트 주제**: 리빙·라이프스타일 셀러들이 입점하는 오픈마켓. 주문이 셀러별로 나뉘고, 부분 취소·반품이 섞여도 **"고객 결제액 = 셀러 정산액 + 플랫폼 수수료 + 환불액"이 항상 맞는다**는 것을 대사 배치로 증명한다.

**플러스 알파와 근거**
- 플러스 알파 = **정산·대사(금융성 배치) + 이벤트 기반 아키텍처(Outbox → Kafka)**.
- 근거: 무신사페이먼츠 우대 "PG사 API 연동 및 데이터 대사", "수백만 건 이상 대규모 배치"[S11], 컬리 Outbox·Kafka[S61], 컬리 Kafka 자격요건[S12]. 신입 지원자 중 정산을 다루는 사람이 드물 것이라는 판단은 **추정이고 검증하지 않았다.**

**내용**
- 핵심 기능: 셀러 입점·상품 승인, 셀러 어드민(상품·주문·정산 조회), 고객 쇼핑몰(제안 1의 기본 흐름), 셀러별 하위 주문·배송비·묶음배송, 구매확정(자동 확정 배치), 정산 주기 배치, 대사 리포트(PG 거래 vs 주문 원장 불일치 탐지)
- 다룰 기술 문제: 하위 주문 분할과 부분 취소 금액 배분(쿠폰 안분), 정산 멱등성(배치 재실행 안전), Outbox → Kafka 전환, 소비자 멱등성, 재시도·DLT, 대사 불일치 분류(누락, 금액 차이, 상태 차이), 대용량 배치 성능(청크, 페이징)
- 스택: 제안 1 + **Spring Batch** + **Kafka**(Docker Compose) + (선택) Elasticsearch

**방향**
- Phase 1에서는 제안 1의 커머스 코어를 단일 판매자로 먼저 완성한다. Phase 2에서 셀러 개념과 하위 주문, Phase 3에서 정산·대사 배치, Phase 4에서 Kafka 전환과 성능을 다룬다.
- 포트폴리오: "돈의 흐름 다이어그램", 대사 리포트 예시(의도적으로 불일치를 주입해 탐지하는 데모), 배치 재실행 안전성 테스트.

**제안의 한계**
1. 범위가 가장 크다(셀러 어드민 추가). 완성하지 못할 위험이 제일 크다.
2. 정산 실무 규칙(세금, 지급 보류, 에스크로 법규)을 조사하지 않았다. 규칙을 지어내면 오히려 감점 요인이 될 수 있다.
3. 근거 공고가 10년차 EM 공고다. 신입 채용에서 정산 경험이 가점이 되는지 직접 근거가 없다.
4. 실제 PG 지급대행은 계약이 필요하다. 시뮬레이션에 그친다.
5. Kafka까지 넣으면 로컬 리소스 요구가 커지고, 1인 운영 부담이 늘어난다.

**사용자에게 던지는 질문 5개**
1. 고객 화면보다 셀러·운영자 화면을 만드는 일에 흥미가 있는가?
2. 숫자(금액 안분, 수수료 계산)를 다루는 도메인을 좋아하는가?
3. 핀테크·결제 회사도 목표 회사군에 들어가는가?
4. 정산 규칙을 실제와 비슷하게 만들기 위해 PG·오픈마켓 셀러 약관을 직접 읽을 의향이 있는가?
5. 제안 1을 먼저 끝내고 제안 2로 확장하는 '단계적 결합'을 받아들일 수 있는가?

**덧붙임**: 제안 1과 배타적이지 않다. 제안 1의 컨셉에서 '입점 브랜드'를 추가하면 제안 2로 자연스럽게 확장된다.

**순위를 매긴 이유**: 차별화 잠재력은 1순위보다 클 수 있다. 하지만 ① 신입 시장 근거가 약하고(경력 공고 위주), ② 범위가 커서 완성 위험이 크며, ③ 정산 규칙 미조사 상태라 2순위로 둔다.

### 제안 3 (3순위): "AI 네이티브 커머스" — 탄탄한 커머스 코어 위에 하이브리드 검색·AI 상품 Q&A·운영 자동화

**조사 결과**
- 원티드 공고 3건 중 2건에 AI 키워드가 있고, 'AI Native'는 8배 늘었다.
- F&F 백엔드 자격요건에 RAG·프롬프트 엔지니어링·AI 에이전트가 있고, 무신사는 "AI 기반 기술을 실무 시스템에 실용적으로 적용한 경험"을 우대한다.
- 커머스 기업들이 AI 기능을 실제로 내고 있다: 무신사 트렌드 큐레이션, 오늘의집 검색 retrieval·오토태깅, 배민 B마트 카메라 검색, Shopify 생성형 추천.

**조사 근거**: [S9][S14][S18][S47][S65][S67][S17]. Shopify 생성형 추천 글은 검색 결과 제목만 확인해서 출처 번호를 매기지 않았다.

**프로젝트 주제**: 제안 1의 커머스 코어를 갖춘 패션 커머스에 "자연어로 찾는 검색(키워드 + 의미 검색)", "상품 Q&A 챗봇(상품 정보·리뷰 근거로만 답변)", "운영자용 AI(상품 등록 자동 태깅, CS 응답 초안)"를 붙이고, **오프라인 평가셋으로 품질을 측정**한다.

**플러스 알파와 근거**
- 플러스 알파 = **AI 기능의 서비스화와 평가**(검색 품질 지표, 답변 근거 검증, 비용·지연 예산).
- 근거: [S14](RAG·에이전트 요구, 단 3년 이상 공고), [S9](무신사 우대), [S18](키워드 증가), [S65](오늘의집 검색 retrieval).

**내용**
- 핵심 기능: 제안 1 기능 전부 + 하이브리드 검색(OpenSearch nori + 벡터) + 상품 Q&A(RAG) + 운영 자동 태깅
- 다룰 기술 문제: 검색 품질 평가(정답셋, 재현율), 환각 억제(근거 문서 인용 강제), LLM 장애·지연 시 폴백(키워드 검색으로 전환), 비용 상한, 개인정보가 프롬프트에 섞이지 않게 하기, 프롬프트 인젝션(리뷰 본문을 통한 공격)
- 스택: 제안 1 + OpenSearch/Elasticsearch(nori, k-NN) + LLM API + (선택) Python FastAPI 사이드카

**방향**
- 반드시 제안 1의 P0(정합성)를 먼저 끝낸 뒤 AI 기능을 붙인다. AI 기능에는 각각 "끄는 스위치"와 폴백을 둔다(Zalando 패턴[S75]).
- 포트폴리오: 검색 전후 지표 비교, 평가셋 회귀 테스트, AI 답변 실패 사례집.

**제안의 한계**
1. LLM API 비용을 조사하지 않았다(이 보고서 범위 밖).
2. 신입 백엔드 공고에서 RAG 경험을 직접 요구한 사례를 찾지 못했다(F&F는 3년 이상). 근거가 트렌드 키워드에 치우쳐 있다.
3. "AI 래퍼" 프로젝트로 보일 위험이 있고, 커머스 코어의 깊이가 희석될 수 있다.
4. 품질 평가는 정답셋 구축 비용이 크다.
5. AI 기술은 바뀌는 속도가 빨라 6~12개월 뒤 차별성이 줄 수 있다.

**사용자에게 던지는 질문 5개**
1. AI 기능 개발(LLM API, 검색 엔진)에 별도 비용(월 몇만 원 수준 가능성)을 쓸 수 있는가?
2. AI 서비스 개발자(AI 엔지니어) 쪽으로 커리어를 확장하고 싶은가, 커머스 백엔드가 중심인가?
3. Python을 추가로 쓰는 것에 거부감이 없는가?
4. 검색 품질 평가처럼 '정답이 애매한' 작업을 견딜 수 있는가?
5. AI 기능을 제안 1의 3순위 확장으로 두는 것(코어 우선)에 동의하는가?

**순위를 매긴 이유**: 트렌드 근거(키워드 증가)는 가장 강하다. 하지만 신입 커머스 채용과 직접 연결되는 근거가 약하고, 비용·평가 불확실성이 커서 3순위로 둔다. 다만 **제안 1의 확장 단계로는 매우 유효하다.**

## 3. 자기 검증

### 3-1. 조사 방향이 맞았는가
- **맞았다고 보는 점**: "바이브 코딩 개발자라는 직무가 있다"는 전제를 공고 원문으로 검증했다. 그 결과 직무명보다 "AI 도구 활용 + 검증"이 일반 직무에 녹아 있다는 것을 여러 독립 출처(공고, 전형 기사, 기술 블로그, 설문)로 교차 확인했다.
- **부족한 점**
  1. (가)·(라) 각 100여 개 목표에 크게 못 미친다(57개, 30개/47페이지). 특히 원티드·점핏·프로그래머스 커리어·리멤버 검색을 체계적으로 집계하지 못했다. 국내 플랫폼 다양성이 사실상 잡코리아에 쏠려 있다.
  2. 신입 공고 원문을 충분히 읽지 못했다. 근거 공고 대부분이 경력 공고다. "신입에게 무엇이 요구되는가"를 신입 공고 20~30건으로 직접 확인했어야 한다. **2차 교차검증 때 가장 먼저 보완해야 할 점이다.**
  3. 외주 시장은 위시켓·크몽 통계 위주다. 이랜서·프리모아·숨고는 접속 실패로 확인하지 못했다.
  4. 국내 개발자 설문(2026)이 없어 글로벌 설문으로 대체했다. 한국에 일반화하는 데 한계가 있다.

### 3-2. 제안이 근거를 제대로 반영하는가
- 제안 1의 "AI 하네스" 플러스 알파는 컬리·오늘의집·무신사·그렙 자료에 기반한다. 그런데 이 중 3개는 **회사가 자기 방식을 소개한 글**이다. "채용 평가에서 하네스를 높게 친다"는 직접 증거(면접 평가표 등)는 없다. 그렙 평가 기준(결과 검증·보안)이 가장 직접적이지만, 공급사 자료다.
- "락 전략 비교 실험이 차별화된다"는 주장은 반대 증거도 있다. 동시성 재고 주제는 인프런 강좌와 블로그에 흔하다. 그래서 차별화를 '주제'가 아니라 '수치·검증·공개'에서 찾는다고 썼지만, **이것이 실제로 서류·면접에서 차이를 만든다는 근거는 없다.** 추론이다.
- 비용(마)은 AWS 일부 단가가 제3자 자료이고 NCP는 핵심 단가를 확인하지 못했다. "AWS가 더 싸다"는 결론은 **확정이 아니다.** 근거가 더 강한 것은 채용 키워드(AWS 1,404 vs NCP 174) 쪽이다.

### 3-3. 모순이나 비약은 없는가
- **모순 가능성 1**: "신입 자리가 줄었다"(KLI, 한은)와 "AI 네이티브 신입을 대규모로 뽑는다"(무신사 66명, CJ올리브네트웍스)는 겉보기에 충돌한다. 해석은 "총량은 줄고 기준은 올랐다"이다. 하지만 무신사 66명은 6개월 전환형 인턴이고, 경쟁률은 약 3.3%다. 이 사례를 일반 신입 시장의 신호로 과대해석하면 안 된다.
- **모순 가능성 2**: 제안 1은 "Redis 분산락 통념과 다른 Shopify의 MySQL 방식"을 강조한다. 동시에 대기열·쿠폰에는 Redis를 쓴다. 모순은 아니지만 "언제 DB, 언제 Redis인가"의 기준을 ADR로 명확히 해야 일관된다.
- **비약 가능성**: "커머스·유통이 크몽 후속 개발 최다 업종"(소상공인 쇼핑몰)을 "대형 커머스 취업에 유리하다"로 연결하는 것은 비약이다. 이 근거는 "바이브 코딩 결과물이 커머스에서 자주 무너진다"는 뜻으로만 쓰고, 취업 유리 근거로는 쓰지 않도록 주의했다.
- **수치 충돌 목록**(출처 간 불일치): 크몽 550%의 기준 기간, JetBrains 조사 기간, Veracode 2026(56% vs 62%), 한은 94% vs 98.6%(서로 다른 분석), Spring Boot 4.0 출시일(11/20 vs 11/30), 잡코리아 헤더·본문 수 불일치, 위시켓 Java 비중(상반기 전체 20% vs 상주 17.4%, 표본이 다름).

### 3-4. 스스로에게 남기는 경고
- 결론 대부분이 "커머스 대기업 경력 공고"에서 역산한 것이다. 사용자의 실제 목표 회사가 스타트업이나 SI라면 우선순위가 바뀔 수 있다(제안 1의 질문 1).
- '최대 퍼포먼스' 요구 때문에 범위를 크게 잡았다. 기간 제약은 없지만, 끝까지 완성하지 못하면 모든 차별화가 무의미하다. Phase 단위로 "여기서 멈춰도 포트폴리오가 성립하는 지점"을 둬야 한다(Phase 2 완료 시점).
