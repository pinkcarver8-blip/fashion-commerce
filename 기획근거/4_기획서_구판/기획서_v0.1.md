## 1. 프로젝트 근거: 2026년 11월 한국에서 무엇을 증명해야 하는가

### 1-1. 결론 (세 에이전트 합의)
1. **"바이브 코딩 개발자"는 정착된 직무명이 아니다.**
   - 일부 중소기업이 직함으로 쓰지만, 확인한 5건 모두 JD(주요업무·자격요건·스택)가 비어 있었다(C 보강 조사).
   - 주류는 **일반 개발 직무 + AI 도구 활용·검증 역량**을 우대하거나 전형에서 평가하는 방식이다.
   - 예: 무신사 2차 "AI 도구 활용 능력 검증 테스트", 컬리, 넥슨, LG CNS, CJ, 현대오토에버의 "생성형 AI 활용 개발·테스트·검증 프로세스".
2. **신입 시장은 축소됐다.**
   - 한국경제 2026-08-12 보도(조사 기관 미명시): 신규 채용으로 인력을 확보하겠다는 기업이 62.6%에서 24.0%로 줄었다.
   - KLI 신입 지원 가능 공고 비중 37.4%.
   - 사람인·점핏 2025 상반기: 백엔드는 지원 비중(23.5%)이 공고 비중(16.2%)보다 커서 **공급 과잉**이다. DevOps·운영은 공고(11.1%)가 지원(10.2%)보다 크다.
3. 그러므로 **"AI로 만들었다"가 아니라 "AI로 만든 것을 검증하고 운영할 수 있다"**를 증명해야 한다.
4. **락 비교와 선착순 동시성 측정은 차별화가 아니라 최소 자격이다.**
   - 근거: 항해 플러스 주차 과제, 인프런 동시성 강좌 수강생 3,654명, GitHub '선착순' 저장소 402개, 같은 설계(Spring Boot 4.1 + MySQL 8.4 + Testcontainers + k6 + ADR + Claude Code)의 2026년 공개 저장소.
   - 이 역량은 커머스 플랫폼 **경력** 공고(무신사 Catalog PE의 "동시성 제어(분산 락, 낙관적 락)")가 요구하는 기본기다. 확인한 신입 공고 36건에는 "동시성"이 한 번도 나오지 않았다.
   - **넣되 표제로 쓰지 않는다.**
5. **전형이 갈라져 있다.**
   - 무신사 AI 네이티브 신입: 지원 약 2,000명 → 1차 코딩테스트 1,700여 명 → 2차 AI 도구 테스트 400명(1차에서 약 76% 탈락) → 3차 면접 100명 → 최종 66명.
   - 네이버·카카오 등은 코딩테스트에서 AI를 금지한다고 소개됐다(플랫폼 콘텐츠 기준, 공식 정책 원문은 미확인).
   - 넥슨은 코딩테스트를 폐지하고 AI 활용 평가로 대체했다.
   - 중소·스타트업은 사전과제·설명형 면접이 많다.
   - → **코딩테스트와 면접 방어는 포트폴리오와 별개의 관문**이다(§14).

### 1-2. 신입 공고 원문 보강 조사 (합의 1차 투표에서 수행, 총 36건)
| 조사 | 표본 | 핵심 결과 |
|---|---|---|
| A: 신입·주니어 FE·풀스택 | 11건 | 운영·배포 7/11, AI 도구 언급 5/11(하네스 언급 0), 성능 최적화·테스트 반복 언급. CWV·E2E·접근성을 직접 요구한 곳은 0~1건 |
| B: 신입·주니어 백엔드 | 13건 | 기본 CRUD·CS 기초·Java/Spring·프로젝트 완주·설명 가능성이 중심. 운영·배포 7~9건(필수 1). 동시성 0건, 트랜잭션·멱등·대사는 PG사 1건. "AI 결과 검증"은 3건(1건은 필수) |
| C: AI 명시·스타트업 주니어 | 12건 | 설계~배포 직접 수행, CI/CD, AI 도구 생산성, "빠르게 실험해 실서비스로 완성"이 반복. 스택은 Next.js·FastAPI·PostgreSQL 계열이 많음 |

**이 결과가 기획에 주는 함의**
- **운영·배포가 신입 공고에서 가장 강하게 지지된다.** 그래서 차별화 축 ①로 올리고, R1부터 CI·실행 가능성을 갖춘다.
- **1순위의 정합성 깊이는 신입 요건 충족이 아니다.** 경력 수준 꼬리 질문에 대한 방어이자 차별화 베팅이다. 이 점을 정직하게 인식한다.
- **"AI 결과물을 이해하고 검증한 경험"은 신입 자격요건 문구로 실제 등장한다.**
- **커머스 신입은 수시 공고가 드물다.** 공채·전환형 인턴(무신사, 에이블리, CJ ENM, CJ올리브영)이 주 진입로이고, 시즌에 의존한다.
- **'주니어' 표기는 0~2년을 뜻하지 않는다.** 예: 컬리 '주니어 FE'는 4~8년, 아파트아이 1~5년, 사각 2년 이상.
- **목표 회사군에 따라 우선순위가 달라진다.**
  - 커머스·SI: Java/Spring/MySQL이 맞다. SI에는 MyBatis·JSP·Oracle이 자주 나온다.
  - 초기 스타트업: Next.js/FastAPI/PostgreSQL 쪽 공고가 많다(§18 Q1).

### 1-3. 근거의 한계 (정직하게 기록)
- 사용자가 요구한 "영역별 100여 개 교차검증"은 **어느 에이전트도 단독으로 채우지 못했다.**
  - A: (가) 57, (라) 30(독립 출처 기준)
  - B: (가) 42, (라) 52(독립 약 18)
  - C: (가) 78, (라) 46(같은 출처 22건 포함)
  - 세 에이전트가 같은 검색 결과 집합을 공유했으므로, 합계를 독립 검증 횟수로 볼 수 없다.
- 대형 커머스(무신사·컬리·쿠팡·29CM·오늘의집)의 **0~2년 공고 원문은 0건**이다. 표본은 잡코리아에 쏠려 있다. 원티드·점핏·사람인 목록은 렌더링 문제로 열지 못했다.

## 3. 사이트 컨셉 (세 에이전트 합의)

### 3-1. 1안 (채택)
- **상품군**: 20~30대 대상 패션
  - 상의·하의·아우터·신발(스니커즈)·가방·잡화
  - **가상 브랜드**와 생성 이미지 사용
  - 상품 단위는 **사이즈×컬러 SKU**
- **코어 판매 모델**: 신품 편집숍, **직매입**, 상시 판매
  - 사이즈 교환·반품이 잦은 업종 특성을 정면으로 다룬다(교환 플로 포함).
- **이벤트**: **주간 한정 드롭**
  - 기본은 **래플(응모 → 추첨 → 당첨자 결제 기한 → 미결제 시 차순위)**.
  - 선착순은 **실험 모드**(부하·동시성 실험용)로 둔다.
  - 1인 구매 제한을 둔다.
  - **드롭은 시연 장면이지 유일한 차별 요소가 아니다.**
- **2단계 확장(R4)**: **입점 브랜드(위탁판매)**
  - 근거: 에이블리 인턴 공고의 "셀러용 플랫폼·백오피스", 컬리 3P 입점, 무신사·29CM의 주력 모델이 입점 구조.
- **선택 옵션(R5 이후)**: **1점 위탁 리커머스**
  - 위탁 신청 → 수거 → 검수·등급 → 촬영 → 등록 → 판매 → 구매확정 → 위탁자 정산.
  - 도메인 흐름은 실재한다. 무신사는 솔드아웃을 종료하고 유즈드에 집중하며, 무신사 Backend 공고 원문에 "리커머스"가 있다.
  - 그러나 신입 채용 공고는 0건이다. 1점 재고는 조건부 UPDATE 하나로 막을 수 있어 동시성 깊이도 크지 않다. 그래서 기본안에서 제외한다.
  - 사용자가 중고·리셀 도메인에 흥미가 있을 때 고른다.
  - **R0 데이터 모델에서 미리 지원할 것**: 판매자 유형(BRAND / CONSIGNOR), 상품 유형(SKU_STOCK / SINGLE_ITEM).
- **제외**: C2C 리셀(한정판 개인 간 거래)
- **타깃**: 20~30대 패션 관심층, **모바일 웹 우선**(커머스 모바일 비중 76.4%)

### 3-2. 대안
리빙·라이프스타일 소규모 브랜드 입점형 오픈마켓. 정산·셀러 백오피스가 중심이다. 사용자가 백오피스에 더 흥미가 있거나, 패션 클론으로 보일 위험을 피하고 싶을 때 쓴다.

### 3-3. 컨셉 운영 원칙
- **"무신사 클론"으로 보이지 않게 한다.** 브랜드명, 로고, UI 톤을 독자적으로 만든다. 실존 브랜드·상표·상품 사진은 쓰지 않는다.
- 사이트 상단에 "포트폴리오 데모, 실제 판매·결제 없음"을 상시 표시한다. 결제는 PG 테스트 키로만 한다.
- 상품 데이터는 **생성기 스크립트**로 수천 SKU를 만든다(§13 R0). 이미지는 직접 생성한 것이나 라이선스가 명확한 것만 쓴다.

### 4-2. 공통 구조 (교차 확인)
- **페이지 골격**: 홈(기획전·개인화) → 카테고리/검색 → PLP → PDP → 장바구니 → 주문서 → PG 결제 → 완료 → 마이페이지(주문·배송·취소·반품). 10곳 모두 이 골격 위에 차별 요소를 얹는다.
- **읽기와 쓰기 분리**: 탐색은 캐시·읽기 모델, 주문·재고·결제는 원본 DB의 트랜잭션 정합성.
- **이벤트 기반 후속 처리**: 주문 확정 후 알림·배송·정산은 이벤트로 분리한다.
- **트래픽 스파이크 대비는 기능이 아니라 운영 절차다**: 사전 확장, 게임데이, 기능 끄기 스위치.
- **충돌 지점**: "Redis 분산락이 정답"이라는 통념과 Shopify의 MySQL 회귀가 다르다. → 재고 원천은 MySQL로 한다.

### 4-3. 이 프로젝트에 적용하는 원칙 3가지
1. **모듈러 모놀리스 + 경계 강제 + Outbox**
   - Spring Boot 앱 하나 안에 `catalog / inventory / cart / order / payment / shipping / claim / drop / (seller·settlement)` 모듈을 둔다.
   - 모듈 간 의존 규칙은 ArchUnit(또는 Spring Modulith)으로 CI에서 막는다.
   - 모듈 간 비동기 통신은 Transactional Outbox(폴링)로 시작한다.
   - "이 지표가 이 값을 넘으면 분리한다"는 분리 기준을 ADR로 남긴다.
   - 근거: Shopify, 컬리, 쿠팡의 전환 순서, 컬리 Dual Write 실패.
2. **읽기/쓰기 경로를 분리하고 각각 다른 품질 목표를 둔다**
   - 탐색: 카테고리 트리(표시용) + 속성 facet + 읽기 모델(캐시). 목표는 응답 시간.
   - 거래: 가격·재고·판매 상태를 **주문서 진입과 주문 시점에 원본으로 재검증**한다(Zero Payload 원리). 목표는 "초과판매 0건, 결제-주문 불일치 0건".
   - 원칙: "목록은 캐시여도 되지만 결제 금액은 캐시면 안 된다."
3. **핵심 여정 단위로 장애를 설계하고 부하를 시험한다**
   - 탐색 → 장바구니 → 주문 → 결제 → 환불 여정마다 장애 주입과 폴백을 정의한다.
   - 장애 예: 지연, 의존 서비스 다운, 웹훅 중복.
   - 폴백 예: 추천 실패 시 기본 목록, 배송 예정일 조회 실패 시 기본값.
   - k6 시나리오도 여정 단위로 만든다. 목표 TPS는 "가정 피크 × 4" 같은 산식으로 정한다.

### 6-2. 주문 모델 (R0에서 확정, R4 확장을 미리 고려)
- **주문(Order)** → **판매자주문(SellerOrder)** → **주문상품(OrderItem)** 3단 구조
- R1~R3에서는 판매자가 "직매입 자사" 1개뿐이지만, 구조는 처음부터 3단으로 만든다.
- 금액은 모두 **서버가 계산**한다. 상품가, 할인(쿠폰 안분 결과), 배송비, 결제 금액을 주문상품 단위까지 저장한다.

### 6-3. 주문 상태 머신 (초안. R0의 ADR로 확정)
```
CREATED → PAYMENT_PENDING ──(승인 성공)──> PAID → PREPARING → SHIPPED → DELIVERED → PURCHASE_CONFIRMED
              │                              │         │
              ├─(TTL 만료·결제 실패)→ EXPIRED   ├─(출고 전 취소)→ CANCELLED / PARTIALLY_CANCELLED
              │                              │
              └─(사용자 이탈)→ EXPIRED        └─(배송 후) RETURN_REQUESTED → RETURN_COLLECTING → RETURN_INSPECTING
                                                                         → REFUNDED | RETURN_REJECTED
                                                       EXCHANGE_REQUESTED → … → EXCHANGE_SHIPPED
```
- **상태 전이 규칙은 코드 한 곳에서만 정의한다.** 허용되지 않은 전이(역방향, 중복)는 무시하거나 거부한다. 웹훅 역순 도착에 대한 방어이기도 하다.

### 6-4. 재고 3계층
- **판매가능 재고**: 고객에게 보이는 수량
- **예약 재고(hold)**: 주문서 생성 시 잡고, **TTL은 PG 승인 시한(10분)에 맞춘다.** 만료 스케줄러가 해제한다.
- **물리 재고**: 입고·출고 기준
- **재고 원장(ledger)**: 모든 증감을 이벤트로 기록한다. 불변식: "원장 합계 = 현재 재고".
- 동시성 기본안은 **조건부 원자 UPDATE**(`qty >= n`, 영향 행 수 확인)다. 비교 대상은 비관적 락과 판매 단위 행 + `SKIP LOCKED`(Shopify식, 드롭 핫 SKU용) 두 가지로 압축한다(R3, ADR).
- **Redis는 재고의 진실 원천이 아니다.** 캐시·대기열·레이트리밋에만 쓴다.

### 6-5. 결제 흐름 (토스페이먼츠 공식 문서 기준)
1. 결제 요청 전에 서버가 `orderId`와 `amount`를 저장한다.
2. 클라이언트가 결제위젯으로 `requestPayment()`를 호출한다.
3. successUrl로 `paymentKey, orderId, amount`가 돌아온다. **서버에 저장한 금액과 대조**하고, 다르면 거부한다.
4. 서버가 시크릿 키(Basic 인증)로 결제 승인 API를 호출한다. **인증 후 10분 안에** 해야 한다(문서에 30분 표기가 섞여 있으므로 ADR에 기록하고 짧은 쪽을 따른다).
   - 모든 POST에 `Idempotency-Key`(최대 300자, 15일 유효)를 붙인다.
   - 처리 중에 재요청하면 `409 IDEMPOTENT_REQUEST_PROCESSING`이 온다.
5. 승인은 성공했는데 DB 저장이 실패하면 **보상 취소**한다. 그래도 남는 불일치는 일일 대사로 잡는다.
6. **웹훅**
   - 10초 안에 200으로 응답하고, 무거운 처리는 비동기로 한다.
   - 실패하면 최대 7회 재전송된다(1·4·16·64·256·1024·4096분 간격, 약 3일 19시간).
   - 로컬 개발에서는 ngrok이나 cloudflared로 받는다.
   - 웹훅 내용을 그대로 믿지 않는다. **결제 단건 조회로 재확인**하고(포트원 V2 문서의 권고와 같은 원리), 이벤트 ID로 멱등 처리한다.
7. **결제수단 범위**: 카드·간편결제(테스트). **가상계좌는 문서용 테스트 키로 테스트할 수 없으므로 제외한다**(설계 문서로만 다룬다).

### 6-6. 배송 연동
- **실제 송장 발번은 택배사 계약이 필요하므로 하지 않는다**(CJ대한통운 Open API는 영업 승인이 필요하고, 굿스플로 출력은 계약 정보가 일치해야 한다).
- `CarrierPort` 인터페이스와 구현체 두 개:
  - **모의 택배사(MockCarrier)**: 발번, 상태 이벤트 생성. 지연·역전·누락·"미도착인데 배송완료" 같은 이상 상황을 주입할 수 있다.
  - **실제 배송조회 어댑터**: 딜리버리트래커 또는 스마트택배. 키 발급과 요금·호출 제한을 R1 착수 시 확인한다.
- 배송 상태는 폴링(필요하면 콜백 병행)으로 갱신한다. 역방향 전이는 무시하고, 마지막 갱신 시각을 표시한다.
- "실제로는 이렇게 연동되고, 포트폴리오에서는 이렇게 대체했다"를 README와 ADR에 명시한다.

### 6-7. 취소·반품·환불 규칙
- 출고 전에는 취소, 출고 후에는 반품·교환으로 상태 흐름을 분리한다.
- **부분취소**: PG 부분취소 API(`balanceAmount`, `isPartialCancelable` 확인), 쿠폰 안분액 재계산, 배송비 재계산, 재고 복구, 쿠폰 복구(정확히 한 번)
- **전자상거래법**(해설 자료 기준, 조문 원문은 R1 착수 시 국가법령정보센터에서 확인):
  - 수령 후 7일 이내 청약철회
  - 반환받은 날부터 3영업일 이내 환급
  - 지연 시 지연배상금
  - 이 기한들을 **SLA 추적 배치**로 구현한다.
- 반품은 택배 연동이 아니라 별도 흐름(신청 → 회수 → 검수 → 환불)으로 둔다.

### 6-8. 판매자 정산 (R4)
- 판매자별 배송비·묶음배송, 플랫폼 부담과 판매자 부담 쿠폰의 안분
- 구매확정(수동 또는 N일 후 자동, 배치) → **정산 원장** → 정산 배치(Spring Batch, **재실행 안전**) → 정산 명세
- PG 거래 대 주문 원장 일일 대사 확장, 불일치 처리 화면
- 규제 동향: 대규모유통업법 개정안이 2026-09 정무위를 통과했다(직매입 35일, 위수탁 20일, 확정 여부 미정). **참고만 하고 핵심 근거로 쓰지 않는다.**

| **④ AI 활용 생산성·검증 프로세스** [중] (모든 축에 걸친 필수 증빙) | AI를 빠르게 쓰되 결과를 검증·책임진다 | §12의 규칙 파일, PR의 "AI 제안 / 내 판단 / 검증", AI 오류 사례집, 생산성 기록(리드타임, AI 오류를 잡은 건수, 테스트 통과율), 핵심 모듈의 **AI 없이 재구현**, 설명 문서 | R0~ |

- **사실로 쓰는 것**: 기업들이 AI 도구 활용·결과 검증 역량을 전형과 신입 자격요건에서 본다(무신사·컬리·현대오토에버, 신입 공고 FE 5/11, BE 6/13, 검증 명시 4건).
- **가설로 표기하는 것**: 하네스(규칙 파일·AI 로그) 형식 자체가 가점이 된다. 확인한 공고 중 하네스를 언급한 곳은 0건이다.

## 9. 기술 스택

### 9-1. 사용자 원안(React + Vite + Spring Boot + MySQL) 검토 결론
- **커머스·SI 표적에는 타당하다.** 근거:
  - 키워드 수: 잡코리아 React 893 / Spring Boot 506, 사람인 React 916 / Spring Boot 588
  - 무신사·컬리 공고 원문의 스택
  - 신입 백엔드 표본 13건 중 10건이 Java/Spring
  - 위시켓 외주 공고
- **보완이 필요하다**:
  - TypeScript는 사실상 필수다.
  - MySQL은 **8.4 LTS**로 쓴다(8.0은 EOL).
  - Spring Boot는 **4.1.x**로 쓴다(3.5는 OSS 지원 종료, 4.0은 2026-12-31 종료).
  - Redis, 테스트·관측 도구를 더한다.
- **초기 스타트업 표적이면 덜 맞는다.** 그쪽 주니어 공고는 Next.js·FastAPI·PostgreSQL 계열이 많다(§18 Q1).

### 9-2. 필수
| 영역 | 선택 |
|---|---|

- Spring Boot 3.5·4.0, MySQL 8.0으로 시작
- Redis를 재고의 단일 진실 원천으로 쓰기
- 실결제·실송장 시도, 운영 키를 저장소에 두기

- 시연 단계에서 ALB·ElastiCache·Multi-AZ·관리형 OpenSearch 상시 운영

- **토스 테스트 서버에 부하 테스트하기**(부하 테스트에는 PG 스텁을 쓴다)

- "락 비교 수치"만으로 차별화를 주장하는 README

MyBatis, Oracle SQL 기초, 정보처리기사·SQLD. 프로젝트 스택은 바꾸지 않는다.

## 11. 품질·검증 전략

### 11-1. 불변식 (모든 테스트·부하·장애 시나리오가 끝날 때 자동 검사)
1. 초과판매 0건: 판매 수량 ≤ 입고 수량, 재고 ≥ 0
2. 재고 원장 합계 = 현재 재고
3. 결제-주문 불일치 0건: PAID 주문마다 승인된 PG 거래가 정확히 1건, 금액 일치
4. 환불 합계 ≤ 결제 금액, 부분취소 후 남은 금액 = PG 잔액(`balanceAmount`)
5. 쿠폰 사용 1회, 복구 1회
6. 예약 재고는 TTL 뒤 반드시 해제
7. 상태 전이는 허용 목록 안에서만 일어난다

### 11-2. 테스트 구성
| 층 | 도구 | 대상 |
|---|---|---|
| 단위 | JUnit 5, Vitest + RTL | 금액 계산, 안분, 상태 전이, 컴포넌트 |
| 통합 | Testcontainers(MySQL·Redis) | 주문·결제·재고 흐름, 멱등, 웹훅 |
| 동시성 | JUnit + 스레드 풀 / k6 | E01·E02·E16·E33 |
| 아키텍처 | ArchUnit / Modulith | 모듈 의존 규칙 |
| 장애 주입 | Toxiproxy, 웹훅 리플레이어, MockCarrier | E09~E14·E23·E29·E37·E38 |
| E2E | Playwright | J1~J4 |
| 부하 | k6(여정 시나리오, PG 스텁) | 목표 TPS = 가정 피크 × 4, 불변식 유지 확인 |

### 11-3. 리포트 (docs/reports)
- **부하 리포트**: 시나리오, 환경, 목표 산식, 결과, 병목 분석, 개선 전후
- **장애 훈련 리포트**: 주입한 장애, 기대 동작, 실제 동작, 수정, 재검증
- **대사 리포트**: 일자별 불일치 건수와 유형, 처리 결과
- **FE 성능 리포트**: 개선 전후 수치

### 11-4. 비즈니스 지표 (R2 필수)
- 주문 수, 결제 성공률·실패율, 웹훅 수신 지연, 대사 불일치 건수, 예약 만료 건수
- 여정 퍼널: 탐색 → 상세 → 장바구니 → 주문 → 결제 전환. 도메인 이벤트와 Outbox를 재사용한다.
- FE 행동 로그(페이지·클릭·이탈)는 R3 선택이고, 개인정보를 최소화한다.
- A/B 실험은 R5 선택이고, 기능 플래그와 버킷팅 장치만 만든다. **실사용자가 없으면 통계적 결론을 낼 수 없는 데모**라고 명시한다.

## 12. AI 활용·검증 프로세스 (바이브 코딩 운영 규칙)

### 12-1. 기능 하나를 만드는 표준 절차
1. **명세**: 이슈에 목적, 수용 기준, 관련 돌발 상황 ID(E01 등), 불변식을 적는다.
2. **컨텍스트**: CLAUDE.md의 규칙(모듈 경계, 금지 사항, 테스트 규칙)과 관련 ADR을 AI에게 준다.
3. **생성**: AI가 구현과 테스트를 제안한다.
4. **검증**: 테스트 통과, 불변식 검사, 아키텍처 테스트, SAST·비밀값 스캔을 확인하고, **직접 코드를 읽는다.**
5. **PR 기록**: "AI 제안 / 내 판단(채택·수정·거부와 이유) / 검증 방법과 결과" 템플릿을 채운다.
6. **결정 기록**: 설계 선택이 있었으면 ADR을 쓴다.
7. **오류 기록**: AI가 틀린 부분은 `docs/ai/mistakes.md`에 쌓는다(유형·발견 방법·재발 방지 규칙). 재발 방지 규칙은 CLAUDE.md에 반영한다.

### 12-2. CLAUDE.md 필수 내용 (R0)
- 프로젝트 목적과 이 기획서 링크, 모듈 구조와 의존 규칙
- 금지 사항(§9-4), 금액·재고 코드 규칙(서버 계산, 원장 기록, 멱등)
- 테스트 규칙: 금액·재고·상태 변경 코드는 테스트 없이 머지하지 않는다.
- 비밀값·개인정보 규칙

### 12-3. 면접 방어 장치
- **AI 없이 재구현**: 재고 예약, 결제 승인, 웹훅 처리 3개 모듈을 R1~R2 사이에 AI 없이 다시 구현한다. 차이와 배운 점은 `docs/ai/rebuild-*.md`에 남긴다.
- **설명 문서 → 모의 면접 질문 목록**: ADR마다 꼬리 질문 3~5개와 답을 `docs/interview/`에 쌓는다.
- 포트폴리오 서술은 **판단 과정** 중심으로 쓴다(신입 공고 근거: "기술적 고민과 문제 해결 과정", "기술적 판단을 포트폴리오로 설명").

### 12-4. 생산성 기록
이슈 생성에서 머지·배포까지의 리드타임, AI 오류를 잡은 건수와 단계, 테스트 통과율, 릴리스 주기를 기록한다.

## 19. 부록: 조사·합의 과정 기록

### 19-1. 절차
1. **1단계 독립 조사**: A·B·C가 서로의 결과를 보지 않고 각자 조사해 제안 3개와 컨셉 3개를 냈다(`research/A.md`, `B.md`, `C.md`).
2. **2단계 교차검증**: 각 에이전트가 다른 둘의 제안 6개와 자기 제안 3개를 평가했다. 핵심 수치를 직접 재확인했다(A 18건, B 22건, C 15건). 수치 충돌을 해소하고 편향을 점검했다(`research/review/`).
3. **합의 1차 투표**: 코디네이터가 합의안 초안(`research/consensus/draft_v1.md`)을 만들고, 각 에이전트가 신입 공고 보강 조사(총 36건)를 한 뒤 섹션별로 투표했다.
4. **결과**: **반대 0.** 모든 섹션이 동의 또는 양립 가능한 조건부 동의였으므로 순환 재검증 없이 합의가 성립했다.

### 19-2. 1단계 제안의 흐름
| 에이전트 | 1순위 | 2순위 | 3순위 | 합의에서의 위치 |
|---|---|---|---|---|
| A | 드롭형 패션 + AI 하네스·정합성 | 멀티셀러 정산·대사 | AI 네이티브(검색·RAG) | 1·2·3순위로 병합 |
| B | 패션 드롭 + 정합성 측정 + AI 검증 | 입점 오픈마켓 정산·백오피스 | AI 네이티브 뷰티 | 뷰티 컨셉 기각, AI 기능은 3순위로 흡수 |
