0.1 한 문단 개요

가상 브랜드 패션 편집숍(사이즈×컬러 SKU)을 만드는 1인 풀스택 포트폴리오다. 목표는 한국 신입 개발자 채용에서 "AI로 만들었다"가 아니라 "AI로 만든 커머스를 검증하고, 운영하고, 돈과 재고가 외부 시스템(PG·택배)까지 맞는다는 것을 증명했다"를 보여주는 것이다. 스택은 React 19 + TypeScript / Spring Boot 4.1 + Java 21 / MySQL 8.4 / Redis이며, 모듈러 모놀리스로 만든다. 첫 정지점 R1은 구매 여정 하나를 실패 경로까지 정합성 있게 만드는 것이고, 기능 확장은 그 뒤 릴리스로 나눴다. 클라우드 배포는 지원 일정이 생길 때까지 미루고, 그 전에는 로컬과 CI에서 배포 가능성을 증명한다.

0.3 핵심 결정 7가지

  1. R1 = 구매 여정 하나 + 실패 경로 + 정합성 핵심 + FE 기본 품질. 쿠폰·부분취소·검색·필터·실제 배송조회·클레임은 R2b로 미뤘다. 넓이를 깊이로 바꾼 것이지 일이 줄어든 것은 아니다. [2.3]
  2. 결제 시도(PaymentAttempt) 모델. 주문 하나에 결제 시도가 여러 개 생길 수 있고, 주문의 current_attempt_id가 가리키는 시도만 승인할 수 있다. [4.3, 5장]
  3. 조건부 상태 전이 + 승인 전 paymentKey 저장. PAYMENT_PENDING → CONFIRMING 전이와 paymentKey 저장을 한 트랜잭션에서 한다. 위젯 키로는 orderId 조회가 안 되므로 복구는 paymentKey에 의존한다. [5.2]
  4. 실시간 경로는 "없으면 버그"인 것만 막는다. 남는 불일치는 복구 작업자 → 일일 대사 → 운영자 큐 순으로 잡는다. [3.1]
  5. 고객 취소는 CANCEL_REQUESTED 중간 상태를 거친다. 출고와의 경합을 막고, PG 취소가 실패해도 되돌릴 수 있게 한다. [5.8]
  6. 주문 모델은 2단(주문 → 주문상품) + 판매자 스냅샷. 판매자주문 계층은 입점 판매자가 생기는 R4에서 이관한다. [4.1]
  7. 배포는 최대한 미룬다. 지원을 결정하면 "배포 창"(1~2주)을 연다. 그 전에는 CI의 프로덕션 이미지 스모크와 배포 런북으로 "배포할 수 있다"까지만 증명한다. [9장]

3.1 아키텍처 원칙 [원문 §4-3]

원칙내용
① 모듈러 모놀리스 + 경계 강제 + Outbox(비동기 경계에만)Spring Boot 앱 하나에 모듈을 나누고, 모듈 간 의존 규칙은 ArchUnit(또는 Spring Modulith)으로 CI에서 막는다. Outbox는 정말 비동기여야 하는 경계에만 쓴다(모듈 내부까지 이벤트로 만들면 추적·디버깅 비용이 먼저 커진다). R0에서 모듈 간 동기 호출 목록을, R2a 착수 시 Outbox 이벤트 목록을 ADR로 확정한다. 분리 기준("이 지표가 이 값을 넘으면 분리")도 ADR에 남긴다. MSA·K8s는 하지 않는다
② 읽기/쓰기 경로 분리탐색은 카테고리 트리 + facet + 읽기 모델(캐시), 목표는 응답 시간. 거래는 가격·재고·판매 상태를 주문서 진입과 주문 시점에 원본으로 재검증(Zero Payload), 목표는 초과판매 0건과 결제-주문 불일치 0건. "목록은 캐시여도 되지만 결제 금액은 캐시면 안 된다"
③ 핵심 여정 단위 장애 설계·부하 시험여정마다 장애 주입(지연, 의존 서비스 다운, 웹훅 중복)과 폴백(추천 실패 시 기본 목록 등)을 정의한다. k6 시나리오도 여정 단위로 만든다
④ 실시간 경로는 핵심만, 남는 불일치는 대사와 운영자 큐로실시간 경로에서는 없으면 버그가 되는 것(초과판매, 이중 승인, 정상 결제 중 예약 해제, 만료 주문 부활)만 막는다. 나머지 드문 불일치는 복구 작업자 → 일일 대사 → 운영자 큐 순서로 잡는다

4.1 주문 모델 [원문 §6-2, ADR-003]

  • 주문(Order) → 주문상품(OrderItem) 2단 구조로 시작한다.
  • 판매자 정보는 두 곳에 둔다.
    • 상품의 seller_id: 지금 이 상품을 파는 판매자. 바뀔 수 있다.
    • 주문상품의 판매자 ID: 주문 시점의 판매자 스냅샷. 상품의 판매자가 바뀌어도 주문 기록은 바뀌지 않는다.
    • R1~R3의 판매자는 "직매입 자사" 한 행뿐이다.
  • 금액은 모두 서버가 계산한다. 상품명, 옵션, 단가, 할인(R2b부터 쿠폰 안분 결과), 배송비, 결제 금액을 주문상품 단위까지 스냅샷으로 저장한다.
  • 주문상품의 내용(SKU, 수량, 금액 스냅샷, 판매자 스냅샷)은 생성 뒤 바뀌지 않는다. 재예약(5.3)이 원 주문과 어긋날 수 없게 하는 근거다. 취소·부분취소·반품은 주문상품을 고치지 않고 별도 기록(취소 원장, 클레임)에 남긴다.
  • 3단 구조(주문 → 판매자주문 → 주문상품)는 R4에서 이관한다. 주문상품 위에 판매자주문 계층을 더하는 작업이며 주문상품 내용은 그대로 둔다. 판매자가 하나뿐인 R1~R3에서 3단 구조는 조회만 복잡하게 하고, R3에서 멈추면 끝내 필요 없다.

4.4 상태 전이 공통 규칙 [원문 §6-3]

  • 전이 규칙은 코드 한 곳에서만 정의한다. 허용되지 않은 전이(역방향, 중복)는 무시하거나 거부한다. 웹훅 역순 도착에 대한 방어이기도 하다.
  • 종결 상태(EXPIRED, CANCELLED)는 어떤 경우에도 되살리지 않는다. 종결된 주문에 승인된 돈이 생기면 주문이 아니라 결제 시도 단위로 처리한다(ORPHANED → 보상 취소).
  • 취소와 출고의 경합: 취소 요청과 출고 준비가 모두 "PAID일 때만" 조건부 전이다. 동시에 일어나면 한쪽만 이기고 진 쪽은 거부·안내한다(E45). PG 취소는 CANCEL_REQUESTED로 바꾼 뒤에 호출하므로 PG 취소 도중에 출고가 끼어들 수 없다.
  • 상태 이름과, 그 상태를 주문에 둘지 결제 시도에 둘지는 ADR-004·006에서 확정한다.

예약 TTL은 운영 정책값

  • 토스의 10분은 결제 인증 후 승인 API를 호출해야 하는 유효 시간이다. 주문 생성 시점부터 세는 시간이 아니다.
  • 예약 TTL = 결제창 체류 + 승인 유효 시간(10분) + 여유. 토스 결제 유효 시간(30분, 기산점은 R0 확인)을 넘길 이유는 없다. 값은 ADR-005에서 정한다.
  • 예약이 먼저 풀려도 버그가 아니다. CONFIRMING 전이 때 재고를 다시 잡기 때문이다. 다만 재고가 없으면 승인하지 못하므로 TTL은 고객 경험과 재고 회전 사이의 정책 선택이다. 드롭(R3)에서는 짧게 조정할 수 있다.

동시성 제어

  • 기본안은 조건부 원자 UPDATE(qty >= n, 영향 행 수 확인). 여러 SKU 주문은 SKU ID 정렬 후 잠금(E02).
  • 비교 대상은 비관적 락과 판매 단위 행 + SKIP LOCKED(Shopify식, 드롭 핫 SKU용)로 압축한다(R3, ADR).
  • Redis는 재고의 진실 원천이 아니다. 캐시·대기열·레이트리밋에만 쓴다.

가상계좌는 문서용 테스트 키로 테스트할 수 없다결제수단은 카드·간편결제만. 가상계좌는 설계 문서로만

5.6 보상 취소 [원문 §6-5 7단계]

  • 대상: 승인은 성공했는데 DB 저장이 실패한 경우(E10), 종결된 주문에 승인이 도착한 경우(ORPHANED, E50).
  • 절차: 취소 요청을 먼저 기록 → 시도 ID로 정해진 멱등키로 취소 API 호출 → 타임아웃이면 같은 멱등키로 재시도. 남는 불일치는 일일 대사(R2a)로 잡는다.
  • R2a 취소 실패 경로(타임아웃·서버 종료, CANCEL_UNKNOWN, 운영자 큐)를 완성한다.

5.7 웹훅 [원문 §6-5 8단계]

  • 10초 안에 200으로 응답하고 무거운 처리는 비동기로 한다. 로컬에서는 ngrok이나 cloudflared로 받는다.
  • 웹훅 내용을 그대로 믿지 않는다. paymentKey로 결제를 재조회하고 이벤트 ID로 멱등 처리한다.
  • 종결된 주문에 승인 완료(DONE) 웹훅이 오면 주문을 되살리지 않고 보상 취소로 보낸다.
  • R1은 중복·위조, R2a는 역순·지연 재현(리플레이어).

5.8 고객 출고 전 전체취소 [원문 §6-7] R1

#처리
1조건부 전이 PAID → CANCEL_REQUESTED와 취소 요청 기록을 한 트랜잭션에서. 요청 시각이 환급 기한의 기산점. 이때부터 출고 준비가 막힌다(E45)
2트랜잭션 밖에서 PG 취소 API 호출. 멱등키는 cancel-{cancelRequestId}
3성공하면 CANCELLED, 같은 트랜잭션에서 재고 복구(정확히 한 번, 원장 기록). 환급 완료 시각 기록
4타임아웃·결과 불명이면 같은 멱등키로 재시도. 그래도 불명이면 CANCEL_REQUESTED에 두고 복구 작업자가 조회로 확정
5명확한 실패면 PAID로 되돌리고 고객과 운영자에게 알림. "이미 취소됨" 같은 응답은 paymentKey 조회로 확인해 처리(응답은 R0 확인)
6오래 풀리지 않는 건의 운영자 큐 이관은 R2a(E49)
중간 상태를 두는 이유 상태를 먼저 CANCELLED로 바꾸면 PG 취소가 실패해도 종결 상태라 되돌릴 수 없고 고객은 환불을 받지 못한다. PG 취소를 먼저 부르면 그 사이에 출고가 끼어든다. 보상 취소(결제 시도의 CANCEL_REQUESTED)와 같은 원리를 주문에도 쓴다.

부분취소 R2b는 쿠폰과 함께 만든다. PG 부분취소 API(balanceAmount, isPartialCancelable), 쿠폰 안분액·배송비 재계산, 재고·쿠폰 복구(각각 정확히 한 번). 쿠폰 없이 부분취소를 먼저 만들면 안분 계산 때문에 다시 만들어야 한다.

6외부 연동과 법령

6.1 배송 연동 [원문 §6-6]

  • 실제 송장 발번은 하지 않는다. 택배사 계약이 필요하다(CJ대한통운 Open API는 영업 승인, 굿스플로 출력은 계약 정보 일치 필요).
  • CarrierPort 인터페이스와 구현체 두 개.
    • MockCarrier: R1은 발번과 상태 변경(배송중·배송완료)만. R2b에서 지연·역전·누락·"미도착인데 배송완료" 주입을 더한다.
    • 실제 배송조회 어댑터(R2b): 딜리버리트래커 또는 스마트택배. 키 발급과 요금·호출 제한은 R2b 착수 시 확인.
  • 배송 상태는 폴링(필요하면 콜백 병행)으로 갱신. 역방향 전이는 무시하고 마지막 갱신 시각을 표시한다.
  • "실제로는 이렇게 연동되고 포트폴리오에서는 이렇게 대체했다"를 README와 ADR에 명시한다.

6.2 취소·반품·환불과 전자상거래법 [원문 §6-7]

출고 전에는 취소, 출고 후에는 반품·교환으로 상태 흐름을 분리한다. 반품은 택배 연동이 아니라 별도 흐름(신청 → 회수 → 검수 → 환불)이다.

전자상거래법(법률 제21312호, 2026-01-20 일부개정, 2026-07-21 시행). 제18조는 국가법령정보센터에서 원문을 확인했다.

  • 따라서 R1의 출고 전 취소에도 환급 기한 추적이 필요하다. 카드 취소는 즉시 처리되지만, 취소 요청 시각과 환급 완료 시각을 기록하고 3영업일을 넘으면 경고하는 테스트를 둔다(E21).

  • 반품까지 포함한 환급 SLA 추적 배치는 R2b.

  • 용도: R1 결제 실패 경로 테스트(타임아웃·실패·결과 불명 재현), CI, 부하 테스트. CI는 토스에 의존하지 않고 시크릿도 필요 없다.
  • 리스크: 스텁이 실제와 다르면 테스트가 통과해도 실제로는 깨질 수 있다. 대응: 로컬 시연과 데모 영상의 J1은 실제 테스트 키로 진행하고, 배포 창에서 배포 환경 J1을 실제 테스트 키로 한 번 더 확인한다.

7.4 부하 시험 기준 [원문 §11-3]

  • "가정 피크 × 4"는 쓰지 않는다. 실사용 트래픽이 없는 데모에서 피크는 정의할 수 없다.
  • 시험 전에 허용 기준을 정한다(예: 여정별 p95 지연 상한, 오류율 상한. 값은 R3 착수 시 ADR).
  • 한계 = 허용 기준이 처음 깨지는 부하. 느리게 버티는 시스템도 성공처럼 보일 수 있어서 "불변식만 지키는 최고 부하"를 한계로 보지 않는다.
  • 한계를 넘긴 부하에서도 불변식이 지켜지는지는 따로 확인한다.
  • 결과는 그 데이터·인스턴스·시나리오의 측정값으로만 쓴다. 리포트에 시나리오 비중, 데이터 크기, 실행 환경, 시험 시간, 병목을 남긴다. 배포 창 전에는 로컬에서 측정하고 환경을 명시한다.

9.3 배포 창 전까지의 "배포 가능성" 증거 [원문 §15-3]

  • CI에서 프로덕션 이미지 빌드·기동·스모크 테스트(R1)
  • 깨끗한 환경 재현: 클론 → .env 작성 → docker compose up → README대로 스모크(R1)
  • 배포 스크립트와 배포 런북 초안(R1). 런북에 9.2의 1~5를 단계별로 미리 적어 둔다. 롤백 절차(R2a)
  • 그레이스풀 셧다운과 expand/contract 마이그레이션(R2a)
  • 이 증거는 "배포할 수 있다"까지만 증명한다. "배포해서 운영했다"는 배포 창 이후에만 쓴다.

14검토 포인트

개발자 관점에서 판단이 갈릴 수 있는 결정을 모았다. 각 항목의 "결정·이유·대가"는 기획서 내용이다. 기획서에 없이 이 보고서가 덧붙인 판단은 (보고서 추론)·(보고서 정리)로 표시했다. "검토 질문"은 이 보고서가 검토자에게 묻는 것이며, 기획서에 명시되지 않은 부분을 묻는 경우 그렇게 적었다.

RP-1. R1 범위: 넓이 대신 깊이 [2.3, 원문 §19-6]
결정R1을 구매 여정 하나 + 실패 경로 + 정합성 핵심 + FE 기본 품질로 한다. 쿠폰·부분취소·검색·필터·실제 배송조회·클레임은 R2b로
이유바이브 코딩 속도로 기능 13개를 한 번에 만들면 기능마다 검증과 이해가 얕아진다. 지원 시점이 정해지지 않아 R1에서 멈출 가능성을 배제할 수 없다. 최종 범위는 R2b까지 가면 같다
대가R2를 둘로 나눈다. 작업 줄 수는 v0.1과 비슷하다(기능 수는 줄고 결제 설계·테스트는 늘었다)
검토 질문: 13개 작업이 1인 + AI 도구로 첫 정지점에 적정한가? 일정 초과 시 자르는 순서(데모 영상 → 최소 배송 상태·E45 → Playwright)가 맞는가?
RP-2. 이전 결제 창의 늦은 성공은 승인하지 않는다 [5.3, E47]
결정현재 시도가 아닌 시도의 성공 URL은 REJECTED로 두고 승인 API를 호출하지 않는다
이유정합성을 편의보다 앞세운 선택이다(ADR-006). 현재 시도 포인터 하나로 이 주문에 연결될 결제를 정한다. 승인 API를 호출하지 않으므로 그 결제는 문서상 완료되지 않는다(결제수단별 고객 화면 표시는 R0에서 확인)
대가고객이 이전 탭에서 결제를 마쳤어도 다시 결제해야 한다(ADR-006에 기록)
검토 질문: 정합성을 편의보다 앞세운 이 UX 트레이드오프를 받아들일 수 있는가?
RP-3. 예약 만료와 결제 진행의 직렬화 [4.5, E05]
결정예약 만료 배치와 CONFIRMING 전이(재예약 포함) 모두 주문 행을 SELECT … FOR UPDATE로 잠그고 처리한다. 동시성 테스트로 고정
이유상태를 읽고 따로 해제하면 그 사이에 전이가 끼어 결제 도중 예약이 풀린다(v0.1 버그)
대가(보고서 추론) 배치가 주문 행을 잠그므로 만료 대상이 많으면 결제 경로와 경합할 수 있다
검토 질문: 주문 행 잠금과 SKU 행 잠금(E02, SKU ID 정렬)의 획득 순서를 ADR-005에 명시해야 하는가? 배치는 건별 트랜잭션이 맞는가? (둘 다 기획서에 명시되지 않음)
RP-4. 고객 취소의 중간 상태 [5.8, E45, E49]
결정PAID → CANCEL_REQUESTED(조건부, 출고 차단) → PG 취소(cancel-{cancelRequestId}) → CANCELLED. 명확한 실패면 PAID 복귀, 불명이면 유지 후 복구 작업자
이유먼저 CANCELLED로 바꾸면 PG 실패 시 되돌릴 수 없고, PG를 먼저 부르면 출고가 끼어든다
대가(보고서 정리) 주문 상태가 하나 늘고, 취소 처리 중 화면(R1 작업 10)과 복구 작업자의 취소 확정 경로가 필요하다
검토 질문: 취소 진행 상태를 주문 상태로 둘지, 별도 취소 요청 엔티티의 상태로만 둘지(ADR-004에서 확정 예정)에 의견이 있는가?
RP-5. paymentKey 선저장과 조회 기반 복구 [5.1, 5.2, E48]
결정CONFIRMING 전이와 같은 트랜잭션에 paymentKey를 저장하고, 승인 호출은 트랜잭션 밖에서 한다. 결과 불명은 복구 작업자가 paymentKey 조회로 확정
이유결제위젯 키로는 orderId 조회 API를 호출할 수 없다. 전이 직후 서버가 죽어도 paymentKey가 남아 있어야 복구할 수 있다
대가상태별 조회 응답이 문서만으로 불분명해 R0 실호출 전에는 조치표를 확정할 수 없다
검토 질문: 복구 작업자를 R1 단순판과 R2a 완성판으로 나눈 경계(R1: DONE·명확한 미승인만 처리, 나머지는 상태 유지 + 경고)가 R1 정지점에서 충분한가?
RP-6. 실시간 경로와 대사의 경계 [3.1 원칙 ④, 2.6]
결정실시간 경로는 초과판매, 이중 승인, 정상 결제 중 예약 해제, 만료 주문 부활만 막는다. 나머지는 복구 작업자 → 일일 대사 → 운영자 큐
이유분산 시스템의 예외는 끝이 없어 모두 상태 머신으로 처리하면 설계가 끝없이 커진다. 실제 커머스·PG 운영도 대사를 최후 방어선으로 둔다
대가(보고서 추론) 대사가 생기는 R2a 전까지(R1 정지점) 복구 작업자가 확정하지 못한 불일치는 경고 로그로만 드러난다
검토 질문: 실시간으로 막을 네 가지 목록에 빠진 것이 있는가?
RP-7. 실패 경로 테스트를 PG 스텁에 의존 [7.3]
결정타임아웃·실패·결과 불명은 PG 스텁(WireMock 또는 자체 제작)으로 재현한다. 스텁 응답은 R0 실호출 응답으로 만든다. CI는 토스에 의존하지 않는다
이유타임아웃·결과 불명은 실서버로 재현할 수 없고, CI가 토스를 부르면 시크릿이 필요해진다
대가스텁이 실제와 다르면 테스트가 통과해도 실제로는 깨질 수 있다. 시연·영상·배포 창의 J1을 실제 테스트 키로 돌려 보완한다
검토 질문: WireMock과 자체 제작 중 어느 쪽이 나은가? 스텁과 실제의 차이를 R2a 이전에 더 줄일 방법이 있는가?
RP-8. 주문 2단 모델과 R4 이관 [4.1]
결정R0~R3은 주문 → 주문상품 2단 + 판매자 스냅샷. R4에서 판매자주문 계층을 추가하는 이관을 한다
이유판매자가 하나뿐인 동안 3단 구조는 조회만 복잡하게 하고, R3에서 멈추면 필요 없다. 실데이터가 없어 이관 비용이 작고 이관 자체가 검증 소재가 된다
대가R4에서 마이그레이션과 6가지 이관 검증이 필요하다
검토 질문: R1~R3에서 판매자 스냅샷 외에 미리 둬야 이관이 쉬워지는 것이 있는가?
RP-9. Outbox는 R2a부터, 비동기 경계에만 [3.1, 3.7]
결정R1은 모듈 간 동기 호출(목록은 ADR-001). Outbox(폴링)는 R2a에서 정말 비동기여야 하는 경계에만 도입
이유모듈 내부 호출까지 이벤트로 만들면 추적·디버깅 비용이 먼저 커진다
대가R1에는 이중 쓰기 방어(E14)가 없다
검토 질문: R1 범위(알림 등 후속 처리가 거의 없음)에서 동기 호출만으로 충분한가?
RP-10. 스택 버전과 QueryDSL [3.5, 3.6]
결정Spring Boot 4.1.x, Java 21, MySQL 8.4 LTS. QueryDSL은 OpenFeign 포크를 쓰되 R0에서 빌드 확인 후 확정, 안 되면 Specification·JPQL
이유3.5·4.0·MySQL 8.0의 지원 종료. 한국 커머스 공고에 "JPA/QueryDSL"이 직접 나온다
대가Boot 4.x 생태계 호환성 리스크. 원본 QueryDSL 유지보수 둔화
검토 질문: 신입 포트폴리오에서 Boot 4.1 채택이 유리한가, 3.x 계열 경험을 보여주는 쪽이 나은가?
RP-11. 클라우드 배포를 미룬다 [9장]
결정지원 결정 전까지 로컬과 CI에서만. CI 프로덕션 이미지 스모크·배포 런북으로 "배포할 수 있다"까지 증명. 지원 결정 시 1~2주 배포 창
이유사용자 결정(Q2·Q3). 지원 전에 클라우드가 꼭 필요한 작업이 계획에 없다. 크레딧·무료 플랜은 가입 시점부터 흐른다

검토 질문: 배포 창 9단계(9.2) 중 미리 해 둘 것이 있는가? 1~2주가 현실적인가?

  4. v0.1 작성 → 외부 비평(ChatGPT) 3회 → v0.2. 합의 항목 중 바뀐 3건(R1 범위, 주문 모델, 리커머스 유형 선설계)은 사용자 지시로 재투표 없이 반영했다.

B.2 교차검증·합의에서 정해진 것 [원문 §19-2~19-5]

구분내용

B.4 외부 비평 요약 [원문 §19-7]

구분내용
받아들인 것예약 TTL을 승인 시한과 같게 둔 설계 오류, "모든 섹션에서 합의"라는 과장, R1 과대, 주문 모델 선행 설계, 부하 피크의 근거 부재, AI 지표의 분모 문제, QueryDSL 유지보수 상태, 법령 확인 시점 불일치, 결제 시도 ID, 멈춘 주문의 복구 작업자, 불변식의 단위, 보상 취소 실패 경로, 부하 한계의 사전 정의, 이관 검증 항목과 판매자 스냅샷, AI 기록의 완전성
반박한 것프로필이 조사 중 추가된 가정이라는 주장(사용자 답변이었다), 법령 확인 순서가 뒤집혔다는 주장(실제 문제는 문서 내부 불일치), 로컬 k6 결과를 용량처럼 제시한다는 주장, 패션을 채용 근거로 정당화했다는 주장, 30분을 확정 보장으로 썼다는 주장, 10분 재시도에 같은 멱등키가 빠졌다는 주장(E09에 있었다), 취소 전 배송 차단 필요(상태 머신이 이미 막는다), 예약 세대 개념(현재 시도 포인터와 불변 주문상품으로 대체), PR 수 분모의 역할(비율 지표가 아니라 고르지 않았다는 증명)
재검토로 되돌린 양보결제 복구 설계 전부를 R1에 넣기 → R1과 R2a로 분할. 축 ④에서 "생산성" 삭제 → 유지

양쪽이 놓쳤다가 찾은 것토스 10분의 기산점(인증 후), orderId 조회 API의 위젯 키 제한, 제18조 ② 3호의 출고 전 취소 기산점
