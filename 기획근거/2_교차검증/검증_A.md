## 2. 제안별 평가

판정 기준: **수용**(그대로 합의안 후보), **조건부 수용**(수정·축소 조건 충족 시), **기각**(단독 제안으로는 채택하지 않음, 아이디어 일부는 흡수 가능).

### B1. "검증된 바이브 코딩": 패션 버티컬 + 주간 한정 드롭, 정합성을 숫자로 증명
- **신빙성: 상.** 핵심 근거인 올리브영 이중 카운터, 컬리 VSMS, 인프런 포화, 토스 문서, Lightsail을 재확인했고 모두 일치했다. 약점은 수강생 PR 미러(S43, 하)와 무신사 1차 인원(700 vs 1,700) 정도다.
- **논리: 중상.** 세 보고서 중 유일하게 "재고 락은 포화"라는 반대 증거를 1단계에서 정량으로 제시하고 차별화 조건(측정·종단 정합성·장애 재현·ADR)을 도출했다. 다만 그 차별화 조건조차 이미 공개 저장소에 존재한다(5장). P0에 가상계좌와 일일 대사까지 넣어 첫 세로 한 줄이 무겁다. OpenSearch를 기본 스택에 넣어 로컬·최소 서버 메모리 부담이 커진다.
- **충분성: 중.** 프론트엔드 깊이를 증명하는 장치가 거의 없다(풀스택 전제와 어긋남). "AI 없이 설명하는 능력"(C 공통 기반 2)이 빠졌다.
- **판정: 조건부 수용.** 조건은 ①P0 축소(가상계좌·대사는 P1), ②OpenSearch는 2단계, ③프론트 품질 지표 추가, ④차별화 근거를 '측정 비교'에서 '종단 운영 증거'로 옮기는 것.

### B2. 입점형 오픈마켓 + 정산·대사 + 셀러 백오피스
- **신빙성: 중.** 토스 부분취소·과세 규칙은 공식 문서다. **대규모유통업법 개정안의 오픈마켓 적용은 기사상 불명확하다(재확인 #12).** "규제가 오픈마켓 정산 설계의 근거"라는 연결은 과장이다. 와이톤 공고는 애그리게이터 경유라 A가 재확인하지 못했다.
- **논리: 중.** 차별화(정산은 드묾)는 그럴듯하지만, B 스스로 "정산 우대 신입 공고 수 미확인"이라고 인정했다. 시각적 설득력이 약하다는 자기 평가는 타당하다.
- **충분성: 중하.** 정산 실무 규칙(세금계산서, 부가세, 지급 보류)이 비어 있다.
- **판정: 조건부 수용(2단계 확장으로).** 단독 1차 프로젝트로는 범위 위험이 크다. 1순위 코어를 끝낸 뒤 '판매자(위탁자) 정산'으로 확장하는 경로를 권한다.

### B3. AI 네이티브 커머스: 뷰티 버티컬 + 자연어 검색·리뷰 요약·MCP
- **신빙성: 중.** 무신사 MCP·리뷰 2,100만 건(디지털투데이 CTO 인터뷰)과 와이톤 LLM 게이트웨이는 A가 재확인하지 못했다. F&F 자격요건(RAG·에이전트)은 A도 원문으로 확인했다(3년 이상 공고).
- **논리: 중.** "MCP 서버로 외부 AI 에이전트가 장바구니를 쓰게 한다"는 세 보고서 중 가장 새로운 아이디어다. 하지만 근거 공고가 경력직이고, 뷰티는 옵션이 단순해 재고 난제가 얕다(B 자인). 컨셉과 플러스 알파가 서로를 약하게 만든다.
- **충분성: 중하.** LLM 비용과 평가 방법을 조사하지 않았다.
- **판정: 조건부 수용(확장 모듈로).** 뷰티 컨셉은 기각한다. 하이브리드 검색·MCP·리뷰 요약은 1순위 위에 얹는 3단계 모듈로 흡수한다.

### C1. 정시 드롭 패션 커머스: 재고와 돈의 정합성을 수치로 증명
- **신빙성: 중상.** AWS 공식 가격 JSON 추출은 세 보고서 중 가장 엄밀했다. 한경 일화는 확인됐다. 하지만 SPRi 귀속 오류(#8), 온라인쇼핑 통계 월 혼동(#13), 근거 없는 "네이버·카카오 금지"를 그대로 수용한 점(#17)이 있다.
- **논리: 중상.** "공통 기반 2: AI 없이도 설명"은 AI 허용·금지 전형이 섞인 시장(가-3)에서 바로 나온 논리적 귀결이다. 세 보고서 중 가장 균형 잡혀 있다. "드롭 1회 리플레이" 시연 설계는 구체적이다. 한계 1(차별화 근거는 일화 1건)을 스스로 짚었다.
- **충분성: 중.** 프론트 품질 증명이 약하고, 리커머스 전환(자기가 찾은 N25)의 함의를 컨셉에 반영하지 않았다.
- **판정: 조건부 수용.** B1과 같은 조건이고, 추가로 컨셉을 '드롭 중심'에서 '1점 상품(리커머스) 포함'으로 보완하는 것을 제안한다(3장).

### C2. 입점형 오픈마켓: 셀러, 정산, 운영 백오피스
- **신빙성: 중.** 에이블리 인턴 공고(셀러 플랫폼·백오피스)는 신입·인턴 수준의 직접 근거라 가치가 크다(A는 재확인 못 함). 티메프 재발방지책(2024-10)은 시행 여부가 미확인이다.
- **논리: 중.** M0에서 하위 주문 구조를 미리 정하라는 조언은 정확하다(나중에 정산을 붙이려면 필요).
- **판정: 조건부 수용(2단계 확장으로).** B2와 병합한다.

### C3. 권역 재고·배송 슬롯 장보기
- **신빙성: 중.** 근거가 컬리에 편중됐다(C 자인). 지도 API 비용·약관을 조사하지 않았다.
- **논리: 중.** "같은 동시성 기술을 시간 슬롯에 적용해 흔한 선착순과 차별화"는 좋은 발상이다. 하지만 물류 시뮬레이션 비중 때문에 일반 커머스 역량이 덜 드러나고, 채용 연결성(컬리·B마트 계열 소수)이 약하다.
- **판정: 기각(단독 3순위로는).** 다만 "재고 이외의 희소 자원 동시성"이라는 발상은 공통 맹점 해소에 쓸 만하다(5장).

### A1(자기). 검증 가능한 바이브 코딩으로 만든 드롭형 패션 커머스, AI 하네스 + 정합성 실증
- **신빙성: 중상.** 1차 근거는 재확인으로 유지된다. 하지만 **Spring Boot "4.0.x" 권고는 낡았다**(4.1.0이 2026-06-10에 출시). 최소 비용은 Lightsail을 검토하지 않아 과대 추정했다(5만 원 vs 3.3만 원). EC2 단가는 제3자 반올림값을 썼다.

- **충분성: 중.** 프론트 깊이와 "AI 없이 설명"이 빠졌다. 사람인·점핏 데이터의 DevOps 수요 초과 신호를 보지 못했다.

## 5. 공통 맹점과 같은 모델 편향 점검

### 5-1. 세 보고서의 1순위가 같은 이유: 근거인가, 패턴인가
**결론: 근거도 있지만, 패턴 효과가 더 크게 작용했다고 본다.**

1. **같은 검색 결과 집합을 공유했다.** 세 보고서의 핵심 근거가 거의 같다. 무신사 리멤버 공고, 크몽 550%, Shopify 재고 예약, 토스 문서, 원티드 키워드 분석, 한경 앤트로픽 기사가 모두 겹친다. 같은 날 같은 검색 엔진에서 같은 상위 결과를 받았으므로, 이것을 독립적인 세 번의 교차검증으로 볼 수 없다.
2. **결정적 증거: 2026년 공개 저장소가 세 보고서의 1순위를 이미 구현하고 있다.**
   - `hyinorbit-code/coupon-consistency-lab`(열람): "선착순 무료 쿠폰 드롭으로 동시성 제어, 성능 개선, 장애 복구 후 데이터 정합성을 재현하고 측정"한다. 스택은 **Java 25, Spring Boot 4.1, Spring Modulith, MySQL 8.4, Flyway, Testcontainers, Docker Compose**이고, 이후 k6·Redis·Kafka·Outbox를 도입할 예정이다. **Claude Code 사용과 ADR**을 명시했고 React SPA를 S3 + CloudFront로 배포한다. 우리가 낸 제안과 스택·방법론이 거의 같다. 단, 아직 1단계 구현 전이고 스타는 0개다.
   - `Jjiggu/CouponToyProject` PR #28(2026-10-27, 열람): 격리 수준·비관/낙관 락·Redis(MULTI/WATCH/Lua)·Async·Pub/Sub·Streams까지 10단계로 비교했다. EC2 부하 테스트 결과 145 TPS → 1,900 → 4,800 TPS, 요청 123만 건에 정합성 100%, SIGKILL·Redis 재시작 후 유실 검증, 대사 API, CLAUDE.md까지 갖췄다. **우리가 '차별화 조건'이라고 한 "같은 조건 측정 비교 + 장애 재현 + 수치 공개"를 이미 높은 수준으로 해냈다.**
   - GitHub 저장소 검색(이름·설명만 매칭하므로 하한값): '선착순' 402개, '재고 동시성' 66개(상위는 인프런 강의 실습). '토스페이먼츠 쇼핑몰'은 17개이고, 대부분 최근의 Next.js + Supabase 바이브 코딩 쇼핑몰이다.
   - **함의**: AI에게 "2026년 취업용 커머스 포트폴리오"를 물으면 같은 답(드롭 + 락 비교 + Boot 4 + MySQL 8.4 + Testcontainers + k6 + ADR + AI 로그)이 나온다. 이 답을 따르는 지원자는 더 늘 것이다. **이 설계는 '차별화'가 아니라 '최소 자격(table stakes)'이 되어 가고 있다.**
3. **반대 증거(이 방향이 여전히 유효한 이유)**:
   - 무신사 Catalog PE 자격요건이 "동시성 제어(분산 락, 낙관적 락)"를 명시한다. 즉 이 역량은 실제로 요구된다(필요조건).
   - 위 저장소들은 스타 0개의 개인 프로젝트다. 시장에 넘쳐나는 것은 '주제'이지, 높은 완성도의 결과물은 아직 드물 수 있다.
   - "PG 웹훅 + 멱등 + 재고 + 아웃박스 + 환불 + 배송 + 부하 테스트를 한 저장소에서 종단으로 다룬 사례"는 이번 검색에서 찾지 못했다. 다만 검색 1회에 기반한 약한 증거다.
   - **정리**: 동시성·측정은 빼면 감점이고, 넣어도 가점이 크지 않다. 차별화는 다른 곳에서 찾아야 한다.

### 5-2. 세 보고서가 공통으로 놓친 것
1. **풀스택인데 프론트엔드 증명 장치가 없다.** 세 제안 모두 백엔드 실험이 중심이다. 그런데 키워드 수는 React가 Spring Boot보다 많다(잡코리아 893 vs 506, 사람인 916 vs 588). 커머스 FE 공고(컬리·무신사)는 TypeScript, React, Next.js, TanStack Query, 테스트(Jest·Storybook)를 요구한다(B 라-3). 프론트 쪽 측정 가능한 품질 지표가 필요하다. 예를 들어 Core Web Vitals, 번들 크기, 접근성 점검, Playwright E2E로 '주문 → 결제 → 환불' 여정 자동 테스트, 낙관적 UI·에러·로딩 상태 설계가 있다. **이 부분은 근거 조사가 부족하다**(국내 FE 신입 공고 원문 확인은 다음 라운드 과제).
2. **'운영 가능성(Operability)'이 플러스 알파로 과소평가됐다.** 사람인·점핏 2025 상반기 리포트(재확인 #7)에서 DevOps·시스템 엔지니어는 공고 비중(11.1%)이 지원 비중(10.2%)보다 크다. 반면 백엔드는 지원 비중(23.5%)이 공고 비중(16.2%)보다 크다. 백엔드는 공급 과잉이고 운영 역량은 상대적으로 공급 부족이다. 이 신호는 크몽(배포·출시가 1위 병목), 오늘의집 올리고(인프라·인증·보안 허들), 컬리 자격요건(배포·모니터링·트러블슈팅)과 일치한다. 세 보고서는 클라우드를 늦추라는 사용자 조건 때문에 운영을 마지막 단계로 미뤘다. 하지만 **CI/CD, 관측성, 장애 훈련, 런북, 롤백, 백업·복구 리허설, IaC 준비는 로컬에서도 할 수 있다.**
3. **"AI 하네스가 평가받는다"는 직접 증거는 세 보고서 모두 없다.** 그런데도 셋 다 이를 플러스 알파의 축으로 삼았다. 이것도 같은 모델 편향일 가능성이 있다. 근거 수준에 맞게 '위생 요건'(하면 좋고 비용이 싸다)으로 내리고, 주된 차별화 축에서는 빼야 한다.
4. **"클론 프로젝트"로 보일 위험의 해법이 약하다.** 세 보고서 모두 이 위험을 언급만 하고 해법(컨셉 차별화)을 내지 못했다. 3장의 리커머스 컨셉이 그 대안이다.
5. **완주 위험**(바이브 코딩 3~6개월). B와 C는 범위가 크다고 인정했지만, '여기서 멈춰도 포트폴리오가 성립하는 지점'을 단계마다 정의한 것은 A뿐이고 그마저 한 줄이다. 합의안에는 **릴리스 단위(R1~R4)마다 공개 가능한 상태**를 정의해야 한다.
6. **사용자의 실제 목표 회사를 모른 채 커머스 대기업 기준으로 역산했다.** 세 보고서 모두 질문으로 남겼다. 그러나 답에 따라 우선순위가 바뀔 수 있다는 점(SI → Java·Oracle·코테, 스타트업 → 속도·풀스택·AI)을 합의안에 명시해야 한다.

## 6. 최종 입장

### 6-1. 최종 제안 1~3순위

**1순위: "운영 가능한 패션 커머스" — 신품 편집숍 + 1점 위탁 리커머스(또는 드롭), 엔드투엔드 정합성과 운영 증거로 증명하는 풀스택**
- **핵심 내용**: 탐색 → 장바구니 → 주문 → 토스페이먼츠(테스트) 결제 → 모의 택배 → 취소·부분취소·반품·환불까지 한 시스템에서 **돈과 재고가 한 건도 어긋나지 않는다**는 것을 테스트·부하·장애 주입·대사로 증명한다.
- 차별화 축은 세 개다. ①단일 주제 랩이 아닌 **종단 운영 정합성**, ②로컬에서부터 쌓는 **운영 가능성**(CI/CD, 관측, 장애 훈련, 런북, 백업·복구 리허설, 이후 클라우드에서 재현), ③**측정 가능한 프론트 품질**(Core Web Vitals, 접근성, Playwright E2E).
- 락 비교 실험과 AI 개발 하네스(규칙, ADR, AI 오류 로그), "AI 없이 설명하기"는 **필수 위생 요건**으로 포함하되 주된 차별화 근거로 내세우지 않는다.
- **기반한 원래 제안**: A1 + B1 + C1 병합. C1의 공통 기반 2와 시연 설계, B1의 포화 인식과 카드형 README, A1의 Phase 구조를 쓴다.
- **순위 이유**: 근거 밀도가 가장 높다(채용공고, 공식 문서, 기술 블로그, 세 에이전트 독립 결론). 5장의 포화 증거를 반영해 차별화 축을 수정했다. 사람인·점핏의 DevOps 수요 초과 신호와 크몽·올리고의 배포 병목 신호로 '운영 가능성'의 근거를 보강했다.

**2순위: "위탁자·셀러 정산과 대사" 확장 — 마켓플레이스/위탁 정산 파이프라인**
- **핵심 내용**: 1순위 코어 위에 위탁자(리커머스) 또는 입점 셀러를 추가한다.
- 구현 대상은 하위 주문 분할, 쿠폰 안분, 부분 취소 금액 재계산, 구매확정 배치, 정산 원장(재실행 안전), PG 거래 대 주문 원장 일일 대사, 불일치 처리 화면이다.
- M0에서 하위 주문 구조만은 미리 정해 둔다(C2 조언).
- 법·규제(대규모유통업법)는 근거로 쓰지 않는다. 적용 범위가 불명확하다(재확인 #12).
- **기반한 원래 제안**: A2 + B2 + C2 병합.
- **순위 이유**: 차별화 잠재력은 크다(세 에이전트 판단). 하지만 신입 채용에서 정산 경험이 가점이라는 직접 근거가 없다. 단독으로 하면 범위와 시연 효과 위험이 크다. 1순위의 리커머스 컨셉을 택하면 위탁 정산으로 자연스럽게 이어진다.

**3순위: "AI 기능 서비스화" 확장 — 하이브리드 검색·MCP 쇼핑 도구·운영 AI(사진 태깅/상태 등급)**
- **핵심 내용**: 1순위 코어 위에 다음을 얹는다.
  - OpenSearch(nori + 벡터) 하이브리드 검색과 오프라인 평가셋
  - MCP 서버(검색·상품 조회·장바구니 담기, 사용자 확인 단계와 권한 포함, B3)
  - 리커머스 운영용 사진 기반 자동 태깅·상태 등급 초안(사람이 승인)
- 모든 AI 기능에 끄는 스위치와 폴백, 비용 상한, 프롬프트 인젝션 테스트를 둔다.
- **기반한 원래 제안**: A3 + B3 병합(뷰티 컨셉은 제외).
- **순위 이유**: 트렌드 근거는 가장 강하다(원티드 AI Native 8배, F&F 자격요건). 하지만 신입 직결 근거가 약하고, 비용·평가 불확실성이 크며, 코어 깊이를 희석할 위험이 있다. C3(퀵커머스)는 채용 연결성이 약해 3순위 후보에서 뺐다.

### 6-2. 최종 사이트 컨셉

  - 타깃: 가성비와 지속가능성을 중시하는 20~30대 패션 관심층과 옷장 정리를 원하는 위탁자

### 6-4. 배포 비용 결론과 클라우드 전환 시점

  - **부하 테스트 일시 확장**: c7g.large($0.0816/h, 공식) 3대 × 8시간 + DB 상향 ≈ $3~5 ≈ **4천~7천 원/회**. C 구성(24시간, ALB 포함)은 약 2.2만 원/회

### 6-5. 의견이 갈릴 지점과 양보 범위
1. **컨셉(리커머스 1점 위탁 vs 신품 + 드롭)**: A만 리커머스를 제안했다. **양보 가능.** B·C가 반대하면 '신품 + 드롭'을 1안으로 받아들인다. 단, 리커머스를 '대안'으로 기록하고, 드롭을 유일한 차별 요소로 두지 않는다는 조건이다.
2. **차별화 축(AI 하네스·측정 비교 vs 종단 운영 정합성·운영 가능성·FE 품질)**: A는 5장 근거로 축을 옮기자고 주장한다. **부분 양보 가능.** 제목에 'AI 검증 프로세스'를 남기는 것은 수용한다. 하지만 "측정 비교 실험이 차별화"라는 주장은 공개 저장소 반례(5-1)가 있어 합의 문구에 그대로 넣는 것에 반대한다.
3. **FE 품질 지표 추가**: A의 신규 주장이다. 근거는 키워드 수와 FE 공고 요구다. 다만 국내 FE 신입 공고 원문 확인이 부족하다. **우선순위 조정에는 양보 가능**(P1로 내려도 됨). 제외에는 반대한다(풀스택 전제).
4. **최소 비용 서비스(Lightsail vs EC2)**: **양보 가능.** 최소 비용은 Lightsail(B)로 하고, 지원 기간에는 EC2+RDS 표준 구성을 권고하는 병기안을 제안한다.
5. **OpenSearch 도입 시점(B는 기본 스택, A·C는 2~3단계)**: **양보 가능.** 2단계로 합의를 제안한다.
6. **3순위(AI 확장 vs C3 퀵커머스)**: A는 C3 기각을 주장하지만, C가 강하게 원하면 'AI 확장'과 함께 '희소 자원 동시성(배송 슬롯)'을 선택 모듈로 넣는 절충을 수용할 수 있다.
7. **양보하지 않을 것**:
   - Spring Boot 4.1.x와 MySQL 8.4 LTS로 버전을 고정할 것
   - "AI 하네스가 채용에서 평가받는다"를 사실처럼 쓰지 말 것
   - 수치 충돌 해소 결과(4장)를 그대로 반영할 것
